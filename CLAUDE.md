# Kaldi Annex: homelab prototype (M0 and M1)

The brief is `docs/brief.md` (historical). The current system on one page is `docs/architecture.md`: read both before changing anything. Later milestones' plans are in `docs/plans/` (`m1.md` is Nejc's M1 plan; `m1.2.md`–`m1.5.md` the step-by-step plans). Decisions and their reasons are in `docs/decisions.md` (an index with status at its top shows what was revised or superseded).

## Ground rules (from the brief)
- **Synthetic data only.** Never use, copy or connect to real client data or systems, Cadro included.
- **LAN only.** No port forwarding, tunnels to the internet or public DNS. SSH port forwards from the Mac for testing are fine.
- **Pin every image version.** No `:latest`. Images must support amd64; the VM is x86_64.
- **Where you may write:**
  - on the VM (`ssh annex`), only Docker and `/srv/annex`;
  - on the Mac, only this repo.
- **Ask Nejc before:**
  - adding a component that isn't in the brief's stack;
  - changing the app contract;
  - changing VM system config (packages, firewall, users, systemd). `annex` has passwordless sudo, but that doesn't make system changes allowed.
- **Never run system changes yourself.** That covers the Mac and the homelab: trusting the mkcert CA, the Docker context, registering the MCP server, `/etc/hosts`, and the Traefik on `dronky`. Write the exact commands and their undo commands into `docs/setup.md` and ask Nejc to run them.
- **Never touch `dronky`** beyond using it as the SSH jump host.
- **Log decisions** in `docs/decisions.md`: what, why, alternatives considered.
- Destructive VM operations (`scripts/wipe-vm.sh`) need Nejc's go-ahead.

## Layout
The whole picture (containers, networks, files on the VM, the deploy sequence, ops threads) is `docs/architecture.md`; the notes below are what to know when editing.
- `compose.yaml` (+ `compose.tls-local.yaml`): the platform. Runs on the VM from `/srv/annex/platform`. It declares no app networks: each app has its own internal `annex-app-<name>` (optional `annex-egress-<name>`), made by `annex_vm.py networks-sync`, which connects Traefik, ops, the gateway and appdata-db to it at runtime (D88). After recreating one of those four by hand, run `networks-sync` (`push.sh` does).
- `config/`: Traefik, Authelia and Homepage config. `*.tmpl` files are rendered by `scripts/render.py` using `{{VAR}}` placeholders.
- `db/product/`: synthetic product DB (schema, seed, `api_views.sql` = the gateway allowlist). `db/appdata/`: app database init and backup hook; `bootstrap.sql` is the annex_ops database, its roles and passwords (idempotent, applied on every push); `migrations/NNN_name.sql` is annex-ops's schema, applied in order by `vm/migrate.py` from `push.sh`, each in one transaction and recorded in `annex_ops.schema_version` (D93). A change to an existing table is a new migration file; never edit an applied one.
- `ops/`: the annex-ops service (all database access goes through `db.connect()`'s small own pool: ops 4 connections, console and hooks 2, D84; threads register in `threads.py` and show on `/healthz`, D81; buffers are byte-bounded, D86) (FastAPI: email via SMTP/Mailpit and Slack for apps, the send log, the alert engine (Docker/log watchers, the health checker `health.py`, incidents; messages go through `annex_ops.outbox` and the sender thread `sender.py`, D90) and usage stats (`usage.py`, `digest.py`: what counts, signals, tiles, the weekly digest; logins never leave `annex usage <app> --by-user`); incoming webhooks (`hooks_*.py`: signature checks, storage, retried delivery; the **only** route without a login, served only under `/h/` by `hooks_app.py`, which runs in its **own container** (`hooks`, D55) with an insert-only DB role; secrets in `secrets/hooks/<app>.json`, never in the database); host and backup monitoring (`host.py`, D56; it also stores a sample every 5 minutes in `host_samples` for the console's Platform page, D76); stored logs that outlive containers (`logship.py` follows and parses, `logstore.py` inserts, partitions and queries; D61-D66); error groups from those logs (`errors_group.py` pure, `errors_run.py` scanner and emails; D67-D68); the **console** (`console_app.py` routes, `console_data.py` queries and ranking, `console_view.py` helpers and the page shell, `console_pages_overview.py` / `console_pages_app.py` / `console_pages_admin.py` pages; all pure and no JavaScript; its **own container**, `console`, D69-D70, D76: read-only DB role `annex_console`, on `platform` and `annex-console` only, never `edge` or `appdata`, no Docker access); the audit trail (`audit.py`: sign-ins, webhook events and gateway aggregates are copied into `annex_ops.audit_events`; `annex_vm.py` writes the rest; `audit_timeline` view adds the send log; D71-D72); later audit). The engine (`engine.py`) is pure: no DB, network or clock of its own; its `now` is monotonic, and `incidents.py` converts wall times at the edges (D90). Built on the VM from the synced bundle. Unit tests: `uv run --python 3.13 --with-requirements ops/requirements.txt --with pytest pytest ops/tests -q`.
- `tests/annex-selftest/`: **Annex's own test app**, the one fixture every platform suite deploys (a stand-in for a client's app that uses every feature on demand: identity, gateway, Postgres, files, email, Slack on `#annex-selftest`, webhooks, error and alert switches, jobs; see its `main.py` for the endpoints). Suites build variants of it with `scripts/selftest.py` (`selftest_build`/`selftest_deploy` in `scripts/testlib.sh`). **Platform tests never use `examples/` or a client's app** (`scripts/test-examples.sh` checks the demo apps separately, before a demo). Test runs switch on **test mode** (D74): every Slack post goes to `#annex-selftest`, marked [TEST]. The Metabase "Annex usage" dashboard is retired (D76); usage lives in the console.
- `vm/`: scripts that run **on the VM** (secrets, Metabase setup). They are synced with the platform.
- `scripts/`: scripts that run **on the Mac**. Source `scripts/lib.sh` for `vm`, `setting`, `render`; test suites also source `scripts/testlib.sh` (results, the tunnel, logins, Mailpit, `wait_healthy`). `scripts/test-smoke.sh` is the quick check after a push; `scripts/test-all.sh` runs everything (long: ask first).
- `cli/`: the `annex` CLI (uv project). `ops.py` holds the operations shared with the MCP server, `manifest.py` validates `annex.yaml`, and `contract.md` is the app contract (`docs/app-contract.md` links to it). Agents get it in parts (D74): `annex contract` is the core, `annex contract <topic>` one section, by the map `CONTRACT_TOPICS` in `ops.py`; a new section is core unless you add it there. Run it with `./annex`.
- `vm/annex_vm.py`: the VM side of app provisioning (DB, gateway role and JWT, secrets) and of user accounts (`users-*`, D57: Authelia's `users.yml` and the user directory). Stdlib only, except PyYAML (Ubuntu's `python3-yaml`) for the users commands; prints JSON, never secret values (except a `--print-password` asked for by a human). Unit tests: `python3 -m unittest discover -s vm/tests`.
- `templates/<name>/`: app templates (`__APP_NAME__` and `__OWNER__` are replaced by `annex init`). `examples/`: demo apps. `runtime/`: the one source of `annex_runtime.py`/`.js` and the browser script `annex-errors.js`; templates, examples and fixtures carry copies, kept identical by `scripts/sync-runtime.sh` (`--check` runs in `test-all.sh`). Edit `runtime/`, then sync.
- `mcp/`: the MCP server (stdio, `mcp` 2.x), a thin layer over `annex_cli.ops`. `skills/annex/SKILL.md`: the Claude Code skill (symlinked into `~/.claude/skills`).
- `democlient/`: **a client's own database, not the platform** (Goat Arcade, D77-D78): compose project `democlient` on the VM, unlabelled, its only network `annex-clientlink`; run with `scripts/democlient.sh up|link|status|check|reseed|dictionary`. product-db reads it with postgres_fdw (`db/product/clientlink/`); its views are in `annex_api` like any other, every column commented. Handoff for builders and their agents: `docs/goat-arcade/`. `reseed` wipes its data (ask first, like other destructive operations).
- `docs/demo.md` + `scripts/reset-demo.sh`: the management demo. Don't run `reset-demo.sh` without Nejc's go-ahead: it removes apps that aren't examples, with their data.

## Conventions
- Settings live in `.env` (gitignored; copy `.env.example`). `scripts/render.py` derives everything else into `.build/platform/.env`, which is also the platform's `.env` on the VM and the CLI's source of truth.
- Secrets are generated on the VM by `vm/bootstrap-secrets.sh` and live only in `/srv/annex/secrets`. Never commit them or write them into the repo.
- Everything Annex creates carries the label `com.kaldi.annex=true`. Compose projects are `annex` and `annex-app-<name>`. Networks are named `annex-<name>`.
- Every platform container has a memory limit and a healthcheck. Keep the platform under about 2.5 GiB of RAM.
- Shell: bash, `set -euo pipefail` (via `lib.sh`). Python: 3.12+ on the Mac via uv; VM-side scripts use bash, jq and the VM's stock python3 only.
- Apps: `./annex deploy <folder>`, then `scripts/test-apps.sh`. Validation errors must say what's wrong and how to fix it, because agents read them.
- Human-only commands (never over MCP): `annex secret set <app> KEY` (value from stdin or `--from-file`; `KEY=VALUE` works but warns, D85), `annex remove`, `annex users`, `annex migrate-networks`, `rollback --with-data`.
- Deploys take a per-app lock and leave a pending release record; a dead one is reconciled by the next deploy or `annex_vm.py deploy-reconcile <app>` (D92). Builds are refused on low disk or an image over 2 GB (D95); images may not carry platform labels (D83). `push.sh` refuses a checkout that lacks the VM's commit unless `--force` (D85).
- Web templates, examples and the fixture enable the CSRF check; `env: {ANNEX_CSRF: "off"}` opts out (D91). Raise `ANNEX_CONTRACT_VERSION` / the runtime's `__version__` when a rule or helper changes (D94); `scripts/sync-contract.sh --check`.
- User accounts are managed with `./annex users` (human only). Don't edit `secrets/authelia/users.yml` by hand while Authelia runs: `annex_vm.py` writes it atomically and twice (D57).
- Temporary files on the VM go under `/srv/annex`, never `/tmp` (the write rule above). One-off containers: `docker run --rm` with a command that exits by itself; never cut a server's output short with `| head`, which leaves it running (three stray server containers ran for 18 hours that way).
- After changing platform files: `scripts/push.sh` (add `--extras` for Metabase and Dozzle), then **`scripts/test-smoke.sh`** (under a minute: every part once).
- **Long suites only when they're needed, and ask Nejc first.** Run the one suite for the part you changed (`scripts/test-<area>.sh`, a few minutes). `scripts/test-all.sh` (30+ minutes) and `scripts/test-alerts.sh` (20 minutes) only when the change concerns what they prove (timings, retries, "exactly one alert"), and tell Nejc before starting them.
- A change to a bind-mounted config file must trigger a recreate. `render.py` hashes `config/<service>` into `ANNEX_CONFIG_HASH_*` for this; add new services there when needed.
