## Push stamp (D85)
`render.py` writes `.build/vm/platform/VERSION` (`.build/local/platform` for the local stack, D99) (`commit=`, `dirty=`, `env_sha256=`), which goes to `/srv/annex/platform/VERSION` with the bundle. `scripts/push.sh` first reads the VM's `VERSION` and refuses when the commit on the VM is not an ancestor of your checkout's HEAD (a stale checkout or another branch would roll the platform back); it prints both commits. Fix it with `git fetch` and a merge or rebase, or knowingly override with `scripts/push.sh --force`. A first push (no `VERSION` on the VM) proceeds, the same commit passes, and a dirty tree is only labelled `(dirty)`. `--extras` and `--force` combine. Scripts read settings from `platform/.env` on the VM (`setting`: one `ssh cat` per run; a plain `cat` on the local stack), falling back to the local render before the first push.

## App networks (D88)
- **The shape.** Every app has its own internal network, `annex-app-<app>` (labels `com.kaldi.annex=true`, `com.kaldi.annex.app=<app>`), with an explicit /24 from `ANNEX_APP_SUBNETS` (default `10.213.0.0/16`, in `.env`; the lowest free one). On it: the app's container and exactly the platform containers it uses: `annex-traefik-1` (web apps: routes, the deploy's health gate), `annex-ops-1` as `ops` (always: health checks, webhook delivery, email and Slack), `annex-gateway-1` as `gateway` (apps with views), `annex-appdata-db-1` as `appdata-db` (apps with Postgres). So apps keep the URLs they had (`http://gateway:3000`, `http://ops:8000`, `appdata-db:5432`), and no two apps share a network. An app with a non-empty `egress:` also gets `annex-egress-<app>`, not internal, with only that app on it: internet (and LAN) access to any host, not filtered per hostname. Apps are on no network in `compose.yaml` (`annex-edge`, `annex-appdata` hold platform containers only).
- **Who keeps it so.** `vm/annex_vm.py networks-sync <app> [--web] [--postgres] [--views] [--egress]` creates the network(s) if needed, connects the platform containers the app uses and disconnects any other platform container; it is idempotent and prints JSON. `annex deploy` and `annex rollback` run it before `docker compose up`; `annex remove` (through `deprovision`) disconnects everything and removes both networks. With no app it does every app from `deploy/<app>/deploy.json` (`type`, `postgres`, `views`, `egress`) and also reports `still_shared` (app containers still on `annex-edge`/`annex-appdata`: deployed before D88) and `orphan_networks` (an app network with no `deploy.json`, e.g. an app whose first deploy failed).
- **After a recreate.** The platform containers join app networks with `docker network connect`, at runtime. That survives a container restart and a Docker restart, but **not a recreate**: a container that Compose replaces comes back with only the networks in `compose.yaml`. `scripts/push.sh` runs `networks-sync` after its appdata-db step and after the full start. If you recreate one by hand (`docker compose up -d --force-recreate gateway`, or an `up` after editing its config), run afterwards:
  ```
  ssh annex python3 /srv/annex/platform/vm/annex_vm.py networks-sync
  ```
  Until then the apps that use it can't reach it (a web app's route answers 502 after a Traefik recreate). Compose itself doesn't undo the connections: it only checks that a container is on the networks it declares, so the extra ones never trigger a recreate.
- **Apps deployed before D88** are on `annex-edge` (and `annex-appdata`) until they are recreated from a new compose file. Redeploy them from their source. Without the source (`vibe-leads`): `./annex migrate-networks <app>` rewrites only the networks of `deploy/<app>/compose.yaml` (the old one is kept as `compose.yaml.pre-d88`; to go back: copy it over `compose.yaml` and `docker compose up -d` in that folder), reads what the app uses from the file (routed: Traefik; on `annex-appdata`: appdata-db; a gateway URL: the gateway), records `egress` in `deploy.json`, runs `networks-sync` and recreates the container. Every app had the internet before D88: pass `--egress` if the app calls anything outside (the record then says `egress: ["*"]`). Human only.
- **Limits.** One Linux bridge and a /24 per app network and per egress network: the default range holds 256 of them; `networks-sync` says when it is full. Traefik and ops get one interface per app. Docker's own pools (172.17-31.x, 192.168.x) are untouched, and the range is not in them; `daemon.json` is unchanged.

## Database migrations (D93)
annex-ops's schema is `db/appdata/migrations/NNN_name.sql` (three digits, lower case, underscores). `scripts/push.sh` applies `db/appdata/bootstrap.sql` (the database, roles and passwords; every push) and then `vm/migrate.py`, which applies the files not yet in `annex_ops.schema_version`, in order, each in one transaction as role `annex_ops` together with its version row. It stops at the first failure and names the file; nothing of that file is kept.
- **Add a migration.** Create the next number (`005_what_it_does.sql`), idempotent where cheap (`IF NOT EXISTS`), with the grants for what it creates at its end (`GRANT SELECT ... TO annex_console`). Then `scripts/push.sh`. **Never edit an applied file**: a change to an existing table or view is a new file. No `CREATE INDEX CONCURRENTLY` and no `\c` (one transaction); no passwords (they are `bootstrap.sql`'s).
- **See what is applied or pending.** `ssh annex "cd /srv/annex/platform && python3 vm/migrate.py --list"` (pending only; applies nothing). Applied: `ssh annex docker exec annex-appdata-db-1 psql -U postgres -d annex_ops -c 'SELECT * FROM annex_ops.schema_version'`.
- **The first push after C3** finds `schema_version` empty and applies 001 to 004 in order. They are idempotent and 001 is the old file, so on the existing database they change nothing but the grants, which 001 resets and 002 to 004 give again, seconds apart.
- **Check (after a change to this mechanism).** `scripts/push.sh` twice: the second prints `0 applied, 4 already in place`. Then a scratch `db/appdata/migrations/099_scratch_fail.sql` containing `SELECT 1/0;` makes the push stop with `migration 099_scratch_fail.sql failed and was rolled back` and no row for it; remove the file and push again.

## Restore a whole VM (D87)
What a nightly archive holds: `backup/apps/<app>/data` and `releases.jsonl`, `backup/dumps/current/*.dump` (every database, custom format), `globals.sql` (roles with their password hashes), `MARKER`, `backup/secrets/` (everything, including `master.env`, the Authelia key and users, each app's tokens) and `backup/state/directory/`. Not in it: the Postgres data directories (rebuilt from the dumps), `deploy/` (app source and images: redeploy each app from its folder with `annex deploy`), `snapshots/`, `certs/` (reissued by `scripts/bootstrap.sh`), Metabase's own state beyond its database. product-db is synthetic data rebuilt by `push.sh`.

The archive contains the secrets: copy it only to places that may hold them, and delete scratch copies.

1. **Prepare the new VM** as in `docs/setup.md` (Docker, the `annex` user, `/srv/annex` owned by annex, the SSH config). Do **not** run `scripts/bootstrap.sh` yet: it would generate new secrets.
2. **Put the archive on the VM** (`scp annex-<time>.tar.gz annex:/srv/annex/backups/`; `chmod 700 /srv/annex/backups`, `chmod 600` the archive).
3. **Unpack the files** (sudo, so the owners in the archive are kept: ops runs as uid 10001 and reads `secrets/hooks` and `state/directory`):
   ```
   ssh annex 'cd /srv/annex && sudo tar -xzpf backups/annex-<time>.tar.gz --strip-components=1 --same-owner /backup/secrets /backup/state /backup/apps /backup/dumps'
   (The archive's member names start with `/backup/`; tar strips the leading slash with a notice. Checked on the VM on 22 Oct: secrets identical to the live ones, the dumps readable by `pg_restore --list`.)
   ```
   `secrets/` is now the old VM's. `.env` keeps the old values too if you restore the same `.env` on the Mac (`ANNEX_*` settings, domain, TLS mode).
4. **Bootstrap and push.** `scripts/bootstrap.sh` (it never replaces an existing secret, so it only fills the layout and reissues the certificate), then `scripts/push.sh`. The platform starts empty; Authelia has the old users and the apps' secrets are in place.
5. **Restore the databases** (appdata-db holds the app databases, `annex_ops`, Metabase's): the roles first, then each dump. `pg_restore --clean --if-exists --create` replaces the empty database the first start created:
   ```
   ssh annex 'cd /srv/annex && docker exec -i annex-appdata-db-1 psql -U postgres -f - < dumps/current/globals.sql'   # "already exists" errors for postgres and the platform roles are expected
   ssh annex 'cd /srv/annex && for f in dumps/current/*.dump; do docker exec -i annex-appdata-db-1 pg_restore -U postgres -d postgres --clean --if-exists --create < "$f"; done'
   ```
   Then `docker restart annex-ops-1 annex-hooks-1 annex-console-1` so they reconnect. `annex_ops.logs` and `health_checks` come back empty (D74).
6. **Redeploy the apps** from their source folders (`./annex deploy <folder>`). Each deploy provisions as usual with the restored secrets and keeps the restored database and `/data` (`apps/<app>/data` came back with step 3). `releases.jsonl` is restored, so release numbers continue.
7. **Check:** `scripts/test-smoke.sh`, `./annex users list`, the console's Platform page, and `ctl host` shows the dump age near zero after `scripts/backup.sh`.

**Try it without touching the VM's data (a scratch directory).** Same unpack with a different target, plus a throwaway Postgres on the dumps:
```
ssh annex 'mkdir -p /srv/annex/restore-scratch && cd /srv/annex/restore-scratch && sudo tar -xzpf ../backups/annex-<time>.tar.gz --strip-components=1 --same-owner /backup/secrets /backup/state /backup/apps /backup/dumps'
ssh annex 'cd /srv/annex && sudo diff -rq secrets restore-scratch/secrets'          # only changes since the archive was taken
ssh annex 'cat /srv/annex/restore-scratch/dumps/current/MARKER'
ssh annex 'docker run -d --rm --name annex-restore-scratch -e POSTGRES_PASSWORD=scratch --network none postgres:16.15-alpine3.24'
# wait a few seconds, then for each dump: docker exec -i annex-restore-scratch pg_restore -U postgres -d postgres --create < dump, then \dt in the databases
ssh annex 'docker rm -f annex-restore-scratch; sudo rm -rf /srv/annex/restore-scratch'
```

## Console (M2.4, D69–D70, D76)
- **What:** `console.<domain>` (`ANNEX_HOST_CONSOLE`; add it to `/etc/hosts`, docs/setup.md): server-rendered, read-only pages, no JavaScript (charts are inline SVG, filters are links, tabs are URLs). Redone in M2.7–M2.9 (D76): **one home per thing**.
  - `/` **Overview**: a ranked "Needs attention" list (down apps, platform incidents, failed jobs and releases, new error groups; a silent health checker is itself an item, so green never means "nobody is looking"), five KPI tiles, the most urgent apps (users with a 14-day sparkline, errors, last deploy, one signal chip) and, for admins, the platform card and the latest activity. Owners get the same for their apps.
  - `/apps`: the apps list with filters (All, Needs attention, Dormant, Graduating, Mine) and a search by name or owner.
  - `/apps/<app>`: tabs, each a URL: **Summary** (usage tiles, everything wrong with the app in one list, jobs, latest releases and warnings), `/logs`, `/errors`, `/releases`, `/usage` (30-day charts; per person for admins), `/config` (grouped; names of variables, never values).
  - `/status`: every app and platform part, up or down, for everyone signed in (the same component as the overview's health).
  - `/audit` (also `/activity`, admins): the activity timeline, with chips (Deploys, Access, Data reads, Messages, Webhooks, Failures, Platform) and incidents opening and closing merged in. `/platform` (admins): the server (disk, memory, newest backup, from `annex_ops.host_samples`), platform incidents and links to Dozzle, Metabase, Mail and the gateway.
- **Who sees what:** from `Remote-User` and `Remote-Groups`. An app's pages: its owner (`owner:` in annex.yaml, a claim and not a verified identity yet, D58) and admins; anyone else gets a 403, and so does a name that isn't an app (so the console doesn't list what exists); admins get a 404 for those. Apps deployed before release records (`vibe-leads`) have no owner here: admins only.
- **Why it's trustworthy:** the container (the ops image, `uvicorn annex_ops.console_app:app`) is on `platform` (Traefik) and `annex-console`, an internal network shared only with appdata-db, never on an app's network (apps are each on their own, D88), so an app can't reach it and forge a `Remote-User`; Traefik's `strip-identity` blanks what a browser sends. Its database role `annex_console` can only `SELECT` what the pages show: no `app_grants`, no webhook bodies or headers (column grants), no cursors, no writes. No Docker socket, no SMTP or Slack token, no secrets, no mounts, read-only filesystem, 96 MiB. Anything on `platform` (annex-ops, Homepage...) could call it directly with forged headers; those are platform components, as with Dozzle (D2).
- **What it reads:** the same functions the CLI uses (`usage.usage_app`, `errors_run.list_groups`, `logstore.query_logs`, `incidents.list_incidents`), so its numbers are `annex status`'s, `annex usage`'s and `annex logs`'s; health is the health checker's results (`annex_ops.health_checks`). Logs of apps are shown escaped; the pages carry a CSP that allows no script.

## Audit trail (M2.5, D71–D72)
- **Read it:** `./annex audit [--app x] [--since 7d] [--action deploy] [--actor y] [-n 100]`, or the console's **Activity** page (admins; `/audit`). One timeline, newest first, kept a year (`audit_retention_days`): who deployed (`deploy`, `deploy.failed`, `rollback` with `from`/`to`/`with_data`, `data.restored`), who set a secret (`secret.set`, names only), who removed an app (`app.removed`), accounts (`user.added`, `user.changed`, `user.removed`, `user.reset`), sign-ins (`signin`, `signin.failed`), which data an app read (`gateway.reads`: per app, view and hour, with the number of requests), what was sent (`email.sent`, `email.rejected`, `slack.sent`... with recipients, never a body) and webhook events received (`webhook.received`, `webhook.rejected`: the hook and app, never a body). `--action` takes a prefix: `--action user`, `--action signin`.
- **Actors:** a CLI action's actor is `user@host` (or `$ANNEX_USER`), as the CLI reports it: **not verified** (D58). An MCP action has `via: mcp` in its details. A sign-in's actor is the login; an app's reads are `app:<name>`; Annex's own alerts are `annex-ops`. A failed sign-in whose username doesn't look like a login (it may be a password typed in the wrong box) is recorded with no actor.
- **Where it comes from:** `annex_vm.py` writes a row as it does the change (a release record writes the release row and its audit row in one call; `release-backfill` adds the history of every `releases.jsonl`, idempotently); annex-ops's `Auditor` thread copies sign-ins from the stored Authelia lines (Authelia now logs at **debug**, because that is the only level at which it logs a *successful* sign-in; annex-ops ships only the sign-in lines, D71), webhook event metadata, and sums the stored gateway lines into buckets (`audit_bucket_s`, 3600; `audit_scan_s`, 60). The send log is read as it is, through the `audit_timeline` view, so the console's role needs no access to `sends`.
- **Limits:** if `annex_vm.py` can't reach the database it says so on stderr and carries on (the change has already happened); the backfill catches up deploys but not secret, account or removal events.

## Tests, the self-test app and test mode (D74)
- **One fixture:** the platform suites deploy `tests/annex-selftest` (and variants of it, `annex-selftest-<what>`), never an example app or a client's app, because those change per client. It is a `web+job` app that uses every feature on demand: `/whoami`, gateway reads (`/gateway/<view>`), Postgres (`/db`), files, `notify` email and Slack (`#annex-selftest`), webhooks (`/hooks/*`), error switches (`/raise`, `/boom`, `/emit` with fake secrets), alert switches (`/data/crashes`, `/data/failjob`, `/data/unhealthy`, `/fail500`), a plain-text logging mode and jobs `tick` (every minute), `work` and `notify` (by hand: `annex run annex-selftest work`). **To diagnose a platform feature in production-like conditions, deploy it** (`scripts/selftest.py build DIR`, then `annex deploy DIR`).
- **Slack in tests:** while a suite runs, annex-ops is in **test mode**: the file `state/ops/test-mode` holds an end time (3 hours ahead, written by `scripts/testlib.sh` when a suite starts and removed when it exits), and every Slack post, the apps' and the platform's alerts alike, goes to `#annex-selftest` as `[TEST] ... (test run: this was meant for #channel)`. The send log marks the row "test mode: posted to ...". `ctl info` shows whether it is on. A suite that dies leaves the file behind, which stops mattering after its end time. `ANNEX_TEST_MODE=0` runs a suite without it. **`#annex-selftest` must exist and the Annex app must be invited to it**, or the posts fail (and `test-notify.sh` says so).
- **The demo apps** (`examples/`) are checked by `scripts/test-examples.sh`, before a demo.

## Logs
- Apps: `./annex logs <app>`, or Dozzle at `logs.` (admins). Apps log JSON lines (`ts`, `level`, `msg`, and `request_id` and `user` inside a request): the logging convention is in the contract, and `annex deploy` warns (never refuses) when a web app's first lines aren't structured. One request's id is in the app's response header (`X-Request-Id`), its log lines and Traefik's access log (`downstream_X-Request-Id`). `LOG_LEVEL` (default `info`) can be set under `env:`.
- **Stored logs (M2.2, D61–D66):** `./annex logs <app> [-n 100] [--since 2h] [--release r4] [--level warn] [--grep text] [--request id] [--source app|gateway|all]` reads `annex_ops.logs`, which outlives containers (a failed or rolled-back release keeps its lines). Kept 14 days (`log_retention_days`) in day partitions (UTC) that annex-ops creates two days ahead and drops whole once they are over the retention; the size guard (`log_max_mb`, 2048) drops the oldest day early and alerts admins (`platform:logs`). `-f` still follows the live container through Docker. If annex-ops doesn't answer, `annex logs` shows the live container's own log and says so.
  - **What is shipped:** every app container, annex-ops, the webhook receiver, the gateway's request lines (from product-db's log, `--source gateway`; the aggregate M2.5 needs), Authelia's sign-in lines (failed attempts, unknown users, denied access, resets, warnings and errors; not the anonymous front-door check or the user-file reloads), and scheduled jobs' output (it is in Ofelia's log: the lines show as `[job:<name>]`). **Not:** the two socket proxies, Traefik, Ofelia's own lines, Metabase, Homepage, Mailpit, Dozzle, the backup container. ops's and the receiver's own health-check lines are dropped (11,000 a day each).
  - **Secrets:** fields named like `password`, `token`, `secret`, `authorization`, `cookie`, `api_key`, `credential`, `private_key` are dropped at any depth; `password=...`, `Authorization: Bearer ...`, JWTs and passwords inside URLs are redacted in text. `test-logs.sh` writes a fixture secret every way it can and greps the table for it.
  - **A flood:** more than 200 lines in one second of log time per container are cut, and one line says how many. Lines are stored with Docker's timestamp, never the app's own.
  - **No gap on a redeploy:** before Docker replaces or removes an app's container (`deploy`, a rollback, `secret set`, `remove`), Annex runs `ctl logs-drain` (5 s limit; for a deploy or rollback the deploy process on the VM does, D101). If annex-ops is down or slow the operation carries on with a warning. Lines written during the old container's own shutdown can still be missed, and a hard crash of annex-ops loses nothing (the cursor only moves after the rows are stored).
  - **Where and how big:** `ctl logs-stats` (partitions, MB, lines; also the sink's buffer and how many rows it dropped since ops started, D81). The table is in `annex_ops`, so it is in the nightly dump. Lines can hold personal data an app shouldn't have logged: they live as long as the retention says, readable by admins through the CLI.
  - **Releases:** every deploy and rollback is also a row in `annex_ops.releases` (`releases.jsonl` stays the record; `push.sh` backfills, idempotently).
- **Error groups (M2.3, D67–D68):** annex-ops reads the stored logs for errors and groups them by exception type and failing frame (or by the message with numbers, ids and paths removed). `./annex errors [app] [--state active|quiet]` lists them (state, count, first and last seen, release, user, a sample and a request id to look up). A new kind of error, one back after a quiet day (`error_quiet_s`, 24 h) or in a newer release emails the app's owner, `alerts.to` and the admins once; at most 5 error emails per app per hour (`error_alerts_per_hour`), the rest in one summary. Browser JavaScript errors arrive through the app's own `/api/_errors` (from `/annex-errors.js`) as `source=browser` lines. Settings (`state/ops/tuning.json` or `OPS_<NAME>`): `errors_scan_s`, `errors_settle_s`, `error_quiet_s`, `error_alerts_per_hour`, `error_event_days` (14), `error_group_days` (30). Tables: `error_events`, `error_groups`, `error_alerts`.
- Gateway access per app: `./annex logs <app> --source gateway` (or `ssh annex docker logs annex-product-db-1 2>&1 | grep annex-gateway`).
- Front door: `ssh annex docker logs annex-traefik-1` (JSON access log), `annex-authelia-1` (login decisions; failed sign-ins are also in the stored logs).

## Jobs
- Ofelia runs each `schedule` entry inside the app's container as uid 10001. See runs with `ssh annex docker logs annex-ofelia-1`, which shows start, stdout and duration.
- `./annex run <app> <job>` runs the same command now and prints its output and exit code.
- Ofelia reads job labels only at startup; a deploy that changes schedules restarts it (D18).

## Releases and rollback
- Each `annex deploy` builds `annex-app/<app>:r<N>`. Before switching, it dumps the app's database and archives `/data` (if under 200 MB) into `snapshots/<app>/pre-r<N>`.
- **The deploy runs on the VM (D101).** `annex deploy` validates `annex.yaml` and the views on the Mac, then makes one call: `annex_vm.py deploy <app>` gets the release line and the source on stdin and does the rest in one process on the VM (upload, build, snapshot, provision, switch, gate, cleanup), sending progress back as it goes. `annex rollback` is one call too (`annex_vm.py rollback <app> [--to N] [--with-data]`); the VM picks the target.
- **Health gate:** the new release must pass its health check within 60 s (`ANNEX_HEALTH_TIMEOUT` in the CLI's environment changes it for one deploy; the CLI passes it, `ANNEX_IMAGE_MAX_MB` and `ANNEX_BUILD_MIN_FREE_GB` to the VM). If it doesn't, the previous release is switched back in automatically, with its manifest (views, storage, schedule), and the deploy fails with the new release's log lines.
- `annex rollback` does the same switch by hand and records it as a new release. `--with-data` also restores the snapshot from the target release's time. A snapshot of the current data is taken first, so a rollback can itself be undone with `annex rollback --to rN --with-data`.
- Kept per app: the images of the last 3 live releases and the last 3 snapshots. `annex remove` deletes both; with `--keep-data`, the release history and snapshots stay.
- **One deploy at a time (D92, D101).** The deploy process on the VM holds an flock on `deploy/<app>/.lock.guard` from before the source upload to its end, so the lock lives exactly as long as the process. `deploy/<app>/current.json` says who holds it, the release, the step and the pid. A second deploy or rollback of the same app is refused with that ("<app> is being deployed or rolled back by kim@mac (r5, at step build, started …, 40 s ago; pid 12345 on the VM)"); deploys of different apps don't wait for each other. While it runs, the release is `pending` in `releases.jsonl` (`annex releases` shows it); the end rewrites the line as `live` or `failed` (a build failure, a provision error or a `kill <pid>` on the VM is a `failed` release with `broke off at <step>: <reason>`) and copies it to `annex_ops.releases`, which never holds a pending line.
- **Ctrl-C and a dropped session detach; they don't cancel.** After the source is uploaded the deploy runs in its own session on the VM and finishes whatever happens to the terminal, the Mac or the SSH connection. The CLI then says "The connection to the VM dropped at the gate step; the deploy continues on the VM" and exits. **Watch it:** `./annex status <app>` (the `deploy` line: running, at which step, pid), `ssh annex tail -f /srv/annex/deploy/<app>/run.log` (one JSON line per step, the last one the result), or `ssh annex python3 /srv/annex/platform/vm/annex_vm.py deploy-state <app>`; the outcome is in `./annex releases <app>`. A Ctrl-C before the upload finished ends the deploy there (a `failed` release, nothing switched). **To stop a deploy** that runs: let it finish and `annex rollback`, or `ssh annex kill <pid>` (SIGTERM: it records its release as failed at the step it reached; a release it had already switched to keeps running, as with a failed gate it was too late to undo, so roll back if needed).
- **A deploy process that died** (SIGKILL, the VM rebooted) leaves the pending line and a free lock (the lock died with it). The next deploy or rollback **reconciles** at once: it says "r5 of <app> was interrupted at gate …" (the step from `current.json`) and looks at the app's container. Running r5's image and healthy (for a web app: the manifest's health check answers 200 through Traefik, waiting up to 60 s while Docker still says `starting`): r5 is recorded `live` and its `deploy.json` written (Ofelia restarted if a schedule changed). Anything else: `failed`; nothing is switched or removed. If no healthy container runs, the message says so and to put the live release back with `annex rollback <app> --to <live release>` (allowed only while the container doesn't run that release's image). After a reboot, `restart: unless-stopped` brings back whatever Compose last started.
- **Reconcile without deploying:** `ssh annex python3 /srv/annex/platform/vm/annex_vm.py deploy-reconcile <app>` (JSON). It refuses while a deploy process holds the lock, naming its pid: that deploy is alive; wait for it, or `kill <pid>` and run it again. There is no lock to break by hand any more (`--break` and `ANNEX_DEPLOY_LOCK_STALE` are gone). A `deploy/<app>/.lock/` directory left by a CLI from before D101 is removed by the next deploy, with a note.
- **No `scripts/push.sh` during a deploy.** The deploy process has its Python code loaded, but it runs `annex_vm.py` functions and Docker against the bundle in `platform/`; a push that replaces the bundle or restarts the platform (Traefik, ops, appdata-db) under a running deploy can fail its gate or its provisioning. Check `annex list` / `deploy-state` first. An old CLI (before D101) is refused at its first call with "this Annex runs deploys on the server now: update your checkout".
- **Build limits (D95).** A build is refused with under 3 GB free on `/srv/annex` (`docker system df` on the VM shows what takes the space; `docker image prune -a` and `docker builder prune` free it), and an image above 2048 MB is removed and refused. Both limits are platform settings: `ANNEX_BUILD_MIN_FREE_GB` and `ANNEX_IMAGE_MAX_MB` in `.env` (then `scripts/push.sh`); the CLI's environment overrides them. App containers have `pids_limit: 256`. A failed image/snapshot cleanup after a deploy shows up in the deploy's warnings.
- **Timeouts.** A deploy or rollback has no overall time limit: the VM sends a heartbeat every 30 s, and the CLI gives up only after 180 s without any line (a dead connection), with the detach message above; the deploy carries on. Other VM commands keep a 15-minute timeout.

## Email and Slack (annex-ops)
- Apps call `ANNEX_OPS_URL` (`http://ops:8000`, on the app's own network, D88; no public route) with their `ANNEX_OPS_TOKEN`. What a token may do comes from `notify:` in the app's `annex.yaml`; it's stored hashed in `annex_ops.app_grants` (database `annex_ops` in appdata-db, in the nightly backup).
- **Prototype mail goes to Mailpit** (`mail.` host, admins only): nothing leaves the VM. Mailpit keeps the last 500 messages in `state/mailpit`. To send to real addresses, a real SMTP relay replaces Mailpit (set `OPS_SMTP_HOST`/`OPS_SMTP_PORT` for ops in `compose.yaml`) and the client approves the recipient domains and addresses.
- **Who can receive:** logins from `state/directory/users.json` and addresses in `ANNEX_EMAIL_DOMAINS` (default `annex.example`) or `ANNEX_EMAIL_ALLOW` (exact extra addresses). Both are in `.env`; change them and run `scripts/push.sh`. A new demo user is picked up without a restart once `scripts/bootstrap.sh` has rewritten `users.json`.
- **Limits:** 60 emails and 60 Slack posts per hour per app (`OPS_EMAIL_PER_HOUR`, `OPS_SLACK_PER_HOUR` in ops's environment). Request bodies over 256 KB are refused.
- **The send log:** `./annex sends [app]`, or `ssh annex docker exec annex-ops-1 python -m annex_ops.ctl sends|grants|info`. It holds app, recipients, subject, time, status (`sent`, `rejected`, `failed`, `unavailable`) and the error, never a body.
- **Connect Slack:** `docs/setup.md` §7. Until then a post to an allowed channel returns 503 "isn't connected" and is logged as `unavailable`. Replacing the token is the same steps.
- **Ops logs:** `ssh annex docker logs annex-ops-1` (request lines only: no tokens, no bodies).

## Status page and alerts (M1.3)
- **Health checks (M2.6, D73):** annex-ops checks every web app itself, every `check_interval_s` (60 s): a GET of `http://annex-app-<app>:<port><healthcheck>` over the app's own network (D88) (the path and port come from the container's labels, so `annex deploy` writes nothing for it; job-only apps have no web check, their jobs are watched instead), and the **front door**: an anonymous request to `ANNEX_FRONTDOOR_URL` with `Accept: text/html` must answer **302** to the login (without an Accept header Authelia answers 401, D41; TLS isn't verified in local mode). An app is up on a 200. After 2 failures in a row (`check_fail_threshold`) it is confirmed down and the alert engine hears `HealthState` (signal `down` on `app:<name>` or `platform:front-door`); after 2 successes (`check_ok_threshold`) it is up again. Every result is a row in `annex_ops.health_checks` (kept 7 days; `ctl health` shows the newest per check). `annex status`, the console (`/status`, the app pages, the fleet) and the discovery page's Status tile read those rows; a result older than three intervals (at least 3 minutes) counts as "unknown: the health checker isn't answering". After an ops restart the last stored results stand in for the first rounds, so an incident left open by a check that has passed since is cleared at once.
- **annex-ops's threads (B1, D81):** `/healthz` lists every background thread with its state (ok, stale, dead) and answers 503 if one isn't ok; the Platform page shows the table, `ctl health` adds `thread:<name>` rows, and the health checker raises `platform:ops` when `http://ops:8000/healthz` fails twice. A dead log follower is restarted by the shipper within 5 s.
- **The status page** is the console's `/status` (everyone signed in): every app and the platform, up or down. The Homepage's **Status** tile shows how many checks are up and down (a `customapi` widget on ops's `/tiles/_status`) and opens it. There is no separate status host any more (`status.<domain>` is gone).
- **What raises an alert** (signals, in annex-ops): health check failing (2 checks in a row), container stopped for over 60 s, crash loop (3 non-zero exits in 10 min), container health check unhealthy, out of memory, error spike (at least 10 5xx and at least 5 % of an app's requests in 5 min), and a scheduled job failing (read from Ofelia's log: `annex run` is not an alert source, its caller sees the exit code).
- **One alert per problem:** signals attach to an *incident* per subject (`app:<name>`, `job:<app>/<job>`, `platform:<service>`). The first signal sends the alert, the rest are added silently, and "resolved" goes out when all have cleared (a stopped app that both Docker and the health checker notice is still one alert). A reminder follows after 1 h open, then every 24 h. Deploys, rollbacks, `secret set` and restarts that finish within 60 s alert nobody. Removing an app, or turning the extras off, closes its incidents without a message. Metabase and Dozzle being stopped is never alerted; being unhealthy while running is. A front door that fails while Traefik or Authelia is stopped or already in trouble joins that part's incident (`platform: traefik ...`), so a Traefik outage is one alert, not two (D90).
- **Sending (D90):** the engine never sends: each message is a row in `annex_ops.outbox`, sent by the `alert-sender` thread (one email to everyone, one post per Slack channel). A send that fails because the mail server or Slack can't be reached, or a rate limit, is tried again after 10 s and 60 s (`send_backoff_s`), then given up after 3 attempts (`send_attempts`); a refused address is final (the others still get theirs). Each part is marked sent the moment it goes out, so a retry or an ops restart never repeats it. Messages that weren't delivered in the last 7 days are listed on the console's Platform page; every attempt is in the send log.
- **Who gets what:** app problems go to the app's owner (the `com.kaldi.annex.owner` label, turned into an email by the user directory), anyone in `alerts.to`, and every user in group `admins`. Platform problems go to admins only. With Slack connected, everything is also posted to `#annex-alerts`. An owner who isn't in the directory means the alert goes to admins with a note.
- **Maintenance:** `restore.sh` and `rollback --with-data` hold the app's alerts for up to 15 minutes while its container is stopped on purpose. For other planned work use `ctl maintenance` (see the table above): signals are collected and nothing is sent until it ends; any that are still active then open the incident.
- **Tuning:** thresholds are defaults in `ops/annex_ops/engine.py` (`Tuning`), overridable by `OPS_<NAME>` environment variables on ops and, at runtime, by `/srv/annex/state/ops/tuning.json` (`stopped_grace_s`, `crash_count`, `crash_window_s`, `crash_stable_s`, `error_window_s`, `error_min`, `error_ratio`, `reminder_first_s`, `reminder_repeat_s`, `tick_s`, `check_interval_s`, `check_timeout_s`, `check_fail_threshold`, `check_ok_threshold`, `send_backoff_s`, `send_attempts`). Production never has the file; `scripts/test-alerts.sh` writes a short one and removes it. If an alert storm ever needs silencing, put a long `reminder_first_s` there, or open maintenance for the subject.
- **State:** the `annex_ops` tables `incidents` (with the full history of signals), `job_runs` (90 days), `log_cursors` (where ops stopped reading Traefik's, Ofelia's and every shipped container's log) and `maintenance`, `outbox` (alert messages, 30 days) and `engine_state` (per container: when it stopped, its last exit and recent crashes; when memory went low; written when they change). ops restores open incidents and those timers at start and re-reads Docker's state, so a push (which recreates ops) doesn't lose or repeat alerts, and doesn't restart a crash count or a grace period. The engine measures durations on a monotonic clock, so a wall-clock step (NTP) can't freeze a reminder.
- **The VM itself** (D56): its disk (alert at 85 % used, cleared below 80 %), its memory (alert when under 256 MB stays available for 5 minutes, cleared above 400 MB) and the age of the newest backup (alert when over 26 hours; it's the archive folder's time, so a manual `scripts/backup.sh` counts) are sampled every minute and alerted to admins like any platform problem, with what to check in the message. `backup-stale` (D87) is a second signal on the same incident: the newest archive is more than a day newer than the `MARKER` of the dumps inside it, i.e. `dump-all.sh` is failing and the archives only look fresh. `ctl host` shows the current numbers (and `dump_age_h`). Settings `disk_alert_pct`, `disk_clear_pct`, `mem_alert_mb`, `mem_alert_s`, `mem_clear_mb`, `backup_max_age_s`, `backup_stale_s`, `host_sample_s` in `Tuning`.
- **Limits:** if the VM itself dies, nothing on it can say so: that needs a check from outside the LAN (production item). The checker's own front-door request makes Authelia log an anonymous "not authorized" line every interval (the log shipper drops it).

## Usage stats and the weekly digest (M1.4)
- **What is counted:** a signed-in page request on an app's router, taken from Traefik's access log, which annex-ops already follows (one follower feeds both the alert engine and usage). Not counted: the app's health path (`com.kaldi.annex.healthcheck` label), static assets (`.js .mjs .css .map .png .jpg .jpeg .gif .svg .ico .webp .woff .woff2 .ttf`), anonymous requests (the login redirects) and platform routers. Apps change nothing.
- **Where it shows:** the app's discovery tile ("Users 7d" with a trend, and its status; job-only apps show "Last run"), `annex usage`, `annex status`, the console (an app's **Usage** tab, the overview's people and sparklines) and the Monday digest. The "Annex usage" Metabase dashboard and the Usage tile were retired in M2.9 (D76).
- **Storage:** raw rows in `annex_ops.requests` for 30 days (`usage_retention_days`), never with a query string, deleted by the rollup. Daily and weekly summaries without logins (`usage_daily`, `usage_weekly`) are kept indefinitely; days and ISO weeks (Monday start) are in Europe/Ljubljana. The rollup runs every 10 minutes (`ctl rollup` runs it now). Removed apps disappear from `annex usage`, the tiles and the dashboard's table; their history stays in the summaries (`annex usage <app>` still shows it).
- **Logins** are in `requests` and nowhere else. They are shown only by `annex usage <app> --by-user` (personal data: admins; in the prototype, CLI access is SSH access). The console's role reads `requests` only for the admins' per-person view and for distinct-people counts (never shown with a login to owners). The tile endpoint (`GET /tiles/<app>` on ops, called by Homepage from its own server) has no token and returns totals and status only; every app can read it too (ops is on every app's network).
- **Signals** (rules in `ops/annex_ops/usage.py`, written by the rollup to `app_signals`): *graduation candidate* = the last 4 complete weeks never fell, the latest had at least 5 users and more than the first; *dormant* = no signed-in request for 30 days and Annex first saw the app at least 30 days ago.
- **The digest:** Mondays at 08:00 (Europe/Ljubljana) by email: admins get every app, each owner their own apps. It covers the last complete week, with the 4-week trend, error rate, p95 and the last 7 days, and lists graduation candidates and dormant apps. It is sent once per week (`annex_ops.digests`), also if ops restarts that day; a fresh install on another weekday does not send one at once. Preview it without sending: `ssh annex docker exec annex-ops-1 python -m annex_ops.ctl digest [--to <login>] [--dormant-days N --min-age-days N]`; add `--send` to send it now.
- **Settings** (defaults in `ops/annex_ops/usage.py`, `UsageSettings`; override with `OPS_<NAME>` environment variables on ops or in `state/ops/tuning.json`): `usage_retention_days` 30, `graduation_min_users` 5, `graduation_weeks` 4 (2 to 4), `dormant_days` 30, `rollup_s` 600, `digest_weekday` 0, `digest_hour` 8.
- **Retired dashboard:** `vm/metabase-retire-usage.sh` removes what an earlier setup created in Metabase (docs/setup.md, step 8).
- **Demo history (optional):** `scripts/seed-usage.sh` writes 8 weeks of synthetic history (marked `synthetic`, weeks 3 to 10 back) so the console's Usage tab has charts; `--clear` removes it. See the note in the script about graduation.

## Incoming webhooks (M1.5)
- **The hooks host:** `hooks.<domain>` (`ANNEX_HOST_HOOKS`) is the **only route without a login**. A webhook is `https://hooks.<domain>[:port]/h/<app>/<hook>`, declared in the app's `annex.yaml` (`webhooks:`); `annex deploy` and `annex status` print each URL. Traefik routes only `/h/` there (rate limit 20/s per source, burst 40; 1 MB body cap) to the **receiver**, its own container (`annex-hooks-1`, D55): the ops image with only the hooks files and a database role that may only insert events, so the internet-facing process holds no SMTP access, Slack token, user directory or Docker access. It refuses everything outside `/h/`. Answers on that host are terse (`{"error": "signature check failed"}`); the reasons are in `annex hooks` and the receiver's log (`docker logs annex-hooks-1`).
- **What happens to a call:** the receiver checks the provider's signature on the raw body (`trello`, `stripe`, `github`, `slack` or `shared-secret`; the secret is an app secret), stores the event and answers the provider at once; a worker in annex-ops forwards it to the app's endpoint with `X-Annex-Hook-Token`, `-Event`, `-Attempt` and `-Hook` headers. Bad signatures are rejected, logged (reason, no body) and never forwarded; at most 60 verified events per minute per hook.
- **Retries:** after 10 s, 30 s, 1 min, 5 min, 15 min, then hourly, until the event is 7 days old (then `failed`). Within one hook, events are delivered oldest first: a failing event holds back newer ones of that hook. Delivery is at least once, so apps dedupe by `X-Annex-Hook-Event`. If a hook's oldest event has been failing for 15 minutes, the app's incident gets a `webhook` signal (same alert and "resolved" as any other problem).
- **Retention and privacy:** event bodies are kept 7 days (needed for retries and replay), so they are in the nightly database dump for that long; then they are deleted. Bodies are shown only by `annex hooks show <id>` (human only); rejected requests have no body.
- **Replay:** `annex hooks replay <app> --id N` (or `--failed`, `--since 1h`) queues copies; the app sees the same `X-Annex-Hook-Event` and attempt 1 (it asks you to confirm: the app will process the events again).
- **Rotating a signing secret:** `annex secret set <app> TRELLO_SECRET=<new>`. It regenerates the hooks file the receiver and ops read (picked up on the next request) and restarts the app; then update the secret at the provider. Events signed with the old secret are rejected in between.
- **Settings:** retry steps (`hook_backoff_s`), the age after which events fail (`hook_max_age_s`) and the alert delay (`hook_alert_after_s`) are in `Tuning` (`ops/annex_ops/engine.py`) and overridable in `state/ops/tuning.json`.
- **Production:** this is the only internet-facing route. It will want a WAF or the providers' published IP ranges in front of it, and its own monitoring and alerting.

## Accounts: Annex's own users (D57)
Annex doesn't need a company SSO: it has its own accounts (Authelia's file backend), managed by an admin from the Mac. Company SSO can be put in front later without changing apps (they only see the `Remote-*` headers).
- **Add someone:** `./annex users add ana --name 'Ana Kovač' --email ana@client.com --groups users`. They get an invitation email (Authelia's "reset your password" message; Mailpit in the prototype) with a link to set their own password, valid 24 hours. No password passes through the CLI. `--print-password` prints a random one once instead, for someone without an inbox.
- **Groups:** `users` (use tools), `builders` (deploy tools; the convention, not enforced yet), `admins` (everything, incl. Mailpit, Dozzle, the gateway's page, admin alerts and digests). `./annex users set ana --groups users,builders` replaces them; a changed group applies at the person's next sign-in.
- **Disable, enable, remove:** `--disable` stops sign-in at once and takes them out of the user directory (no alerts or emails), reversibly; `remove` deletes the account. Apps they own keep running: give them a new `owner` and deploy again. The last active admin can't be removed, disabled or demoted.
- **Passwords:** anyone can reset a forgotten password from the sign-in page ("Reset password", by email) or change it in Authelia's settings (`auth.` host → settings; a one-time code by email confirms it). Minimum 12 characters. An admin can send a reset link (`./annex users reset ana`) or set a random password (`--print-password`). Authelia allows 30 reset or invitation emails per 10 minutes from one address.
- **Where it lives:** `secrets/authelia/users.yml` (password hashes; the source of truth) and `state/directory/users.json` (login, name, email, groups of active accounts; what annex-ops reads for alerts, digests and logins as email recipients). `annex users` keeps both in step, and `push.sh` re-syncs the directory, so a password change by the user never needs anything from you.
- **Metabase** keeps its own accounts (D9): add one there too if the person needs Metabase.
- **The three demo users** (`sam`, `cm`, `kaldi-admin`) have their passwords in `secrets/users.txt` for `scripts/show-users.sh` and the test suites. `annex users reset <demo-user> --print-password` updates that file; if a demo user changes or resets their own password by email, the file no longer matches.

## The demo client's database: Goat Arcade (D77, D78)
A stand-in for a client's own production database: compose project `democlient` (`democlient/`, on the VM in `/srv/annex/democlient`). It isn't part of the platform, so `push.sh` doesn't start it, and backups, alerts, the console and log shipping ignore it. product-db reads it through postgres_fdw, and apps see it only as the Goat Arcade views on the gateway. Handoff docs: `docs/goat-arcade/`.
- **Start and link** (once, after `push.sh`): `scripts/democlient.sh up`, then `scripts/democlient.sh link`.
- **Before a demo or a handoff:** `scripts/democlient.sh reseed` (asks first). The data then ends yesterday. `scripts/democlient.sh check` should print seven `t` rows (the planted stories), and `status` prints the counts, the anchor date and the link.
- **A view changed:** edit `db/product/clientlink/api_views_arcade.sql`, then `scripts/push.sh` (it re-applies the views once linked) and `scripts/democlient.sh dictionary` (regenerates `docs/goat-arcade/data-dictionary.md`). `CREATE OR REPLACE VIEW` keeps apps' grants. A view whose columns change shape must be dropped, and every app reading it must be deployed again to get its grant back.
- **A client table changed:** drop its foreign table (`DROP FOREIGN TABLE src_arcade.<t>`) and run `link` again. Never drop `src_arcade`: that drops the views and every app's grants on them.
- **Stop:** `scripts/democlient.sh down` keeps the data. While it's down, the Goat Arcade views fail with a connection error, and everything else works.
- **Where:** `/srv/annex/democlient` (compose and SQL), `state/democlient-db` (its data), `secrets/democlient.env` (its admin password, and `annex_reader`'s password, which product-db's user mapping also holds).
