## D1. Apps run through `ssh annex` and the VM's Compose (14 Oct)
**What.** The CLI copies the app folder to `/srv/annex/deploy/<app>`, writes the generated compose file there and runs `docker compose` on the VM over SSH, the same way the platform runs. The brief said "built and run through the annex-vm Docker context, using the Mac's Compose".
**Why.** Compose reads `env_file` on the client. With the Mac's Compose, per-app secrets (DB password, gateway JWT, `annex secret set` values) would have to pass through the Mac. Nejc said it's fine for secrets to touch the Mac in this throwaway demo, and asked for the least complex option. One transport (SSH) for both platform and apps is simpler: no path translation, no Compose version skew, and env files stay on the VM.
**Alternatives.** (a) Mac Compose via the context, with secret values fetched over SSH and passed inline. Two transports, and values in the generated compose. (b) Build via the context, `up` via SSH. Two transports for no gain.
**Consequence.** The `annex-vm` context is optional (handy for inspection), not required.

## D2. Split the edge network: `annex-edge` + `annex-platform` (14 Oct, approved by Nejc)
**What.** `annex-edge`: Traefik, apps and gateway. `annex-platform` (internal): Traefik, Authelia, Homepage, Metabase, Dozzle.
**Why.** Dozzle trusts `Remote-User` from whoever calls it. On a shared edge network an app could call Dozzle directly with a spoofed header and read every log. Now apps reach platform UIs only through Traefik and forward-auth.
**Alternatives.** One edge network as in the brief. Per-app networks (open for later).

## D4. Two socket proxies (14 Oct)
`socket-ro` (containers, networks, info, events; no POST) for Traefik, Homepage and Dozzle. `socket-exec` (adds POST and exec) for Ofelia and the backup hooks. Each sits on its own internal network. **Caveat:** POST plus containers lets a caller create containers, so `socket-exec` is root-equivalent. That's acceptable for the prototype; production needs a narrower path.

## D5. Forward-auth on the entrypoint, plus header stripping (14 Oct)
Every router on the HTTPS entrypoint (HTTP in upstream mode) gets `strip-identity` and then `authelia` by default, so an app can't be exposed without login by mistake. `strip-identity` blanks any client-sent `Remote-*` header. Traefik's forward-auth then sets them from Authelia's answer. Authelia's own host is a `bypass` rule. `logs` and `gateway` are admins-only, with an explicit deny for everyone else. Without that deny, non-admins fell through to the catch-all rule; the test found this.

## D6. `ANNEX_PUBLIC_PORT` (14 Oct)
Port 443 on the Mac is already used by another process, so the browser tunnel listens on 8443. The optional `ANNEX_PUBLIC_PORT` is appended to every public URL (Authelia redirect, Homepage links, `ANNEX_BASE_URL`), so login redirects keep the port. Leave it empty once a route serves Annex on 443.

## D7. Config changes force a recreate (14 Oct)
Compose doesn't notice changed bind-mounted files. `render.py` hashes each service's config directory into `ANNEX_CONFIG_HASH_<SERVICE>`, which is passed as an env var, so a change recreates exactly that container. Config is mounted as directories, not single files, because rsync replaces files and a single-file bind mount would keep the old inode.

## D8. Authelia memory 256 MiB (14 Oct)
At 128 MiB Authelia was OOM-killed during three logins in a row: argon2id verification uses about 64 MiB per login. 256 MiB is enough for the demo.

## D9. Metabase keeps its own login (14 Oct)
Metabase OSS can't take identity from headers; that needs Pro (JWT/SAML SSO). It sits behind Authelia like everything else, and has its own accounts: `kaldi-admin` is the Metabase admin, while `sam` and `cm` are normal users. Each has the same password as in Authelia (set by `vm/metabase-setup.sh`). Metabase's product connection uses `metabase_ro`, which can only read `annex_api` and is limited to that schema in Metabase's sync settings. Sample content is disabled.

## D10. Gateway details (14 Oct)
PostgREST has no anonymous role, so every call needs an app JWT. Its public hostname is admins-only and mainly shows that it's locked. Each request is logged with the app's role through `db-pre-request = annex_gateway.log_request` (a `RAISE LOG` visible in product-db's logs), next to PostgREST's own access log. `push.sh` re-applies `api_views.sql` (idempotent) on every push and tells PostgREST to reload its schema.

## D11. Backup container is not on the `appdata` network (14 Oct)
The brief lists backup on `appdata`. It doesn't need to be: database dumps run *inside* appdata-db as an offen `archive-pre` exec hook (`db/appdata/hooks/dump-all.sh`) through `socket-exec`. The backup container only reads `/srv/annex/apps` and `/srv/annex/dumps`.

## D16. App runtime hardening (14 Oct)
Every app container runs as **uid 10001** (`user:` in the generated compose), with a read-only root filesystem, `/tmp` as a 64 MB tmpfs, `cap_drop: ALL`, `no-new-privileges`, 256 MiB and 0.5 CPU. The Dockerfile must still declare a non-root `USER`; the deploy inspects the built image and refuses root. A fixed uid means `/srv/annex/apps/<app>/data` can be chowned once, without knowing the image's user. The contract documents this. There's no per-app override in v0.

## D17. How the CLI deploys (14 Oct)
`annex deploy` runs these steps:
1. Validates `annex.yaml` and checks the requested views against the live allowlist.
2. Tars the folder in Python, skipping `.git`, `node_modules`, `.venv` and similar, and unpacks it into `/srv/annex/deploy/<app>/src`.
3. Runs `vm/annex_vm.py provision` on the VM. This creates the DB role and database, the product-db role with grants on exactly the requested views, the JWT, and the data directory, then writes `secrets/apps/<app>/runtime.env`.
4. Writes `compose.yaml` and builds on the VM. The image is tagged `annex-app/<app>:<timestamp>`; older tags are removed after a successful deploy, and the build cache is capped at 1.5 GB.
5. Starts the container. For web apps it then waits for the healthcheck (probed from the Traefik container), for the route (a login redirect through Traefik on the VM) and for Docker health.

Each app's compose service is named after the app and the container is `annex-app-<app>`, so names are unique on the shared networks. `ANNEX_GATEWAY_URL` is `http://gateway:3000`. Apps join `annex-edge`, and `annex-appdata` only when `storage.postgres` is set. Secret values are written single-quoted, so Compose never interpolates `$`. Values with `'` or newlines are refused in v0.

## D18. Ofelia restarts on schedule changes (14 Oct)
Ofelia 0.3.22 reads job labels only at startup; a probe showed it ignores containers started later. The CLI restarts `annex-ofelia-1` after a deploy or remove that touches an app with schedules. Jobs are `job-exec` labels on the app container (`no-overlap`). `annex run` uses `docker exec` with the same command, so manual and scheduled runs behave the same. Job-only apps idle with `sleep infinity`. 5-field cron gets a leading `0` seconds field for Ofelia.

## D19. Missing secrets fail the deploy (14 Oct)
If `annex.yaml` declares a secret that hasn't been set, the deploy stops and names the exact `annex secret set` command. That command is human-only, not exposed over MCP. `annex secret set` on a deployed app regenerates its env file and recreates the container.

## D20. Authelia `GOMEMLIMIT=160MiB` (14 Oct)
After many logins Authelia sat at 222 of 256 MiB, because Go keeps argon2 buffers. A soft Go memory limit makes it collect and return memory earlier; it settles around 157 MiB.

## D21. Jobs run as the app user (14 Oct)
Ofelia's `job-exec` defaults to **root**. A root job in a container with `cap_drop: ALL` couldn't write to `/data`, which is owned by 10001, and would leave root-owned files otherwise. The CLI sets `ofelia.job-exec.<job>.user=10001`. Ofelia logs each scheduled run, with its stdout and duration.

## D23. Backups and restore (14 Oct)
- **Nightly backup:** offen runs at 02:00 Europe/Ljubljana. Before archiving, its `archive-pre` hook runs `dump-all.sh` inside appdata-db: `pg_dump -Fc` of every database (apps and Metabase) plus globals. The archive `annex-<timestamp>.tar.gz` holds `/backup/apps/<app>/data/…` and `/backup/dumps/current/*.dump`. Retention is 7 days (`BACKUP_RETENTION_DAYS`), and offen logs each prune. `scripts/backup.sh` runs the same thing now.
- **Restore:** `scripts/restore.sh <app> [archive]` calls `annex_vm.py restore`. It extracts only that app's dump and files, stops the container, drops and recreates the app database, runs `pg_restore`, replaces `/srv/annex/apps/<app>/data` (chowned to 10001), then starts the container again. The app must be deployed, because restore brings back data, not code or config.
- **Proof:** `scripts/restore-test.sh` passes 12/12 on `monthly-report`.
- **Not covered:** product-db (seed data, re-created from `db/product`) and platform state (Authelia's sqlite, regenerable). Backups stay on the VM's own disk, so they don't survive losing the VM. Production goes to S3.

## D24. MCP server on the 2.x SDK (14 Oct)
`mcp==2.3.0`, where FastMCP is now `MCPServer`. The server (`mcp/`) is a thin layer over `annex_cli.ops`, so CLI and MCP behave identically. Blocking calls run in a worker thread. Known failures are raised as `ToolError`; the SDK hides the message of any other exception ("Error executing tool"), and agents need the message to fix things. `annex_deploy` returns the deploy steps with the result. `remove` and `secret set` aren't exposed. Registration is user-scoped (setup.md §4), so it works from an empty folder.

## D25. `static` template has a tiny server with two endpoints (14 Oct)
A purely static site can't read identity headers or call the gateway, and the token must not reach the browser. The template's `server.py` (stdlib, `python:3.13.16-slim-trixie`) serves `public/` plus two endpoints: `api/me` (identity) and `api/data/<view>` (gateway proxy with the app's token; filters pass through, and the gateway still enforces the app's views). So a dashboard is plain HTML/JS with same-origin `fetch`. There's no build step on the server: build locally and commit the output to `public/`.

## D30. Releases and the health gate (M1.1, 15 Oct)
- **Releases.** Every deploy is release `r<N>`, image `annex-app/<app>:r<N>`. The M1 plan wrote `annex/<app>:r<N>`; keeping the M0 repository name means `remove`, `wipe-vm.sh` and the image cleanup needed no change. Each release is one line in `/srv/annex/apps/<app>/releases.jsonl`: image, the validated manifest, who (`$ANNEX_USER` or user@host), via (cli/mcp), source folder, git commit (if the folder is tracked), data snapshot and result (`live` or `failed`). The file sits next to `data/`, so the nightly backup includes it and `remove --keep-data` keeps it.
- **Build before the switch.** The image is built with `docker build` before anything changes, and the generated compose file only references it (`pull_policy: never`). In M0, `docker compose build` used the compose file, which was already rewritten for the new version. Now a build failure leaves the running version and its compose file untouched.
- **Health gate:** 60 s (`ANNEX_HEALTH_TIMEOUT`) for the healthcheck to return 200, polled through Traefik's container as before. It fails early if the container stops. Job-only apps must still be running after 3 s. On failure, the previous live release is re-activated **from its stored manifest** (provision with its views, storage and secrets, then compose generated by the current CLI). The failed image is deleted and the deploy error names the reason and includes the last 40 log lines. Data isn't touched; that's what `--with-data` is for.
- **Rollback is a new release** that points at the older image, so the history stays linear and a rollback can be undone (`--to rN` also rolls forward). The default target is the last live release before the current one. A rollback that fails the gate switches back to where it started (and restores the data it replaced, with `--with-data`).
- **Alternatives.** Re-using each release's stored compose file instead of regenerating it from the manifest: simpler, but rolling back would also drop platform labels added later (e.g. M1.3's). Marking an old release as live again instead of appending one: loses the audit trail.

## D31. Data snapshots before each switch (M1.1, 15 Oct)
Before release N goes live (deploy or rollback), `annex_vm.py snapshot` writes `/srv/annex/snapshots/<app>/pre-r<N>/`: `pg_dump -Fc` of the app's database if it has one, and a tar of `/data` if it's under 200 MB (larger: skipped and noted; the nightly backup covers it). `meta.json` records which release was live (`from_release`). `rollback --with-data` to rK restores the newest snapshot taken while rK was live, with the same restore code as `restore.sh`. Snapshots are outside `apps/`, so they aren't in the nightly backup: they're short-term undo, not backups. The last 3 per app are kept; pruning runs after a deploy or rollback finishes, so the snapshot a rollback needs is never pruned first. `--with-data` is CLI-only and asks for confirmation; the MCP's `annex_rollback` never touches data.

## D33. Bring your own stack, and `resources.memory` (15 Oct, approved by Nejc)
- **Templates are the fast path, not a requirement.** The deploy already accepted any `Dockerfile` (it only refuses images that run as root), but the contract read as if only the four templates existed. The contract now has a "Bring your own stack" section: a checklist (`$PORT`, a health check that works without a login, non-root `USER`, read-only filesystem with `HOME=/tmp`, everything built in the image, identity and the gateway token on the server, Postgres and `/data` only, one container, 50 MB upload) and notes for common stacks (Vite/React SPA via the `static` server, Next.js, Streamlit, Django/Flask, compiled languages). The skill points agents at it when the user wants another framework or brings existing code.
- **`resources.memory`** (contract change, optional): 128m–512m, default 256m. Next.js, JVMs and heavier Python data apps don't fit in 256 MB, which in practice ruled them out. The cap of 512m keeps one app from taking a large share of the VM's 3.8 GiB; anything bigger is a graduation candidate. A raised limit is not an approval step: the deploy succeeds with a warning, the container carries `com.kaldi.annex.memory`, and `annex list` shows a memory column so the platform team sees it (the M2 console's fleet view will too). `Manifest.memory_mb` defaults to 256, so manifests stored with older releases still load for rollback.
- **Alternatives.** Approving raised limits per app (a platform-side allowlist): safer for the VM, but it adds a human step to every Next.js deploy, and the cap already bounds the risk. CPU as well as memory: not needed yet, because the CPU limit throttles rather than kills, and builds aren't limited. Allowing sizes like `1g`: keeps the format simple to only `<n>m`, which the error spells out.

## D34. annex-ops: one service built from the repo (M1.2, 15 Oct)
**What.** `ops/` is a small FastAPI service (`annex-ops:local`, built on the VM from the synced bundle, the first platform image built from source). It owns everything the platform sends outward: email and Slack for apps now, and the base for M1.3 alerts, M1.4 usage and M2 audit. Code is split into small modules (`auth`, `email`, `slack`, `sends`, `directory`, `ctl`) with the DB and network kept out of the pure functions, so 47 unit tests run on the Mac. Its data is the `annex_ops` database in appdata-db (`db/appdata/annex_ops.sql`, in the nightly backup). A `docker exec ... python -m annex_ops.ctl` admin command is what the CLI uses (`annex sends`, the Slack warning). SMTP uses `smtplib` and Slack uses `urllib`: no extra dependencies. The numbering note: the plan said D33 onwards, but D33 was taken by the "bring your own stack" commit, so this is D34.
**Why.** Apps must hold no SMTP password or bot token, so something has to hold them; one service for all outbound traffic means one place to rate-limit, log and later audit.
**Alternatives.** A library inside each app (every app would need the credentials). Putting this in the CLI/VM scripts (it has to run continuously and answer apps on the network). Separate email and Slack services (more containers for the same RAM-poor VM).

## D35. Tokens are stored hashed in `app_grants` (M1.2, 15 Oct)
**What.** `annex_vm.py provision` creates a random token per app (`secrets/apps/<app>/ops_token`, injected as `ANNEX_OPS_TOKEN`) and writes only its sha256, with the app's email flag and Slack channels, to `annex_ops.app_grants`. ops looks the hash up on every request, so changing a grant takes effect at once, with no ops restart. A deploy without `notify:` (or a rollback to a release without it) deletes the row and the token. `Manifest.notify_email` and `notify_slack` have defaults, so manifests stored by older releases load (D30).
**Why.** A database leak or an ops log never exposes a usable token, and revocation is a row delete.
**Alternatives.** A JWT carrying the scopes (like the gateway): stateless, but revoking a grant means rotating the secret for everyone, and scopes are frozen into the token. Reading grants from files mounted into ops: no DB, but a stale-mount risk (D7) and nowhere to keep the send log next to them.

## D36. Networks for ops, and no public route (M1.2, 15 Oct)
**What.** ops is on `edge` (apps reach it, and it reaches Slack: `platform` and `appdata` are internal), `platform` (Mailpit's SMTP) and `appdata` (its database). It has no Traefik labels, so there is no hostname for it. Mailpit is on `platform` only; its UI is routed by Traefik behind forward-auth.
**Why.** Apps call ops directly and authenticate with their token, not through the login front door, so a public route would only add exposure. Apps can't reach Mailpit or appdata-db's `annex_ops` database directly: ops is the only door. Any app on `edge` can reach ops, but without a valid token it only gets a 401.
**Alternatives.** Routing ops through Traefik (needed only for webhooks, M1.5, which will get its own route). A dedicated `ops` network for apps (per-app networks are still open for later).

## D37. The user directory file (M1.2, 15 Oct)
**What.** `vm/bootstrap-secrets.sh` writes `state/directory/users.json` (login → name, email, groups; no password hashes) from the same `USERS` list that produces Authelia's file, on every run. ops mounts the **directory** read-only and re-reads the file when its mtime changes. Unlike everything under `secrets/`, the directory is world-readable, because ops runs as uid 10001.
**Why.** Apps know logins (from `Remote-User`), not addresses. Mounting a directory avoids the stale single-file mount (D7). Authelia's own file holds password hashes, so ops must not read it.
**Alternatives.** Querying Authelia (no API for this in file mode). Putting emails in `annex.yaml` (apps would hard-code addresses, and the client's user list is the source of truth).

## D39. Incidents, not alerts (M1.3, 15 Oct)
**What.** The alert engine (`ops/annex_ops/engine.py`) turns *signals* into *incidents*. A signal (`down`, `stopped`, `crash-loop`, `unhealthy`, `oom`, `errors`, `job-failed`) belongs to a *subject*: `app:<name>`, `job:<app>/<job>` or `platform:<service>`. A subject has at most one open incident (a unique index enforces it). The first signal opens it and sends the alert; later ones are added without a message; "resolved" goes out once every signal has cleared; a reminder follows after 1 h, then every 24 h. This is what makes "stop an app", which both Docker and Gatus notice, produce exactly one alert.
**How it's built.** The engine is pure: it takes `(now, input)` and returns actions (`open`, `add_signal`, `clear_signal`, `resolve`, `remind`, `forget`), with no database, network or clock of its own, so every rule has a unit test (125 tests in `ops/tests`). One thread (`incidents.py`) is the only consumer of a queue fed by the Docker watcher, the log followers and the Gatus webhook, and the only writer, so there are no races. It persists incidents in `annex_ops.incidents` (with a history of every signal raised and cleared, for the M2 console) and sends the messages. On restart it reloads open incidents and a reconcile pass re-reads Docker (and Gatus's last results), so a push, which recreates ops, neither loses nor repeats an alert.
**Details that came up while building it.**
- Containers are tracked by Docker id, not name: a Compose recreate (new container, old one destroyed a moment later) must not look like a crash. A destroyed container takes its own signals with it. If a sibling container of the subject exists (a recreate), the app's owner hears "resolved"; if none is left (`annex remove`, `extras.sh off`), the incident, and the app's job incidents, close **without a message**.
- A single OOM kill is held until the container has been quiet for `crash_stable_s`, like a crash loop, instead of opening and resolving within seconds of its restart.
- A `down` or `errors` signal restored from the database after an ops restart is still evaluated, so it can't get stuck (found while writing the restart tests).
- Maintenance (below) suppresses opening and reminders. An incident that was already open still sends its "resolved", because its recipients were told about the problem.
- `_platform` alerts go through M1.2's `send_email`, so they count against the hourly limit of 60 emails. One email goes to all recipients; if one address is refused, each gets its own, so one bad address can't silence the rest.
**Alternatives.** One alert per signal with de-duplication by time: simpler, but "exactly one" then depends on timing. Giving each source (Gatus, Docker, logs) its own alerting: three channels to configure and three messages for one outage.

## D41. Spike results (M1.3, 15 Oct)
1. **Gatus reload.** A new YAML file in a mounted directory is picked up by itself after about 25–30 s (the API is unavailable for a few seconds during the reload). A *deleted* file is **not** noticed: its endpoint was still being monitored 90 s later. So the CLI restarts `annex-gatus-1` whenever an app's file changes (written with different content, or deleted by `remove` or a redeploy to a job-only manifest), and not when it's unchanged. The deploy writes the file after the health gate, because Gatus checks immediately when it restarts, and the app should be up by then.
2. **Gatus API.** `GET /health` returns `{"status":"UP"}`. `GET /api/v1/endpoints/<group>_<name>/statuses` returns `results[]` with `success`, `status`, `timestamp`, `errors` (only when failing); the key is `apps_<app>` or `platform_front-door`; an unknown key is a 404; `GET /api/v1/endpoints/statuses` lists all.
3. **Ofelia's lines** (ANSI colour codes, plus Ofelia's own timestamp): `ERROR [Job "alert-probe-check" (f4ee8fcf0adc)] Finished in "288.2ms", failed: true, skipped: false, error: error non-zero exit code: 1`; a good run is the same line at NOTICE with `failed: false ... error: none`. The error text can contain commas, so the parser takes everything after `error: `.
4. **Docker events through `socket-ro`.** `filters` with `type=container`, the Annex label and `event=die,start,stop,destroy,oom,health_status` work server-side: `die` excludes the noisy `exec_die`, and `health_status` matches `health_status: healthy`. `die` carries `exitCode` as a string; on `docker stop` the order is `kill`, `stop`, `die`; every event has the Compose project and service labels. The stream is chunked, so it has to be read through `HTTPResponse`, not the raw socket.
5. **Front door.** From a container on `annex-edge`, a request to Traefik's address with the home hostname answers 302 to the login **only if the request has an `Accept` header** (`*/*` or `text/html`); with none, which is what Gatus's Go client sends, Authelia answers 401 with the same `Location`. **This differs from the plan**, which expected 302: the Gatus endpoint sets `headers: {Accept: text/html}` and still expects 302.

## D42. Job failures come from Ofelia's log (M1.3, 15 Oct)
Docker `exec_die` events only carry the command, and `monthly-report`'s two jobs run the same command; they also can't tell a scheduled run from `annex run`, whose caller already sees the exit code. Ofelia's log names the job and says `failed: true/false`, so `follow_logs.py` follows `annex-ofelia-1` and maps the job key to `(app, job)` through the `ofelia.job-exec.<key>.schedule` labels (app and job names both contain `-`, so a key is never split). Runs are kept in `annex_ops.job_runs` for 90 days and shown by `annex status`. A job's incident resolves on the next good run of *that* job. (This deviates from the M1 plan's wording, which said exec events.) The follower is generic (a container name, a handler, a cursor in `annex_ops.log_cursors`) so M2.2 can reuse it to ship every container's logs. A first start reads the last 10 minutes; later starts resume from the cursor, which is saved the moment a line arrives (at most every 2 s), and a replayed job run isn't recorded twice.

## D43. Grace period, maintenance and thresholds (M1.3, 15 Oct)
- **60 s before "stopped".** Deploys, rollbacks, `secret set` and the Ofelia restart (D18) stop a container for a few seconds, and none may alert. Only `restore.sh` and `rollback --with-data` can take longer: annex_vm opens a maintenance window (`app:<app>`, 15 min) before stopping the container, and ends it afterwards (for `rollback --with-data` the CLI ends it once the release is running). A maintenance window on `app:x` also covers `job:x/*`. `ctl maintenance` is the manual form; ops syncs the table every tick.
- **Thresholds**, all overridable: down = 2 failed Gatus checks 60 s apart, cleared by 2 good ones; crash loop = 3 non-zero exits within 10 min, cleared after 10 min without one while running; error spike = at least 5 % 5xx **and** at least 10 in 5 min (from Traefik's access log, `RouterName` `app-<name>@docker`), cleared after 5 min below; reminders after 1 h and then every 24 h. Defaults live in `Tuning` (engine.py); `OPS_<NAME>` environment variables and `state/ops/tuning.json` (re-read when its mtime changes) override them. Production never has the file.
- **Extras:** Metabase and Dozzle being stopped is never alerted (`scripts/extras.sh off` does that on purpose); being unhealthy while running is.

## D44. Gatus: a derived image, the edge network, no external heartbeat (M1.3, 15 Oct)
- **Image.** `twinproduction/gatus:v5.37.0` has no shell or `wget` (checked on the VM: root, entrypoint `/gatus`, no healthcheck), but every platform container keeps a healthcheck (CLAUDE.md). `images/gatus/Dockerfile` copies a static `busybox:1.37.0-musl` in as `/bin/wget`. It's built on the VM like ops. The config is mounted under `/annex` with `GATUS_CONFIG_PATH`, never `/config`, where the image's sample config (7 endpoints) would be merged in.
- **Networks.** Gatus is on `annex-edge` so it can probe apps on their internal port, and on `annex-platform` for Traefik's route, Homepage's widget and its webhook to ops. Traefik has the home and auth hostnames as aliases on `edge`, so Gatus checks the front door by its real name. **Accepted:** any app (or any container on `annex-edge`) can read Gatus's API and so see which apps are up, without logging in. That is not data, and the discovery page shows it anyway.
- **Gatus's webhook** to `ops:8000/internal/gatus` carries `OPS_INTERNAL_TOKEN` (generated on the VM, never an app token); identifiers are in the URL and the errors in a plain-text body, because `[RESULT_ERRORS]` can contain quotes.
- **No external heartbeat.** If the VM dies, nothing on it can say so. That needs a check from outside the LAN, which the brief rules out; it's a production item (an external uptime monitor pointed at the status page or the front door).

## D46. Usage stats: what counts, where it's kept, who sees what (M1.4, 15 Oct)
1. **Per-person usage is acceptable, admins only** (Nejc, 15 Oct; M2 plan). Totals appear on tiles, in Metabase, in the digest and in `annex usage`. Logins appear only in `annex usage <app> --by-user`, which prints a reminder that it's personal data. In the prototype CLI access means SSH access, which means admin.
2. **What counts:** a line on an `app-<name>@docker` router with a non-empty `request_Remote-User` (Traefik's access log already keeps that header). Not counted: the app's health path (new label `com.kaldi.annex.healthcheck`, so a custom `healthcheck` is honoured), static assets (by extension), anonymous requests (login redirects) and platform routers. The query string is dropped before storing (it can hold client names) and the path capped at 200 characters; `Duration` is converted from nanoseconds to ms.
3. **Storage:** raw rows in `annex_ops.requests` for 30 days, deleted by the rollup; `usage_daily` and `usage_weekly` (no logins) kept indefinitely; days and ISO weeks (Monday start) in Europe/Ljubljana. The rollup runs every 10 minutes and never overwrites `synthetic` rows. A unique index on the row's content plus `ON CONFLICT DO NOTHING` drops the lines a restart replays from the follower's cursor (which is saved at most every 2 s); ops flushes its buffer when it shuts down, so a restart neither loses nor repeats rows (tested). A hard crash can lose up to 5 s of buffered rows.
4. **Signals:** *graduation candidate* = the last 4 complete weeks never fell, the latest had at least 5 users and more than the first; *dormant* = no signed-in request for 30 days and Annex first saw the app at least 30 days ago. Both thresholds are settings. The rules live in Python (`usage.py`, pure and unit-tested at their edges); the rollup writes the verdict to `annex_ops.app_signals` and the `usage_apps` view reads it, so there is one place for the rules. With three demo users graduation can only show with real history.
5. **The digest** goes out Mondays 08:00 local time: admins get every app, each owner their own, never a login. It covers the last complete week (a Monday-morning digest summarises the week that just ended) with the 4-week trend as numbers (`3 → 4 → 4 → 6`), error rate, worst daily p95, users in the last 7 days, and the graduation and dormant sections. It is sent once per week (`annex_ops.digests`, the week is recorded before sending), also if ops restarts that day; a fresh install on a Wednesday doesn't send one at once, because it only catches up within 24 hours of the scheduled time.
6. **Tiles call ops without a token** (`GET /tiles/<app>`, totals and status, never logins). Homepage proxies the widget call on its own server, so the browser never calls ops. **Accepted:** apps (any container on `annex-edge`) can read these totals too.
7. **Metabase reads summaries only**, through the role `metabase_usage`: `SELECT` on `usage_daily`, `usage_weekly` and the view `usage_apps`, nothing else (checked: denied on `requests`, `sends`, `incidents` and `app_grants`). The view runs with its owner's rights, which is why it can use `requests` for rolling 7- and 30-day distinct users without the role having access. Normal Metabase users (`cm`, `sam`) can open the dashboard too: it holds only totals, so that matches "owners and the client see totals".
**Alternatives.** Per-request events pushed by apps (every app changes; not "zero effort"). Counting every request incl. assets (inflates numbers 10–50×). Computing signals in SQL (harder to test). Showing logins in Metabase (it would leak to every Metabase user).

## D50. Spike results (M1.5, 15 Oct)
1. **Authelia `bypass` through forward-auth for another host:** works. With a `bypass` rule for the hooks host first in `access_control.rules`, a request with no session reaches the backend (no 302, no 401) whether or not it has an `Accept` header (D41's difference doesn't apply to bypass). Client-sent `Remote-User`, `Remote-Groups` and `Remote_User` arrive at the backend **absent** (strip-identity ran, and with no session Authelia sets nothing).
2. **Traefik labels on a container:** a router `Host(...) && PathPrefix(`/h/`)` with router-level `ratelimit` (average 20, burst 40) and `buffering.maxRequestBodyBytes=1048576` middlewares sits on top of the entrypoint middlewares. On the hooks host, `/v1/me`, `/healthz`, `/internal/gatus`, `/tiles/...` and `/` are a **404 from Traefik** (no router matches); a 900 KB body passes and a 2 MB body gets **413**. Sequential curls through the tunnel are too slow to trip the rate limit (about 10/s); 300 requests with 60 in parallel gave 51 × 200 and 249 × 429.
3. **Signature formats, checked against each provider's current documentation (15 Oct 2026):**
   - **GitHub:** `X-Hub-Signature-256: sha256=<hex HMAC-SHA256(secret, body)>`. Published vector (secret `It's a Secret to Everybody`, payload `Hello, World!`) reproduces: `757107ea…043e17`.
   - **Slack:** `X-Slack-Signature: v0=<hex HMAC-SHA256(secret, "v0:<X-Slack-Request-Timestamp>:" + body)>`, replay window 5 minutes, compared with an HMAC compare function. The docs' worked example (secret `8f742231b10e8888abcd99yyyzzz85a5`, timestamp `1531420618`, the `/webhook-collect` body) reproduces `v0=a2114d57…b503` (pinned in the unit tests). A `url_verification` request has `type`, `challenge`, `token`; the endpoint answers 200 with the challenge as plain text.
   - **Stripe:** `Stripe-Signature: t=<unix>,v1=<hex>[,v1=...][,v0=...]`; signed payload `"<t>." + body`; HMAC-SHA256 with the endpoint secret; several `v1` appear while a secret is being rolled (any may match); only `v1` counts (`v0` is a test scheme, ignored to prevent downgrade); the libraries' default tolerance is 5 minutes. No published vector: the unit test pins one computed with `openssl`.
   - **Trello:** `X-Trello-Webhook: base64(HMAC-SHA1(secret, body + callbackURL))`, the URL exactly as given when the webhook was created; Trello sends a `HEAD` to the callback URL on creation and refuses to create the webhook without a 200. No published vector: pinned from `openssl`.

## D51. The hooks route: the only one without a login (M1.5, 15 Oct)
**What.** `hooks.<domain>` (`ANNEX_HOST_HOOKS`) is routed by Traefik labels on the ops container: `Host(...) && PathPrefix(`/h/`)` to port 8000, with `hooks-ratelimit` (20/s per source, burst 40) and `hooks-limit` (1 MB body) as router middlewares. Authelia has a `bypass` rule for that host, first in the list; `strip-identity` still runs, so no request there carries trusted `Remote-*` headers. ops adds a second layer: a host guard middleware answers 404 for **any path outside `/h/` when the `Host` is the hooks host**, so a routing mistake can't expose `/v1/*`, `/internal/gatus` or `/tiles` (tested directly against ops with that Host header, including path-traversal attempts). Everything answered on that host is terse (`{"error": "signature check failed"}`, `not found`, `slow down`): the reasons go to ops's log and `annex hooks`, and never include a body, a secret or a signature.
**Why two layers.** This is the one route without a login; either layer alone fails open on a mistake.
**Production note.** This hostname will be the only internet-facing endpoint. It will need a WAF or the providers' published IP ranges in front of it, and its own monitoring and alerting (the status page and alert engine here cover the platform, not an external probe of this route). In the prototype (LAN only) no real provider can reach it: test events are signed on the Mac and sent through the SSH tunnel.
**Alternatives.** A separate small receiver service (another container for the same code path; the host guard gets the same isolation inside ops). Authelia's per-path rules instead of a host (paths on the shared app hosts would be public, and an app could shadow them).

## D52. Signing secrets, tokens and what the app must check (M1.5, 15 Oct)
**What.** A webhook names a secret declared under `secrets:`; a human sets it with `annex secret set`. `annex_vm.py provision --hooks` copies the values into `/srv/annex/secrets/hooks/<app>.json` (`{token, port, hooks: {name: {verify, secret, path}}}`), written atomically and chowned to uid 10001 with mode 600; the directory stays owned by the `annex` user (755) so the next provision can replace the file, and it is mounted read-only into ops (the directory, not the file: D7). **Secrets never go in the database, ops logs or any CLI output** (the test greps for all three random values everywhere). A per-app `ANNEX_HOOK_TOKEN` is injected into the app (and written to the hooks file); the app checks `X-Annex-Hook-Token` with the runtime helper `hook_event(headers)` (`hookEvent(req)` in node), so nobody can reach the endpoint around Annex. (`ANNEX_OPS_TOKEN` can't be reused: ops stores only its hash, D35.) `annex secret set` re-provisions, so rotating a signing secret updates what ops checks; a release without `webhooks:` (or a rollback to one) deletes the file and token, and its URL is a 404. `Manifest.webhooks` has a default and `from_dict` rebuilds `Webhook` objects, so older releases still load (D30).
**Alternatives.** Secrets in `annex_ops` (rejected: D35's reasoning, plus bodies are already there); a JWT as the app token (stateless, but it can't be rotated per app without a signing key shared with every app).

## D53. Receive, store, deliver (M1.5, 15 Oct)
- **Answer first.** After the signature checks out, the event is stored (`annex_ops.hook_events`, `pending`) and the provider gets 200 `{"ok": true, "id": N}` at once; Slack's `url_verification` is answered with its challenge and not delivered. Signature headers are not stored or forwarded (Annex has checked them); only `Content-Type`, `User-Agent`, `X-GitHub-Event`, `X-GitHub-Delivery` and `X-Slack-Retry-Num` are. The raw body is read before anything parses it. `HEAD /h/<app>/<hook>` is 200 for a declared hook (Trello's registration check).
- **Delivery** is at least once, by one worker thread every 2 s: `POST http://annex-app-<app>:<port><path>` with a 10 s timeout, redirects not followed, headers `X-Annex-Hook`, `-Event` (the original id for a replay), `-Attempt` and `-Token`. 2xx = delivered. Otherwise the next attempt follows the backoff 10 s, 30 s, 1 min, 5 min, 15 min, then hourly, until the event is 7 days old (then `failed`). Within one hook, events go oldest first and a failing event holds back newer ones (tested with pure functions). One thread means one slow app can delay others by its 10 s timeout; fine at this volume.
- **Storage:** bodies are kept 7 days (retries and replay), so they are in the nightly dump for that long; events older than 7 days are deleted daily. Rejected requests are logged with the reason and **no body**. Pending events of an app that no longer declares the hook (or was removed) become `failed` with that reason.
- **Replay** (`annex hooks replay`, human only, asks first): copies of the stored events as new `pending` ones with `replay_of` set; the app sees the same `X-Annex-Hook-Event` and attempt 1.
- **Human-only CLI:** `annex hooks <app>` (metadata only), `annex hooks show <id>` (headers and the body, truncated to 64 KB, with a reminder that it can hold personal data) and `replay`. Nothing over MCP.

## D54. Alerting and differences from the plan (M1.5, 15 Oct)
- **The `webhook` signal.** If a hook's oldest pending event has been failing for more than 15 minutes (`hook_alert_after_s`), the delivery worker reports it to the M1.3 engine (`HookFailing`, repeated every cycle; `HookOk` when it recovers), giving the signal `webhook` on `app:<app>`: it joins the open incident of a stopped app (one alert, one "resolved", tested) or opens its own. Reports that stop for 60 s (the worker died, or ops restarted with a restored signal and the hook has since recovered) clear the signal, so it can't get stuck. Removing the app closes it quietly.
- **Differences from the plan.**

  - `GET` on a hook URL is a terse 405; `ctl hooks` takes `list`, `show` and `replay`.
  - The plan's "rollback revokes" test deploys a copy of the fixture without `webhooks:` (a normal deploy; the rollback path uses the same provisioning with the older manifest).

## D59. The logging convention (M2.1, 16 Oct)
**What.** Every Annex app logs one JSON object per line on stdout: `ts` (ISO 8601 with time zone), `level` (`debug|info|warn|error`) and `msg` are required, anything else is free-form. Inside a request each line also gets `request_id` and `user` (the `Remote-User` login). `LOG_LEVEL` is injected (default `info`) and is the one injected name an app may override under `env:` (validated: debug, info, warn or error; a secret can't be named `LOG_LEVEL`). The rules are in the contract's new "Logging" section, the skill and every template's `AGENTS.md`: use the logger, pick the level (debug detail, info what happened, warn odd but handled, error failed), log errors with context, jobs log a start and an end line with counts and duration and exit non-zero on failure, and **never** log secrets, tokens, passwords, cookies, request bodies or full product records (counts and IDs are fine; other personal data isn't, so `client-lookup` logs `chars=4, matches=3`, never the search text, and the report job logs the recipients' logins, not their addresses).
**The helpers** (`runtime/annex_runtime.py` and `.js`, synced to every copy with `scripts/sync-runtime.sh`): Python has `log.debug/info/warn/error/exception(msg, **fields)` on stdlib `logging` with a JSON formatter (the root logger too, so uvicorn's and libraries' lines come out in the same format), `request_context(headers)` (a context manager that sets `request_id` and `user`) and `new_request_id()`. Node has `log.*(msg, fields)`, `annexRequest` (Express middleware on `AsyncLocalStorage`, no dependency) and `newRequestId()`. A field can't overwrite `ts`, `level`, `msg`, `request_id` or `user` (it gets a trailing `_`); an incoming `X-Request-Id` is reused only if it looks sane (8–64 of `A-Za-z0-9._-`), otherwise a new 16-hex id is made, so a client can't inject newlines or oversized values into the logs. In Node the access line gets the context explicitly, because `finish` events can fire outside the async context (found by the unit test).
**The templates.** `python-web` and the two examples get a FastAPI middleware that sets the context and the `X-Request-Id` response header and logs one access line per request (method, path without the query string, status, ms; `/healthz` at debug level, so the 30-second health checks don't fill the log), turns an unhandled exception into an error line with its stack and a plain 500, and starts uvicorn with `log_config=None, access_log=False` so nothing prints in another format. `node-web` does the same with `annexRequest` plus an error handler. `python-job` logs start and end lines. `static` can't import the runtime (its server is stdlib and "keep as is"), so `server.py` writes the same format itself. Every web template logs a `started` line at startup, which is also what the deploy check looks at.
**The check (warn only).** After the health gate, `annex deploy` reads the new web container's last 50 lines; the pure function `logcheck.structured()` (unit-tested) says whether at least one is a JSON object with a valid `level` and a `msg`. If there are lines and none are, the result gets "logs aren't structured: use `log` from annex_runtime.py instead of print() ...". The deploy always succeeds. **No lines at all means no warning** (a quiet app has nothing to judge). Job-only apps are skipped until M2.2 can check their first run from stored lines. `tests/print-probe` (an app that uses `print()`) pins the warning in `test-apps.sh`.
**Tests.** `runtime/tests` (12 Python and 7 Node tests: format, levels, request context, unsafe ids, reserved fields, exception stacks), `cli/tests` (9 tests of the check), both run by `test-smoke.sh` and `test-all.sh`. `test-smoke.sh` also deploys `client-lookup`, sends one request and checks that the response's `X-Request-Id` is on the app's log lines **and** in Traefik's access log, that the last line is structured, and that the search text isn't logged. I also deployed all four templates once: no warning, the same id on the header, the access line and the log lines, a client-supplied id reused.
**Alternatives.** Wrapping `print()` (monkey-patching hides the problem, and the agent still writes plain text). Refusing deploys with unstructured logs (Nejc, 15 Oct: warn, never refuse). A `structlog` or `pino` dependency (a new package per template for 40 lines of code). Putting the request id in a `traceparent` header (nothing downstream reads it yet).

## D61. Open question: pg_trgm and the search index (M2.2, 16 Oct)
**Answer: yes.** `postgres:16.15-alpine3.24` ships `pg_trgm` 1.6. It is a *trusted* extension, so `annex_ops` (the database owner) installs it with `CREATE EXTENSION IF NOT EXISTS pg_trgm SCHEMA public` in `annex_ops.sql`, without a superuser and without a new component (tested in a throwaway database first, then applied by `push.sh`). ## D62. Open question: partition management (M2.2, 16 Oct)
**Answer: annex-ops does it, in plain SQL, with no extension or scheduler.** `pg_partman` isn't in the image (a new component), and the platform's scheduler (Ofelia) runs app jobs, not platform ones.
- **Partitions** are UTC days, `annex_ops.logs_YYYYMMDD`. A line gets its partition made *before* it is inserted (so no line ever fails for want of one), and the keeper thread (`logship.Keeper`, hourly, `log_housekeeping_s`) makes today's and the next two days'.
- **Retention:** a partition is `DROP`ped when its whole day ended before now minus `log_retention_days` (14), so a line lives between 14 and 15 days. A line older than the retention, or more than two days in the future, is never stored (it would have no partition worth keeping). Cursors of destroyed containers older than the retention are deleted in the same pass.
- **Size guard:** if the partitions (tables and indexes) pass `log_max_mb` (2048), the oldest are dropped early, never the newest, and the engine gets `LogSample` and raises `platform:logs` for admins ("the stored logs passed 2048 MB, so the oldest day(s) were dropped early"). It clears when the table is under 80 % of the limit again, so it doesn't flap at the limit. The three settings (`log_retention_days`, `log_max_mb`, `log_rate_per_s`, `log_housekeeping_s`) come from `state/ops/tuning.json` or `OPS_<NAME>` like the others; `test-logs.sh` shortens the retention to 2 days and watches an ancient partition disappear.
- **The unique index** on a partitioned table has to contain the partition key, so the dedupe key is `(ts, h)`.

## D63. How lines get into the table (M2.2, 16 Oct)
**What.** `logship.py` (decisions, pure and unit-tested), `logstore.py` (inserts, partitions, queries) and `follow_logs.Follower` in a new *exact* mode (D42's follower and its cursor table, as the plan said).
- **One follower per container id**, started by the watcher's `Seen`/`Start` and stopped on `Destroy` (it reads to the end of the stream first). Followers are keyed by id, not name: a recreated container has a new id, so its lines carry its own `release` label, and the old container's last lines are still read to the end. Cursors are `ship:<name>:<id12>` in `log_cursors`.
- **Exact mode** (needed, found while reading the code): the old follower skips a line with the same microsecond timestamp as the one before, and the lines of one traceback (and of one job run) share a microsecond. Exact mode takes Docker's nanosecond timestamps, skips nothing, hands the handler integer nanoseconds, replays one second before the saved cursor after a restart, and **only saves the cursor after the sink has stored the rows** (`before_save = sink.flush`). So a hard crash loses nothing and a replay is harmless: every row has `h = md5(container, stream, nanosecond timestamp, raw line)` and `UNIQUE (ts, h)`, so `ON CONFLICT DO NOTHING` (D46's pattern) removes repeats; a small in-memory set keeps most repeats from reaching the database at all.
- **`ts` is Docker's timestamp, never the app's own** (an app can't pick its day or fall outside a partition); the sub-microsecond remainder is in `ns`, so same-microsecond lines keep their order. A first start with no cursor reads from the container's start, at most `log_retention_days` back.
- **What is shipped** (Nejc, plan decision 5): every app container, `annex-ops`, the receiver (`hooks`), the gateway's lines, Authelia's sign-in lines. Not the socket proxies, Traefik, Gatus (nor Ofelia's own lines, Metabase, Homepage, Mailpit, Dozzle, backup). Beyond the plan: ops's and the receiver's uvicorn access lines for `/healthz` 200 are dropped (two containers × 5,760 lines a day, the same reason the proxies are excluded).
- **Gateway reads:** product-db's `RAISE LOG` line (`LOG: annex-gateway role=app_x method=… path=…`, no query string) becomes a row with `container='gateway'`, `app` from the role (`app_monthly_report` → `monthly-report`, unambiguous because app names have no `_`), `fields {method, path, view}` and the app's current release. The CONTEXT/STATEMENT lines Postgres adds are dropped. `annex logs --source gateway` shows them; the default hides them from an app's own logs. M2.5 aggregates them.
- **Authelia:** its logfmt is parsed; kept are failed attempts, unknown users, access denied to a known user, password-reset lines, and every warning or error; dropped are the "not authorized to user <anonymous>" line the front-door check causes every minute (283 in four hours) and the user-file reloads. Authelia doesn't log successful sign-ins at info (M2.5's spike 2 decides what to do about that). A failed attempt line contains whatever was typed as the username, which can be a password typed into the wrong box: it is kept like Authelia keeps it, for the retention, readable by admins only.
- **Scheduled jobs** (not in the plan's list, but the plan needs them: "job-only apps' first run's stored lines"): a job runs through `docker exec`, so its output isn't in the app's container log but in **Ofelia's** (`StdOut: <first line>`, then the other lines bare). A second, exact reader on `annex-ofelia-1` (own cursor `ship:annex-ofelia-1`; the existing one that feeds the alert engine is untouched) stores the output under the app with `container = job:<name>` and the app's current release. Output of `annex run` goes to its caller and isn't stored.
- **Not-JSON lines** (a `print()`, a library, a traceback): stored as written (indent kept), `fields` NULL (that *is* the "not structured" flag the job-only check uses), `level` guessed: `error` for a traceback, its frames, a line that starts with an exception class, or that contains `ERROR`, `FATAL`, `CRITICAL` or `Exception`; else NULL (as the plan says). JSON that lacks a valid `level` or a string `msg` is treated the same way, as the convention's check does. Levels `warning`, `critical` and so on are not mapped for structured lines: they aren't the convention.
- **Secrets** (plan: dropped before storing): keys matching `password|passwd|token|secret|authorization|cookie|api_key|credential|private_key` (case-insensitive substring: `max_tokens` goes too, on purpose) are removed at any depth of `fields`. As a net under the rule (not a licence), free text in messages, string values and plain lines is redacted for `password=…`, `Authorization: Bearer …`, JWTs and `user:password@` in URLs. `test-logs.sh` writes one test secret as a field, nested, in a header-like field, in a plain line and in a traceback, proves the live container logged it, and greps the whole table for it. NUL, terminal colours and lone surrogates are cleaned and NaN becomes text, so one odd line can't fail a batch; a line the database still refuses is skipped and counted, not retried for ever.
- **Rate cap** (200 lines/s per container, `log_rate_per_s`), counted in *log time*, not wall time, so reading history gives the same answer as reading live: the second's extra lines are dropped and **one line** ("annex-ops dropped N log line(s) of this container: it wrote more than 200 lines in one second", level warn) is stored when that second is over (also when the flood simply stops).
- **Sizes:** messages are cut at 8 KB, fields at 8 KB serialised (then only their key names stay), one string value at 2,000 characters.
**Alternatives.** Following by container name (can't tell releases apart, and the cursor of the old and new container would collide); Docker's `since` with µs and the old strict "newer" test (drops traceback lines); a periodic bulk read instead of followers (a gap whenever a container is replaced between reads); a `fields::text` column next to `msg` for search (doubles the storage; an expression index doesn't).

## D64. No gap on a redeploy, and it must never block one (M2.2, 16 Oct)
`cli/ops.py` calls `ctl logs-drain <container> --timeout 5` (through `docker exec annex-ops-1`, wrapped in `timeout 10`) in `_activate` right before Compose replaces the container, which covers a deploy, a rollback and, on a failed health gate, the re-activation of the previous release that replaces the *failed* container. ## D67. Error groups: where they come from, what is "the same", when an email is owed (M2.3, 16 Oct)
**What.** `errors_group.py` (pure, unit-tested), `errors_run.py` (scanner thread, database, emails). No new component: a thread in annex-ops reads `annex_ops.logs` (D63) every `errors_scan_s` (10 s), over the window that ended `errors_settle_s` (10 s) ago, so every line of a traceback has been stored. It turns rows into events, stores each once and counts it in its group.
- **What is an event:** a structured line at level `error` (`log.error`, `log.exception`, the template middleware's "unhandled error"), a Python traceback an app printed (header, frames, exception line, assembled from the stored rows of one container, with chained exceptions as one event), and any other line that was guessed `error` (D63). Web apps, scheduled jobs (container `job:<name>`) and browser reports (`source=browser`) are covered; the gateway's lines are not.
- **What is "the same":** the fingerprint is `(app, key)`. For an exception (a structured line's `exc` and `stack`, or a printed traceback) the key is the exception type plus the file and function of the failing frame, so a different message doesn't make a new group; otherwise the message with numbers, UUIDs, hex ids, quoted values and file paths replaced by placeholders. **The frame is the innermost one in the app's own code**, not in `site-packages`, the standard library or `node_modules`: the first run grouped everything as `wrapped_app` (a Starlette wrapper that re-raises) because the stack's tail was cut at 2,000 characters. Fixed twice: `stack` now keeps 6,000 characters (a Python traceback its **end**, where it was raised; Node its start), and the frame is chosen as above.
- **Idempotent:** an event is stored under the hash of the line that started it (`error_events`, primary key), so reading a window twice, a restart's replay or a drain count nothing twice. The scan cursor is `log_cursors` `errors-scan`; a first start begins at "now" (no flood of emails about old errors). A traceback that the window ends in the middle of holds the cursor back to its first line; one older than 30 s with no end is finished as it is. A finished trace waits `TRACE_GAP_S` (3 s) after its last line, because a chained trace could still follow. Two tracebacks in a row are two events, not a chain (found by the first test run: they were merged).
- **When an email is owed:** a new group; a group not seen for `error_quiet_s` (24 h); a group seen in a **newer release** than it was last seen in (it had gone from the releases in between, or it's a new deploy's problem: one email per release at most). Not for more of the same: 50 errors differing in a number are one email (tested). Sent by the same thread: to the owner, `alerts.to` and admins (`messages.recipients`, through `incidents.send_alert`, so they're in the send log like every email), at most `error_alerts_per_hour` (5) emails per app per hour; if more are owed than fit, the last slot is **one summary** of the rest ("6 more kinds of error"), and with no slot left they wait for the next hour. A notification, not an incident: nothing resolves, nothing is raised in the engine.
- **State** (for `annex errors` and the console): `active`, or `quiet` when not seen for `error_quiet_s` or when a newer release than the last one that had it is live (read from `annex_ops.releases`, latest life of the app). "Quiet since r3" is shown, never emailed.
- **Retention:** events 14 days, groups 30 days after last seen, send log 7 days (hourly housekeeping). `annex remove` deletes the app's events, groups and send log (a redeployed name starts at r1 again, D65).
**Alternatives.** Grouping inside the log shipper's handler as lines arrive (no late rows, but every restart's replay would double count and a window can't be re-read); counting events from the logs table at query time (no state, but "owed an email" needs one); one email per error with de-duplication by time (the plan's "exactly one" would depend on timing).
**Tests.** `test-errors.sh` (below) and 28 unit tests in `test_errors_group.py` and `test_logship.py` (normalising, fingerprints, traces, chains, windows, frames, quiet/owed rules, the hourly plan, the messages).

## D71. Spike 2: where successful sign-ins come from (M2.5, 16 Oct)
**Result.** Authelia 4.39 logs a successful first-factor sign-in only at **debug** ("Successful 1FA authentication attempt made by user 'sam'", with the path and `remote_ip`); a failed one is an error at any level. Tested with a throwaway Authelia (`docker run --rm`, the real config and users file, a fresh in-memory database, two POSTs to `/api/firstfactor`, then it exits): 66 log lines for two sign-ins and ten signed-in forward-auth calls, i.e. **two debug lines per request** ("Checking the authentication backend for an updated profile", "Check authorization of subject ... and object <url>"), no cookies or passwords in them. Options weighed:
1. **Authelia at debug, annex-ops ships only the sign-in lines (chosen).** One config line (`log.level: debug` in the template; recreates Authelia on the next push). The cost: the container's own log grows by about two lines per request through the front door (roughly 100–200 bytes each; Docker rotates it at 3 × 10 MB, `daemon.json`) and the debug lines can contain the URL of a request, query string included: Traefik's access log already holds exactly that, so nothing new is exposed. `parse_authelia_line` keeps only `Successful 1FA/2FA ...` among debug lines, so the stored logs aren't flooded.
2. Authelia's `authentication_logs` table (every attempt with a success flag): it lives in the same sqlite file as sessions, TOTP secrets and identity tokens, which must not be mounted into annex-ops; Authelia's CLI can't export it.
3. The plan's fallback, Traefik's access log: `POST /api/firstfactor` with 200 shows *that* someone signed in but not *who* (no session yet, the body isn't logged), and "first signed-in request of the day" isn't a sign-in.
**Also:** failed sign-ins were already available. A failed attempt's username is kept as the actor only if it looks like a login (`^[a-z][a-z0-9._-]{1,31}$`); anything else (a password typed into the username box) is recorded as "not a login" with no actor, because the audit trail is kept a year, the logs 14 days.

## D72. The audit trail (M2.5, 16 Oct)

## D81. annex-ops reports its own threads (21 Oct, hardening B1)
**What.** `ops/annex_ops/threads.py` is a registry: every long-running thread registers a name and the longest one pass may take (sleep included), then calls `beat(name)` on every pass.
- `/healthz` lists each thread with its state and the age of its last beat, and answers **503** when one is `dead` (the thread ended) or `stale` (no beat for more than 3 periods). It also lists the buffers (`queues`): the log sink's rows waiting and `lost`, the shipper's followers and queue, the engine's queue, and the usage buffer with a `dropped` hook that B2 fills.
- Expected periods (stale = 3 times these): engine 30 s (a pass can wait on SMTP, Slack and a log tail, 10 s each), usage 60 s, digest 90 s, hooks delivery 60 s, host sampler `host_sample_s + 30`, health checker `check_interval_s + 30`, error scanner `errors_scan_s + 60`, auditor `audit_scan_s + 60`, log sink 30 s, log shipper 60 s, log keeper 120 s, Docker watcher and each log follower 150 s (Docker ends a quiet stream after 120 s). A loop whose sleep is a setting updates its period at each beat.
- **Followers never die.** `Follower.run` wraps the whole body: an unexpected exception is logged once a minute per follower, waited out with a doubling delay (2 s up to 60 s) and the follower starts again from its saved cursor; the loops catch `Exception` per pass too. Handler and cursor-save errors share the once-a-minute log. A follower stopped on purpose retires from the registry; one that is still listed after its thread ended is shown `dead`.
- **The shipper restarts dead followers** from their cursor, checked every 5 s (`Shipper.revive`, using the Seen/Start it kept for each container). A failed restart (Docker busy) keeps the dead entry and is tried again.
- `Sink.lost` now also counts the rows dropped when a failed insert is put back over the limit (before, only `add` counted).
- **Health checker.** A new platform check, `platform:ops`, requests `http://ops:8000/healthz` (`config.OPS_URL`) every round and is up on a 200. After two failures the engine raises `down` on `platform:ops`, the subject the Docker watcher already uses for ops, so a dead thread alerts admins as "platform: ops is down". The check goes through the platform network, so it also proves the network path the console uses. Docker's own healthcheck of the ops container hits the same URL and now goes unhealthy too: that is the second signal on the same subject, not a second incident.
- **How the thread table reaches the console.** The console fetches ops' `/healthz` over the platform network (`threads.fetch`, 2 s timeout, standard library only) when it renders the Platform page. Considered instead: ops writing the table into the database for the console's read-only role. Fetching needs no new table or grant, shows the live state (a database outage included, where a table would go stale) and keeps the console without access to ops internals; a failed fetch is shown as "annex-ops did not answer". The cost: `/healthz` is also readable by apps on `edge` (it already was). It carries thread names (`follow-ship:annex-app-<name>:<id>` names containers), queue numbers and no data, like `/tiles`.
- **`ctl`.** `ctl health` adds `thread:<name>` rows in the shape of the checks (`state` ok, stale or dead) and `thread:_ops` `unreachable` when ops doesn't answer, so `--json` consumers that read `["state"]` keep working. `ctl logs-stats` adds `sink` (buffered, max, lost) and `queues`. Both read the running ops through `http://127.0.0.1:8000/healthz`, because the buffers live in that process, not in `ctl`'s.
- **Console.** The Platform page has an "annex-ops" section: threads (worst first), their last progress and period, the buffers and the rows dropped.

**Why.** A thread that died (or hung on a socket) left no trace: `/healthz` only ran `SELECT 1`, a follower that hit a driver error outside `OpsError` ended silently and was never restarted, and `Sink.lost` was never shown (review finding, hardening plan "What was found").

**Alternatives.**
- A restart policy on the unhealthy container: `restart: unless-stopped` ignores health, and `autoheal` is a new component and a socket with write access.
- One heartbeat table in Postgres: blind in the failure that matters most (the database), and a write per thread per pass.
- Failing `/healthz` on a stale thread only: rejected because a restart loop caused by one slow thread hides the others; the table names the culprit and the incident carries the 503 text.
- Registering threads in `__init__`: a thread that never started would read as stale; they register at the top of `run()`, so a thread that crashes before that is not listed (nothing in ops does work there).

**Not done.** The usage ingest's dropped count and the byte budgets are B2 (`threads.gauge("usage", ...)` already reads `ingest.dropped` if it exists). The alert engine's own sender thread is B5.

**Tests.** `ops/tests/test_threads.py` (verdict, registry, `/healthz` 503, `fetch`), a follower surviving an unexpected store error and an unexpected loop error (`test_follow_exact.py`), `Shipper.revive` (`test_logship.py`), the `platform:ops` target (`test_health.py`) and the console's table (`test_console_view.py`). `test-logs.sh` checks that `/healthz` lists the followers and the sink's counters after ops restarts. Not run here (VM): `test-smoke.sh`, `test-logs.sh`.

**Prod:** metrics (Prometheus or CloudWatch) replace the thread table; `/healthz` stays.

## D83. Images with platform labels are refused (22 Oct, hardening A2)
**What.**

- The contract line "never write Docker labels" now says a deploy refuses such images.

## D85. Push stamp, one settings source, secrets from stdin, prerequisites (22 Oct, hardening C2)
**What.**
- **Push stamp.** `render.py` writes `.build/platform/VERSION` (`commit=`, `dirty=`, `env_sha256=`); it goes to the VM with the bundle. `push.sh` reads the VM's `platform/VERSION` first and calls `scripts/pushcheck.py check`, which prints both commits and refuses when the VM's commit is not an ancestor of the local HEAD (the same commit passes), or is not in this checkout at all (message: `git fetch`, or `--force`). A VM with no VERSION file (the first push) proceeds. `--force` skips the check and `--extras` still works; flags combine. The decision is a pure function (`pushcheck.decide`), tested in `cli/tests/test_pushcheck.py` (the repo's script tests live in `cli/tests`, like `test_selftest_builder.py`).
- **One settings source.** `setting` in `scripts/lib.sh` reads `platform/.env` on the VM, the file the CLI's `Remote.settings` reads, with one `ssh cat` per run cached in `.build/settings.<pid>` (the pid of the main shell, so `$(setting X)` subshells share it; the file is deleted at start and old ones are swept). Where the VM has no `.env` yet it falls back to the local render and says so on stderr. `setting_local` is the old behaviour (the local render) and `bootstrap.sh` and the last line of `push.sh` use it: bootstrap runs before any `.env` is on the VM and needs the local `ANNEX_CERT_NAMES`, and after the sync both are equal. `render` still writes the local copy for the rsync.
- **`annex secret set <app> KEY`** reads the value from stdin (hidden prompt on a terminal) or `--from-file PATH`; one bare key per call and one line, so a pasted multi-line value is refused instead of split. `KEY=VALUE` still works and warns on stderr that the value is in shell history and the process list. `ops.secret_set` is unchanged (it keeps `_name` and `KEY_RE.fullmatch`) and so is the MCP server. The fix-it messages (manifest, `annex_vm.py`), the contract, the skill and the templates now show the bare-key form. The suites keep `KEY=VALUE` with several keys in one call (random test values, output discarded).
- **`docs/setup.md`**: a Prerequisites section, and the two hard-coded paths became `$(pwd)` (run from the repo root).

**Why.** A checkout that was behind (or on another branch) could silently roll the platform back, and nothing recorded what was deployed (review finding, hardening plan "What was found"). Scripts read a local render that could differ from what the CLI saw on the VM. A secret on the command line ends up in shell history.

**Alternatives.**
- Stamp compare by `.env` hash too: the hash is stored and shown in the file, but a changed `.env` is a normal reason to push, so it doesn't refuse.
- A lock on the VM (one pusher at a time): more mechanism, and the stamp already catches the stale-checkout case it was meant for.
- Caching settings in a variable: lost in `$(...)` subshells, which is how every script calls `setting`.
- `secret set KEY` taking several keys from stdin as `KEY=VALUE` lines: that is the form that leaves the history problem to the caller's pipe; one key per call is simpler to explain.

**Known limits.** The stamp is written by the rsync, before the start, so a push that fails halfway leaves the new commit on the VM; pushing again is a no-op check. A dirty tree is only labelled `(dirty)`: its commit is the one the changes sit on.

**Tests.** `cli/tests/test_pushcheck.py` and `cli/tests/test_secret_input.py`. Not run here (VM): `test-smoke.sh`, a `push.sh` twice in a row, `push.sh` from a checkout that lacks the VM's commit.

**Prod:** the stamp becomes the deployed image tag and release record; secrets come from the client's secret manager.

## D86. Byte budgets and bounded queues in annex-ops (22 Oct, hardening B2)
**What.** Every buffer in annex-ops that grows while something downstream is slow or down now has a limit in bytes as well as rows, and drops the oldest first, counting what it dropped.
- **Log sink** (`logstore.Sink`): `log_buffer_rows` 20,000 and `log_buffer_mb` **20**. A row's size is `row_bytes`: its text, its serialised `fields` and 600 bytes for the objects around them (an estimate to bound by, not a measurement). Over either limit, `add` and the put-back after a failed insert drop the oldest rows and add them to `lost` (already in `/healthz`, which now also shows `bytes` and `max_bytes`). One row bigger than the whole budget is dropped too.
- **Usage buffer** (`usage.Ingest`): `usage_buffer_rows` 50,000 and `usage_buffer_mb` **8** (300 bytes per row plus its strings). It used to grow without bound in `handle` as well as in `flush`'s retry, so both are capped now. Dropped rows are counted in `dropped`, which B1's gauge already read, and it also shows `bytes` and `max_bytes`.
- **Engine queue** (`incidents.Manager`): `queue_max` 10,000 (the queue's `maxsize`) and `queue_soft` 5,000. The queue carries Docker events (die, start, stop, destroy, OOM, health, seen), the health checker's verdicts, host and log samples, webhook and job results, maintenance, **and `Request`, one per Traefik line** (the 5xx rate). Only `Request` is a log-derived signal that is safe to lose: past `queue_soft` waiting inputs it is dropped and counted (`engine.dropped` in `/healthz`, logged once a minute), without blocking the Traefik follower. Everything else waits for room with a plain `put`; the soft limit keeps half the queue free for it, so a flood of requests can never take the place of a container's death. A job result is a log-derived signal too, but one per job run, so it is kept like the rest.
- **Shipper queue** (`logship.Shipper.q`): not bounded. It only carries Docker events (a container seen, started or destroyed), nothing may be dropped there, and it holds at most a few entries per container. Log lines never use it. A comment says why.
- All five numbers are settings (`_settings`: `OPS_LOG_BUFFER_MB` and the others in the environment, or in `tuning.json`), read when ops starts. The engine's two are in `Tuning`, the others in `LogSettings` and `UsageSettings`.

**The arithmetic.** ops has 128 MiB (`compose.yaml`) and measured **85 MiB at its highest** (D73 after the alert suite, D74 over a quiet day) with these buffers nearly empty. Worst case is a database outage, where the sink and the usage buffer fill together: 20 + 8 MiB, plus the engine queue (10,000 inputs of about 250 bytes, 2.5 MiB if it ever filled) is **30.5 MiB**. 85 + 30.5 = 115.5 MiB, **12.5 MiB of headroom**. The plan's first numbers (32 and 16 MiB) would have reached 135 MiB, over the limit, so they were lowered; they are settings, so a bigger container limit and bigger buffers go together. At normal volume (a few lines per second) neither buffer comes near its limit: 20,000 rows is hours of the whole platform's logs.

**Why.** A database outage left the sink's 20,000-row cap as the only limit, but rows are not the same size (a line is capped at a few KB, `fields` nest), and the usage buffer and the engine queue had no limit at all: ops would have grown until the kernel killed it, taking the alert engine with it, at the moment alerts matter most (review finding, hardening plan "What was found").

**Alternatives.**
- A byte limit measured with `sys.getsizeof` per row: slow on every line and still blind to shared strings; a fixed overhead plus the text is close enough and cheap.
- Dropping Docker events when the engine queue is full: no; a missed `die` is a missed alert. Blocking the watcher is the lesser harm (the engine thread is also watched, B1).
- Two queues for the engine (one for requests): needs the engine loop to read two queues in order; the soft limit does the same with one.
- Spilling to disk instead of dropping: a disk buffer to manage (and `/srv/annex` is the only place ops may write); the lines are in Docker's own log until a follower reads them, and a restart replays from the saved cursor, so a dropped sink row is only lost if the container's log rotated too.

**Not done.** B6 (a cap before parsing, sink inserts off the follower thread) is a separate step. Rows dropped from the sink are not recovered from Docker's log after the outage; the follower has already moved its cursor.

**Tests.** `ops/tests/test_budgets.py` (14): row and byte limits and the count for the sink, a failed insert put back over both limits, one huge row, the usage buffer by rows and by bytes, `handle` over its limit, and the engine queue (requests dropped past the soft limit, Docker events kept after the requests filled their share, a full queue never blocking a request). Not run here (VM): `scripts/test-logs.sh` (its restart check reads the sink's counters from `/healthz`).

**Prod:** a log pipeline with its own disk buffer (Vector or Fluent Bit) instead of in-process buffers.

## D87. Backups that restore a VM (22 Oct, hardening B7)
**What.**
- The backup container also mounts `secrets/` and `state/directory/` read-only (`/backup/secrets`, `/backup/state/directory`), so a nightly archive holds what a new VM needs besides the databases and `/data`. Nejc approved that the archives now contain secrets.
- `dump-all.sh` writes `dumps/current/MARKER` (UTC time, one line) into the new dump folder before it replaces `current/`, so the marker always belongs to the dumps next to it. A failed dump leaves the old `current/` and the old marker.
- `host.py` reads the marker with one small request (`docker_api.path_read`: `GET /containers/annex-backup-1/archive?path=/backup/dumps/current/MARKER` on the read-only proxy, which already allows the HEAD form; it refuses anything over 4 KB). `HostSample` gets `dump_at`. The engine raises `backup-stale` on `platform:backup` when the archive's time is more than `backup_stale_s` (a day) newer than the marker, and clears it when not. It is a second signal on the existing subject, so one incident, one e-mail; an unreadable or missing marker (the first night after the upgrade, a proxy error) gives no verdict and leaves an open signal alone. `ctl host` shows `dump_age_h`.
- `vm/bootstrap-secrets.sh` makes `backups/` mode 700.
- `docs/operations.md`: "Restore a whole VM", and the scratch-directory check.

**Why.** Archives held app data and database dumps but not the secrets, so a lost VM meant a new `master.env`, new tokens and all accounts gone. And a failing dump hook (set -eu) left the archive step succeeding with the previous dump: the archive-age alert stayed green over data that was days old.

**Alternatives.**
- Read the marker out of the newest archive: a gzip tar has no index, so reading one member decompresses everything before it (every app's `/data`), every minute. The dumps folder is replaced as a whole and archived at the same moment, so the live marker is the same file the newest archive holds. The cost: if someone runs `dump-all.sh` by hand between archive and check, the marker is newer than the archive's copy; the check only lets a newer marker pass, so that is harmless.
- Mount `dumps/` into ops: a bigger mount than one file read, and ops would see every database dump.
- Archive permissions: offen v2.49.1 runs as root in the container and I found no setting for the file mode that I could verify offline. The protection is the directory: `backups/` is 700, owned by annex, so other local users can't enter it whatever the file mode. Per-file 600 (and an offen `BACKUP_FILE_PERMISSIONS`-style setting, or GPG) is left to the orchestrator's check on the VM; see the hand-back.
- Backing up Postgres data directories: no, dumps are the format that restores across minor versions.

**Not done.** The secrets sit unencrypted in the archive (offen's `GPG_PASSPHRASE` would encrypt, but then the key must live outside the VM: prod). `deploy/` (app sources) isn't archived: redeploy from the app's own folder.

**Tests.** `ops/tests/test_host.py`: the engine rule (open, exact-day boundary, no repeat, clear, joining the overdue incident, unreadable marker), marker parsing, `path_read` on a fake tar. Not run here (VM): a backup, the archive's contents and mode, the scratch restore.

**Prod:** archives to S3 with offen's GPG encryption and a key outside the VM; secrets in a secrets manager make this moot for most of `secrets/`.

## D88. Per-app networks (22 Oct, hardening A5, Nejc: egress enforced, 10.213.0.0/16)
**What.**
- **One internal network per app**, `annex-app-<name>` (labels `com.kaldi.annex=true`, `com.kaldi.annex.app=<name>`, `com.kaldi.annex.network=app`). On it: the app's container and only the platform containers it uses, connected at runtime with `docker network connect`:
  - `annex-traefik-1` if the app is web (routes; the deploy's health gate `docker exec`s `wget` from it);
  - `annex-ops-1` as `ops`, always (health checks, webhook delivery, email and Slack, the job and log machinery that reach the app by name);
  - `annex-gateway-1` as `gateway` if it reads views;
  - `annex-appdata-db-1` as `appdata-db` if it has Postgres.

  The aliases are the names apps already use (`http://gateway:3000`, `http://ops:8000`, `appdata-db:5432` in `DATABASE_URL`), and ops and Traefik already reached apps by container name (`annex-app-<name>`), so no app and no ops code changed.
- **Apps left `annex-edge` and `annex-appdata`.** The generated compose file declares only `annex-app-<name>` (and the egress network below), both external. No two apps share a network, so an app can't resolve or connect to another app, and identity headers can only arrive through Traefik.
- **Egress is enforced.** `egress: []` (every template, example and the fixture) means no internet: the app's only network is internal. A non-empty list also puts the app on `annex-egress-<name>`, a non-internal network with only that app on it; platform containers never join it (`networks-sync` disconnects any it finds). It opens **any** host, and the LAN: the list isn't filtered per hostname (that needs a proxy, below). The manifest now refuses entries that aren't hostnames and its message says what `[]` and a list mean; the contract's `egress` line and a new "Network" rule say the same.
- **Subnets.** Every app and egress network is created with an explicit `--subnet`: the lowest /24 of `ANNEX_APP_SUBNETS` (new setting, default `10.213.0.0/16`, `.env.example`, rendered into the platform `.env`, validated by `render.py`) that overlaps no existing Docker network; on Docker's overlap error the next is tried (two concurrent deploys). No `daemon.json` change (VM system config).
- **Traefik:** each web app carries `traefik.docker.network: annex-app-<name>`; the provider default stays `annex-edge` for the gateway and the receiver (comment in `config/traefik/*.tmpl`).
- **`vm/annex_vm.py networks-sync`** (stdlib, idempotent, JSON): `networks-sync <app> [--web] [--postgres] [--views] [--egress]` creates the network(s) if needed, connects the platform containers the app needs and disconnects other platform containers (Compose project `annex`); without `--egress` it removes a leftover egress network. With no app it syncs every app from `deploy/<app>/deploy.json` (`_write_record` now stores `egress`) and reports `still_shared` (app containers still on `annex-edge`/`annex-appdata`) and `orphan_networks`. The CLI's `_activate` runs it before `compose up` (deploy, the gate's automatic switch back, rollback). `deprovision` (called by `annex remove`) disconnects everything and removes both networks. Pure parts (`network_needs`, `record_needs`, `sync_plan`, `pick_subnet`) have tests.
- **Runtime, not compose.** The platform's `compose.yaml` doesn't name app networks (it can't: they come and go with apps). A runtime connection survives a restart and a Docker restart but not a recreate, so `push.sh` runs `networks-sync` after its appdata-db step and again after the full start; by hand, after a recreate (`docs/operations.md`, "App networks"). **Compose doesn't fight it:** its recreate check compares the config hash and, for networks, only that the container is on every network the service *declares* (`checkExpectedNetworks` in Compose v2's convergence code); extra networks are ignored, so `docker compose up -d` neither recreates nor disconnects. (A declared external network that was removed and recreated has a new ID, so the app's container would be recreated by its own `up`: what we want.)
- **Apps deployed before this** stay on the shared networks until their container is recreated from a new compose file. Redeploying does it. For an app whose source isn't at hand (`vibe-leads`), `annex migrate-networks <app> [--egress]` (human only, not over MCP) rewrites only the networks of its compose file on the VM (a pure `rewire_compose`, tested; the old file is kept as `compose.yaml.pre-d88`), reads what the app uses from the file (routed, on `annex-appdata`, a gateway URL), records `egress` in `deploy.json` (`["*"]` with `--egress`: hosts unknown), runs `networks-sync` and recreates the container.
- **Contract and runtime:** identity headers are trustworthy only on the front-door path, and apps can't reach each other (contract "Identity" rule, `current_user`/`currentUser` docstrings, synced to every copy).

**Revises.**
- **D2:** "per-app networks (open for later)" is done. `annex-edge` now holds Traefik, the gateway, ops and the receiver only; the problem D2 solved for Dozzle (an app calling a platform UI with a forged header) now holds between apps too.
- **D17:** apps no longer join `annex-edge` and `annex-appdata`; the deploy runs `networks-sync` before starting the container, and the generated compose file declares the app's own network (and its egress network).
- **D36:** ops is no longer reached on `edge`: apps reach it on their own networks, where it is `ops`. It stays on `edge` for Slack. "Any app on `edge` can reach ops" becomes "every app can reach ops, and only ops and what it declared".
- **D69's network line:** apps are no longer on `edge` or `appdata`; appdata-db is on `appdata`, `console` and the network of each app with Postgres. The console's guarantee is unchanged (it is on no app network; `test-console.sh` and `test-smoke.sh` check it).

**Why.** With one flat `annex-edge`, any app could call another app directly with a forged `Remote-User`, and the contract told apps to trust it (hardening plan, "What was found"). Before the Goat Arcade demo several builders' apps run side by side. Egress: Nejc chose enforcement now; an internal-only network is the one switch Docker gives without a proxy.

**Alternatives.**
- Keep `annex-edge` for egress, alone per app: same as the egress network here, but every app would keep the internet.
- One shared `annex-egress` for all apps that declare egress: apps on it could reach each other again.
- Connecting platform containers in compose files (an app's compose naming Traefik): Compose would recreate the platform's containers or need them in each app project; runtime connections are one place (`networks-sync`).
- A hostname-filtering egress proxy (Squid, or an allowlist in a forward proxy): real enforcement of the list, but a new component (ask first), a contract change (`HTTPS_PROXY`), and apps that ignore proxies. Left for production.
- Docker's default address pools for the networks: would work, but they can collide with the LAN's ranges, and an explicit range is easy to read in `docker network inspect`.

**Limits.** One Linux bridge and one /24 per app network and per egress network: the default range holds 256, enough for 20-30 apps with room; `networks-sync` says when it is full. Docker's isolation rules grow with each bridge (fine at this size). Traefik and ops get one interface per app. An app with `egress` can reach the LAN and the VM's published ports like any container with a gateway; other apps' egress addresses are cut by Docker's inter-bridge isolation. An app named `appdata-db` with Postgres would clash with that alias (it did on `annex-appdata` too; not reserved, as that changes the contract). An app whose first deploy failed has no `deploy.json`, so `networks-sync` with no app lists its network as an orphan instead of reconnecting it.

**Tests.** `vm/tests/test_networks.py` (needs, records, plan, subnet picker), `cli/tests/test_networks.py` (compose networks, Traefik label, flags, `rewire_compose`, egress validation), `test_selftest_builder.py` (`--egress`), `test_ops_names.py` (`migrate_networks`, network names). `scripts/test-platform.sh` "App isolation": no resolve or connect between two apps, controls to the gateway, appdata-db and ops `/healthz`, internal networks with exactly the expected members and a 10.213 subnet, no app on `annex-edge`/`annex-appdata`, `egress: []` can't reach 1.1.1.1:443 and an egress variant can, a forced gateway recreate cuts it and `networks-sync` restores it, removal removes the networks. `scripts/test-console.sh`: appdata-db's networks besides app networks. Not run here (VM): every suite.

**Prod:** per-app networks are the shape to keep (the plan's production list, item 7). In AWS: one security group per app (or ECS task) that may reach only the load balancer's, the gateway's, ops' and the database's groups, and egress through a filtering proxy or NAT with an allowlist that finally enforces the hostnames in `egress:`.

## D89. Log shipper: the cap before the parse, inserts only on the sink thread (22 Oct, hardening B6)
**What.**
- `ContainerHandler` and `JobOutput` now work in this order: line in the retention window, replay check (`Recent`, on a hash of the raw line: `logship.line_hash`, the same value `make_row` stores in `h`), **rate cap**, **parse**, row. The cap only needs `ns`, so a flood costs a hash and a counter per line instead of a JSON parse and the scrubbing regexes. The dropped-lines row is built as before (same text, same `fields`, same timestamp, one per flooded second, `flush_drops` for a flood that stops). Its `app` is now the container's own app (it used to be the app of the line that carried the report; only the gateway's cap differs, where that line could be any app's).
- `logstore.Sink.add` only enqueues (a full batch just wakes the sink thread). The sink thread (`log-sink`, B1's beat and gauge unchanged) makes every insert, once a second or at once when woken. A slow `INSERT` stalls the sink thread and nobody else; followers go on reading and the budgets of D86 bound the buffer, with the same `lost` counter.
- `Sink.flush(timeout=5)` (the follower's `before_save`) no longer inserts inline: it wakes the sink thread and waits until every row added **before the call** is stored. It returns **False** on timeout and as soon as an insert attempt fails, and then `Follower._save_exact` skips the cursor save, so the cursor stays on the last stored line and a restart replays from there.
- Cursor-safety invariant: rows are numbered as they are added (`added`); a successful insert sets `stored` to the number that was last in the batch it took; `flush` is True only when `stored >= added-at-call`. A row added while a batch is in flight is not covered by that batch. A failed batch goes back to the front of the buffer and `stored` does not move. Rows the budget trims are gone for good and counted (`lost`), so they no longer hold a flush back (as before: the cursor moves past them).
- A sink with no thread (`ctl logs-drain` makes its own) still inserts inline in `flush()`; `drain` flushes every 500 lines, as `add` used to.

**Why.** The cap sat after the parse, so a chatty container made ops parse and scrub every line it was about to drop. And `add` inserted inline once 500 rows were waiting, on the follower's own thread: a slow database stalled the reader of one container's log (and, through `before_save`, the same again at every cursor save), until Docker's pipe backed up into the container.

**Alternatives.**
- Cap before the replay check: a replay after a restart (the follower re-reads a margin) would count against the cap and could cut genuine lines of that second.
- A cap check that skips counting lines the parser would drop: needs the parse, which is the cost to avoid. Lines that parse to nothing (empty, the ops health-check lines) now count; they are a handful a minute, and a flood of noise is still a flood.
- `flush()` waiting without a timeout: a database outage would park every follower; with the timeout and the early False on a failed insert they come back, skip the save and read on.
- A bounded queue that blocks `add` when full: that is the stall again; the budget drops the oldest instead (D86).

**Not done.** `flush_drops` and the dropped rows still depend on the shipper thread's one-second tick, as before. A lost row (budget) is still not recovered from Docker's log.

**Tests.** `ops/tests/test_logship.py` (5 new): the parser is not called for lines over the cap (container and job output), the dropped-lines row, replays don't count, parser-dropped lines do count, a cursor is not saved while the sink's insert is in flight and is saved after. `ops/tests/test_logstore.py` (7 new): `add` never touches the database, `flush` waits for the thread and only the thread inserts, timeout, early False on a failed insert, rows added during an insert are not covered, budget-dropped rows don't block, threadless inline flush. Not run here (VM): `scripts/test-logs.sh` (section 5 restart without gap or duplicates, section 6 the cap) and the drain check.

**Prod:** a log pipeline with its own disk buffer (Vector or Fluent Bit) instead of in-process buffers.

## D90. Alert engine robustness: an outbox, saved timers, a monotonic clock, one front-door incident (22 Oct, hardening B5)
**What.** Five changes around the M1.3 engine (D39). The engine stays pure; everything new that touches the database or a clock is in `incidents.py` and the new `sender.py`. Revises D39 ("sends the messages" from the engine thread, the restart story), D43 (what a restart resets) and D73 (the front door's own subject). New tables only (`db/appdata/annex_ops.sql`; C3 turns them into a migration).
- **Sends off the engine thread.** The engine thread no longer composes or sends: `notify` adds a row to `annex_ops.outbox` (kind, subject, what the engine said in wall time) and wakes the `alert-sender` thread (registered with `threads`, period 90 s, gauge `alert-sender`: waiting, sent, failed). The sender reads the owner from the container's labels, the user directory and the last log lines (all three used to run on the engine thread: up to 10 s each for the log tail, SMTP and Slack), composes the message **once** into the row's `message` (so a retry sends the same text to the same people), and sends one email to everyone and one post per Slack channel. Each of those deliveries has its own state in the row, **saved the moment it is sent**, so a retry or a restart never repeats a delivered part. A failure that can pass (502/503: mail server or Slack unreachable; 429: rate limit; anything that isn't an `OpsError`) is retried after `send_backoff_s` (10 s, then 60 s); after `send_attempts` (3) the row is `failed`, logged (`sender: ... was not delivered: ...`) and listed on the console's Platform page ("Alert messages": the failed ones of the last 7 days and how many wait for a retry). A refusal (an address outside the allowed domains) is final for that delivery; a refused group email is split into one per address first, as `send_alert` did (D39). Messages of one subject go out in order: a "resolved" waits while its "opened" is being retried (`sender.due`, the `hook_events` pattern, D53). Retry times are kept in memory on the monotonic clock; after an ops restart every pending row is tried at once. Finished rows are kept 30 days. The console role gets `SELECT` on the outbox's columns without `message` and `action` (addresses, log lines); `last_error` can name a refused address, which the admins-only page shows. `incidents.send_alert` stays for the error scanner's emails (D67), which already run in their own thread.
- **Saved counters and timers.** `annex_ops.engine_state` (key, jsonb value) holds what Docker and the database can't give back after an ops restart: per container (`ctr:<id>`) `stopped_since`, `last_die` and the recent non-zero exits (`dies`), and `host:mem_low_since`. `Engine.export_state(offset)` returns them; `incidents.Manager.save_state` compares the export with the last one written after every pass (on the engine's clock, so the offset's jitter isn't a change; `Request` passes skip it) and upserts or deletes only what changed. At start `LoadState` puts them back before the open incidents are restored. A loaded container is `known=False`: no time rule fires for it until the reconcile pass reports it (its saved `stopped_since` then continues the grace period, its saved exits the crash count, its `last_die` the crash-loop quiet period), and `ReconcileDone` forgets it if it is gone. Rows this version can't read are ignored and deleted at the first write. The plan named the table `container_state` and listed `hooks_failing`; one table with keys covers the host timer too, and **`hooks_failing` stays memory-only**: the delivery worker re-reports every failing hook within 2 s of a restart from `hook_events`, and a restored `webhook` signal already clears itself if no report follows (D54). **Also memory-only, rebuilt at start:** running and health (the reconcile pass), open incidents and their reminders (their table, as before), the 5xx window and its "below since" clock (the Traefik follower replays from its cursor), maintenance windows (their table), the health checks' debounce (seeded from `health_checks`, D73). A Docker event missed while ops was down stays missed.
- **Time.** The engine's `now` is `time.monotonic()`. `incidents.Clock` gives the monotonic time and the offset to wall time once per pass; `to_engine_time` moves the wall times inputs carry onto the engine's clock (a Traefik line's timestamp, a backup's mtime and dump marker, a failing hook's start, a maintenance window's end), restored incidents are rebased the same way, and actions are converted back for storage and messages (an incident's `opened_at`, a signal's `since`, history timestamps; the opening time a message shows is the one stored when it opened). So a wall-clock step backwards (NTP) can't freeze a reminder, a grace period or a crash window, and one forwards can't fire them. **Saved timers can't be monotonic across a restart** (the monotonic clock starts again at boot, and differs between processes), so they are written in wall time and rebased on the new clock at load: a wall-clock step *while ops is down* shifts them by the step, which is the only place one still counts.
- **One incident per Traefik outage.** The front door's verdict is decided in the engine (`_front_door`): when it goes down while `platform:traefik` or `platform:authelia` is in trouble (a container not running, even within its 60 s grace period, or any active signal), its `down` signal joins that part's incident ("platform: traefik is down", detail "the front door isn't answering (...)") instead of opening `platform:front-door`. That covers both orders: Traefik stopped first (the usual case, since the checker needs two rounds) and the stop's grace period ending after the front door was confirmed down. Up clears `down` wherever it is (also one restored from before a restart); a second down verdict while it is raised somewhere changes nothing. A front door failing with Traefik and Authelia fine is still its own incident, and if Traefik fails after that, the two stay separate (they were noticed as two problems). Authelia is in the rule because its outage breaks the front door the same way; the plan named only Traefik.
- **Reconcile safety.** `watch_docker.Watcher.reconcile` sends `ReconcileDone` only after every `inspect` answered: a 404 means the container was destroyed during the pass (left out, as before), any other error (the proxy busy, a timeout) leaves the pass incomplete: the Seen ones are reported, `ReconcileDone` is not (it would forget the container and quietly close its incidents), and `run()` repeats the pass in 5 s. The health checker starts after the first pass either way (a verdict for a container not yet seen is ignored). The log shipper already deleted a follower's cursor only when it stopped the follower, and it stops one only on a `Destroy` input, which only Docker's `destroy` event produces (`ReconcileDone` never reaches it); `logship.py` is unchanged, and a test pins that down.
- **Incidents of apps removed while ops wasn't listening** (found by `test-alerts.sh` on the VM after the merge: two `unhealthy` incidents of `annex-selftest-job*`, removed while ops was unhealthy from a pool problem, stayed open across several restarts). A restored incident whose container ops never knew has no `Destroy` coming and nothing in `ReconcileDone`'s "known but not seen" set. Now a complete pass also closes every `app:<name>` and `job:<name>/...` incident whose app has no container left, the way a `Destroy` of its last container does: **quietly** (no "resolved" to the owner or admins), with the app's webhook, 5xx and hook state dropped. A redeployed app is never caught: the pass lists stopped containers too, and Compose creates the new container before it removes the old, so a recreated app always has one; an incident restored for an app whose container was recreated while ops was down stays open on the new container (tested). Platform subjects without a container (`front-door`, `disk`, `backup`, ...) are untouched. Tests: `test_engine.py` +4.

**Why.** Review findings (hardening plan, "What was found"): a slow mail server or Slack held the engine thread for up to 30 s per message with no retry, so one outage lost alerts and delayed every other input; an ops restart (every push) reset crash counts and grace periods; wall-clock arithmetic meant a clock step could freeze reminders; a Traefik outage opened two incidents (`platform:traefik` and `platform:front-door`); and a failed `inspect` during reconcile looked like a destroyed container.

**Alternatives.**
- One outbox row per delivery, composed on the engine thread: the composing (labels, directory, log tail) is the slow part, so it belongs to the sender; per-delivery state inside one row keeps the "opened before resolved" order per subject simple.
- Retrying in memory only: an ops restart (every push) would lose a message being retried, which is exactly when the mail server may be the thing being restarted too.
- Exactly-once sending: SMTP and Slack have no idempotency key; the window for a repeat is a crash between a server accepting a delivery and the one-row update that marks it, which is as small as it gets without one.
- Saving `running` too: the reconcile pass reads it from Docker, and a saved "stopped" for a container that came back while ops was down would raise a false alert at the first tick (hence `known=False`).
- Merging the front door into Traefik's subject permanently (one subject for both): a front door broken by a Traefik route or Authelia config while Traefik runs would then read "traefik is down"; the rule merges only while a part is visibly in trouble.
- Persisting monotonic times with the boot id: still wrong across a VM reboot, and wall time is what a person reading the row needs anyway.

**Not done.** The incident row and its outbox row are two writes, not one transaction: a crash between them loses that one message (the incident is open; its reminder follows). Messages owed while the database is down are lost as before (the incident write fails first). `test-alerts.sh` has no Traefik scenario: stopping Traefik cuts the suite's own path to Mailpit; the rule is unit-tested and is on the VM checklist below.

**Tests.** `ops/tests/test_engine.py` (+17): the front door joining Traefik's incident in both orders and Authelia's, staying separate when Traefik is fine, a restored merged signal clearing; crash count, grace period, crash-loop quiet period and low-memory time across a restart with a different clock origin, a saved container waiting for the reconcile pass and forgotten when gone, unreadable rows; and through `Manager` with a fake clock and fake tables: a wall-clock step back of an hour doesn't stop the reminder, wall times in inputs are rebased, a backup's age is wall-clock, state is saved on change only and in wall time, restore rebases and drops unreadable rows. `ops/tests/test_sender.py` (13): backoff, order per subject, what is retryable, composing, per-delivery state saved before the next one, a refused group split, retried then delivered (Slack not posted twice), given up after three, composed once, and a restart with a half-sent row (only the owed part goes out, the "resolved" behind it waits). `ops/tests/test_watch.py` (+6): a complete pass, a 404 left out, a failed inspect (500 or timeout) keeping the pass pending and an incident open, and only a real destroy reaching the shipper. `test_console_view.py` (+1): the Platform page's Alert messages. 386 unit tests in all (408 after the merge with main and the reconcile fix). Not run here (VM): `test-smoke.sh`, `test-alerts.sh` (Nejc's go-ahead), `test-host.sh`, `test-console.sh`.

**Prod:** the outbox is also where a real email provider's bounces and delivery receipts would be recorded; with a managed queue (SQS) and a provider with idempotency keys the sender becomes a consumer of that queue.

## D91. CSRF check in the runtime and the contract (22 Oct, hardening A4, Nejc: default on, opt-out env)
**What.**
- **Contract, core section "Cross-site requests"** (not a topic: every app gets it): a `POST`, `PUT`, `PATCH` or `DELETE` is refused with 403 when `Sec-Fetch-Site` is anything but `same-origin` or `none`, or when `Origin` is present and is not the app's own host. Requests with neither header (curl, another server, ops' webhook delivery, which sends no `Origin`: `hooks_verify.FORWARD_HEADERS` doesn't forward it) pass. `GET` never changes anything.
- **Runtime:** `csrf_violation(method, headers)` (pure, any framework) and `CsrfMiddleware` (ASGI) in `annex_runtime.py`; `csrfViolation(method, get)` and `csrfGuard` (Express) in `annex_runtime.js`. The app's own host is the `Host` header or the first `X-Forwarded-Host` (Traefik passes the original host); `Origin`'s `host:port` is compared with it, case-insensitively. `Origin: null` and a different port are refused. A refusal logs one `warn` line (`cross-site request refused`, with the reason).
- **On by default** in `python-web` (added before `request_log`, so a refusal still has a request id and an access line), `node-web`, both examples and the selftest fixture (which calls `csrf_violation` in its plain `http.server` handler first). `static` has no state; `python-job` has no HTTP.
- **Opt-out:** `env: {ANNEX_CSRF: "off"}` in `annex.yaml`, for an app that other sites' pages call on purpose (it must then authenticate those calls itself). The manifest allowed no `ANNEX_*` names under `env:`; `ANNEX_CSRF` joins `LOG_LEVEL` in `OVERRIDABLE_ENV` (`on`, `off`, `true`, `false`: YAML 1.1 reads an unquoted `off` as `false`, and the runtime treats `off`, `false`, `0` and `no` as off). The contract's injected-environment table lists it.

**Why.** One session cookie serves every app subdomain (hardening plan, "What was found"), so a page of app A (or any website) can make a signed-in user's browser send a state-changing request to app B with the user's identity; SameSite doesn't help between sibling subdomains. Browsers state where a request comes from; the check costs one line in an app. Since D88 apps can't call each other directly, so the only cross-app request is a browser's.

**Alternatives.**
- A per-request CSRF token (synchronizer or double-submit cookie): needs session state and template changes in every form and fetch; apps written by agents would forget it. Fetch metadata is stateless.
- The check in Traefik (a forward-auth or plugin step in the front door): covers every stack including "bring your own", but it is a new component or plugin (ask first) and apps that must be called cross-site would need a per-app switch in labels. Left for production.
- `Origin` only: older browsers and some same-origin `POST`s omit it; `Sec-Fetch-Site` is the stronger signal, `Origin` covers browsers without it.
- Requiring one of the two headers (refusing when both are absent): would break curl, `annex run`-style tests and ops' webhook delivery. A cross-site browser request always carries at least one of them, so allowing "neither" is safe.
- Opt-out as a manifest field instead of `env:`: a contract schema change for one switch; the env name needs no CLI change beyond the allowlist.

**Limits.** An app in a stack without the runtime (the "bring your own stack" topic) must write the check; the contract says so. Browsers that send neither header (very old) are not protected. `Sec-Fetch-Site: same-site` is refused on purpose: sibling apps are the threat. The check can't protect an app that sets `ANNEX_CSRF: "off"`. It does not replace the per-app cookie question (production item 13). A cross-site `GET` that changes state is out of scope.

**Tests.** `runtime/tests/test_csrf.py` and `csrf.test.mjs` (both runtimes: headerless, safe methods, each `Sec-Fetch-Site` value, own-host and sibling `Origin`, port, `null`, forwarded host, webhook-delivery headers, opt-out values, the middleware answering 403 or passing); `cli/tests/test_manifest_env.py` (`ANNEX_CSRF` values, other `ANNEX_` names still refused); `cli/tests/test_contract.py` (the section is core). `scripts/test-apps.sh` "Cross-site requests": through the front door with a login, a foreign `Origin` plus `cross-site`, a foreign `Origin` alone and `same-site` get 403, same-origin and headerless POSTs pass (404 from a probe path), a cross-site GET is untouched. Not run here (VM): `test-apps.sh`.

**Prod:** per-app session cookies (a host-only cookie per app) or an origin check in the front door, once the IdP is decided (production item 13); this runtime check stays as the second layer.

## D92. Deploy lock and pending release record (22 Oct, hardening C1)
**What.**
- **A lock per app.** `vm/annex_vm.py deploy-begin <app> --actor <who>` takes `/srv/annex/deploy/<app>/.lock` (a directory: `mkdir` is atomic) with `owner.json` inside: actor, a random token (no pid: the holder is on another machine), started_at, step, release. A short `flock` on `deploy/<app>/.lock.guard` makes "read the lock, then take it over or update it" one step. A lock older than **30 minutes** is taken over by the next deploy, which says from whom; a younger one refuses with the holder, release, step and age. `deploy-step <app> <token> <step>` records the step; `deploy-end <app> <token> <n> live|failed` (final line on stdin) and `deploy-step` refuse a token that doesn't hold the lock (the lock was taken over: the newer deploy reconciled this one's release).
- **A pending line.** `deploy-begin` numbers the release (max in `releases.jsonl` + 1) and appends `{"release": n, "result": "pending", …}` with the CLI's line (manifest, who, when, via, git; a rollback's target image) and the `deploy.json` the release will have if it goes live. `deploy-end` rewrites that line with the outcome (temp file, fsync, rename; the file is small) and releases the lock. Only the VM writes `releases.jsonl` now (`_append_release` is gone).
- **Exactly one database row per release.** `deploy-end` (and reconcile) copy the final line to `annex_ops.releases` and its audit row themselves, best effort as before. `release_row` returns nothing for a pending line, so neither `release-record` nor `release-backfill` ever stores one; the final line keeps the pending line's `deployed_at`, so the primary key `(app, deployed_at, release)` sees one release.
- **The CLI.** `deploy` and `rollback` call `deploy-begin` right after validation (manifest, views; a rollback's target), through a context manager `_Lock`; every exit without an outcome (an exception, Ctrl-C) ends the release as `failed` with `broke off at <step>: <first line of the error>` and `interrupted_at`, with a 60 s timeout, and never hides the original error. Steps: `upload`, `build`, `snapshot`, `provision`, `switch`, `gate` (from `_activate`), `back-provision`/`back-switch`/`back-gate` while a failed gate switches back, `restore` for `--with-data`, `finish`. `_cleanup` runs under the lock, before `deploy-end` (another deploy's fresh image must not be pruned), keeps the new image explicitly and only warns if it fails. `remote.py` turns `subprocess.TimeoutExpired` into an `AnnexError` naming the step and the 30-minute rule.
- **Order: begin before the upload and the build** (the plan suggested build, snapshot, begin). The release number names the image tag `r<n>`, and the source upload and the build share `deploy/<app>/src` and that tag with any other deploy of the app: numbering after the build would need a temporary tag and still leave the upload racing. So the lock covers upload, build, snapshot, provision (with A5's `networks-sync`), switch, gate and end. Cost: a build failure is now a `failed` release (with its reason; it consumed a number), where before it left no line. Numbers are never reused, which was the point. A rollback checks its target before locking (a typo leaves no release) and re-checks after locking that the live release didn't change in between (if it did, it fails and says so).
- **Reconcile** (`reconcile` in `deploy-begin`; also `annex_vm.py deploy-reconcile <app> [--break]` by hand). A pending line from an earlier run is reported (`r5 of <app> was interrupted at gate (started by …); …`, the step from the stale lock) and settled by what Docker says, not guessed: the app's container runs the pending image and is healthy → `live`, its stored `deploy.json` is written, Ofelia restarted if a schedule changed. For a web app "healthy" is the gate's own probe (the manifest's health check through Traefik), not Docker's healthcheck (the fixture's `--broken-health` variant has a healthy Docker check and a 404 gate); a container still `starting` gets up to 60 s. Anything else → `failed`, and **nothing is switched or removed**: if the dead deploy got past `compose up`, the old container is gone already, and removing the new one leaves the app down just the same while hiding its logs. The message says whether a healthy container is running (which release's image) and, if none is, to run `annex rollback <app> --to <live release>`; `annex rollback` now accepts the live release as a target exactly when the app's container doesn't run its image.
- **A failed gate re-provisions the previous release's manifest** (grants, secrets, webhooks, networks) before switching back, as before C1; the deploy's release line is the only one written for it.
- **Test fixture:** `SELFTEST_SLOW_HEALTH=N` makes `/healthz` answer 503 for N seconds, so a deploy sits in its gate long enough to be killed.

**Why.** Two deploys of one app computed the same `r<n>`, and an SSH drop between `compose up` and the release record left a running container with no record while the next deploy reused the tag (hardening plan, "What was found"). With several builders and agents deploying before the Goat Arcade demo, both happen.

**Alternatives.**
- `flock` alone, held for the whole deploy: dies with the SSH session that holds it, which is right for a crash but wrong for the deploy's many separate SSH calls; it can't span them.
- A lock file with the CLI's pid: the pid is on the Mac, meaningless on the VM, and two Macs deploy.
- Auto-switching back to the previous release on reconcile: a decision made by a different person's deploy, possibly over a release that just needs more time; a human decides with one command.
- Removing the unhealthy container on reconcile (the plan's wording): see above; kept the container and the logs.
- Recording build failures as no release (dropping the pending line): numbers would be reused, which is what C1 removes.

**Limits.** 30 minutes is long for a deploy whose terminal died; `ANNEX_DEPLOY_LOCK_STALE=0` or `deploy-reconcile --break` is the escape hatch for someone who knows the holder is dead (docs/operations.md). `annex remove` doesn't take the lock (it deletes the deploy folder, lock included). A deploy killed during the build leaves the remote `docker build` running until it ends on its own. A reconcile-to-live doesn't run `_cleanup` (the next deploy does).

**Tests.** `vm/tests/test_deploy_lock.py` (29): lock, refusal naming the holder, stale takeover, `stale_after=0`, an owner-less lock dir, token checks on step and end, a taken-over deploy that can't end, pending rewrite and numbering, no temp files left, no pending line in the database rows, every reconcile decision (healthy, job app without healthcheck, starting then healthy, unhealthy, previous image running, no container, nothing to roll back to, a pending line without a lock, a rollback's image), `container_state` judging a web app by the gate's probe. `cli/tests/test_deploy_lock.py` (14): call order (begin before upload, end last), what begin is given, failed on an exception, a build failure, Ctrl-C at the gate, an unreachable VM at the end not hiding the error, a held lock stopping before any change, a failed gate ending once with `rolled_back_to`, reconcile notes shown and returned, rollback with the target's image, a bad target refused before locking, rollback failure, the live release as a target, the timeout message. `scripts/test-rollback.sh` 4-6 (not run here: VM): two concurrent deploys (one wins, the other names the winner, one release added, no lock left); a deploy killed with SIGKILL in its gate (pending, lock held, a deploy refused naming the step, the next deploy takes over, reports and records it live); the same with a broken version (recorded failed, "No healthy container", `annex rollback --to <live>` repairs).

**Prod:** the lock and the pending record live on in the deploy API, which replaces the shared SSH key (the plan's production list, item 1); the API owns the lock, the pending record, provisioning and the switch.

## D93. Numbered schema migrations with a version table (22 Oct, hardening C3)
**What.** `db/appdata/annex_ops.sql` is gone. `db/appdata/bootstrap.sql` keeps what must run outside a transaction and on every push: `REVOKE CONNECT ... template1`, the roles and their passwords (read with `\getenv`, D80), `CREATE DATABASE annex_ops`. The schema is `db/appdata/migrations/`: `001_base.sql` (the old file as it was before the hardening tables, minus the roles), `002_usage_rollup_logs_index.sql` (B3, D82: `usage_rollup_apps`, `logs_container_ts`, the console's grant), `003_db_connections.sql` (B4, D84), `004_outbox_engine_state.sql` (B5, D90). `vm/migrate.py` (stdlib, on the VM, called by `push.sh` after the bootstrap) lists the files, reads `annex_ops.schema_version(version text primary key, applied_at)`, and applies each missing file with `psql --single-transaction -v ON_ERROR_STOP=1`, as `SET ROLE annex_ops`, with the `INSERT INTO schema_version` in the same transaction, so a file is applied and recorded, or not at all. It stops at the first failure and names the file. A file that is missing but sorts below an applied one is refused (renumber it). It needs no password: psql runs as `postgres` inside the container, and the migrations contain none.
- **The switch-over.** On the live VM `schema_version` is empty at first, so the first push applies 001 to 004 in order. All are idempotent and the VM already has everything, so only the grants move: 001 resets `annex_console`'s grants (`REVOKE ALL ON ALL TABLES`) and gives the old set, and 002 to 004 add theirs, each in its own transaction a moment apart. The console may see a permission error in that window if it reads in it. The next push is a no-op.
- **Grants live in the migration that creates the object.** The `usage_rollup_apps` grant moved out of 001's grant list into 002; the others were already separate statements.
- **`usage_apps` stays.** The plan said to drop the old view in C3. B3's follow-up made `usage.usage_rows()` fall back to the view for apps the rollup has not stored yet and `refresh_rollup()` reads it, so it is the rollup's source and is kept; its comment says so.
- **Alternatives.** (1) A migration tool (Alembic, Flyway, sqitch): a component outside the brief's stack for a dozen files. (2) Keeping the roles and `CREATE DATABASE` inside 001: `CREATE DATABASE` can't run in a transaction and the passwords have to follow `master.env` (a rotated one must reach the roles), so they stay a rerunnable bootstrap. (3) Running the runner on the Mac: it would need the database through SSH; on the VM it is one `docker compose exec`. (4) A checksum per file to catch an edited applied file: not done; the rule is in CLAUDE.md and `operations.md`, and review sees the diff.
- **Costs.** An applied file can't be repaired in place: a mistake is fixed by the next file. `001` can't be tidied. `CREATE INDEX CONCURRENTLY` is not possible (a test in `vm/tests/test_migrate.py` checks no migration uses it, `\c` or `\getenv`); on a big table that matters, and the step then needs its own runner mode.

**Tests.** `vm/tests/test_migrate.py` (7): order, skipping the applied, a no-op when all are applied, a gap below the newest applied, unknown applied versions ignored, bad names and a duplicate number, and the repo's own files (names, no `CONCURRENTLY`, `\c`, `\getenv`). On the VM: `push.sh` twice (the second applies nothing), a failing scratch migration stops the push with its name (`docs/operations.md`, "Database migrations").

**Prod:** the same mechanism against RDS, run as a separate deploy step with `migrate --list` (a dry run) before a platform upgrade, a migration role that is not the superuser, and expand-then-contract changes for anything the running version still reads.

## D95. Build limits: free disk, image size, pids_limit, cleanup warnings (22 Oct, hardening C5)
**What.**
- **Free disk before a build.** `_build` first runs `df -PB1 /srv/annex` on the VM and refuses with under **3 GB** free. The message says how much is free, that nothing was built, and names `docker system df` (what takes the space) and `docker image prune -a` / `docker builder prune` (to free it) for the Annex owner. A `df` that returns nothing numeric does not block a deploy.
- **Image size after the build.** `docker image inspect -f '{{.Size}}'`; above **2048 MB** the image is `rmi`'d and the deploy refused, naming the app, the size and the limit, with the usual fixes (slim base, no caches, no data files in the source folder). The check runs before the root-user and label checks.
- **Overridable.** `ANNEX_BUILD_MIN_FREE_GB` and `ANNEX_IMAGE_MAX_MB`: the CLI's environment first (the test sets a low cap), then the platform `.env` (`r.settings`, from `.env` via `render.py`; empty means the default), then the defaults. A value that isn't a non-negative number is refused naming the setting. The verdicts are the pure `build_space_verdict` and `image_size_verdict`.
- **`pids_limit: 256`** on every app container in `compose_for`.
- **Cleanup warnings.** C1 already turned a failed `_cleanup` into a progress line; it now also **returns** the warning, which goes into the deploy's (and a rollback's) `warnings` list, so an agent using the MCP server sees it and the disk filling up is not silent.
- Both refusals happen under C1's lock, so they end the release as `failed` with the message as its error; the `AnnexError` text reaches the CLI and MCP unchanged (the same path as a Dockerfile build failure, which C1's tests cover).

**Why.** A build on a nearly full disk fails halfway and leaves layers behind; an agent's Dockerfile can pull in several GB (or an app can `COPY` a data folder) and fill the VM's disk, which stops Postgres, the logs and every other app. A fork bomb in one app should hit its own limit, not the host's process table.

**Alternatives.**
- Platform setting only: the test would have to rewrite the VM's `.env` and push; the CLI environment override makes the test fast and leaves the VM untouched.
- Cap by build context size: misses what the Dockerfile downloads. The image size is what costs disk.
- Check free space again after the build: the cap on the image plus the pre-check already bound it; the next deploy's pre-check catches the rest.
- `docker build --memory`: BuildKit ignores it, so no build-time memory limit is claimed.

**Not done.** No build-time CPU or memory limit (needs a builder with limits). Build cache layers of a refused build stay until the next `builder prune` in `_prune` (1.5 GB cap). The size check is on the final image, so a build that fills the disk and then fails is only stopped by the free-space pre-check.

A second deploy or rollback is refused naming the holder: "demo is being deployed or rolled back by kim@mac (r5, at step build, started …, 40 s ago; pid 12345 on the VM). Wait for it to finish, then try again; it runs on the VM, so it finishes even if its terminal closed". `deploy-state <app>` answers `{running, current}` with a shared non-blocking probe (the lock's taker retries for a second, so a probe never makes a deploy fail); `annex status` shows it as its `deploy` line. `deploy-reconcile <app>` takes the lock non-blocking and refuses while a run holds it, naming its pid ("wait, or `kill <pid>` and run this again"); `--break` is gone.
- **Begin, under the lock** (`settle`, `open_release`): write `current.json`; remove a `deploy/<app>/.lock/` directory left by a pre-D101 CLI, with a note naming its `owner.json`; reconcile a pending line by D92's rules unchanged (healthy and running the pending image: `live`, else `failed`, nothing switched), with the step from the previous `current.json` (or the old `owner.json`) when its release is the pending one, else "an unknown step"; then number the release and append the pending line. A rollback resolves its target between the two, under the lock, so D92's "the live release changed while this rollback was starting" check is gone: it can't happen.
- **Detaching** (Nejc: Ctrl-C and a dropped session detach, they don't cancel). The process ignores SIGHUP, takes the lock, settles, numbers, and receives the source (`tarfile` stream, `filter="data"`, into `src.new`, then swapped in; a truncated upload is a `failed` release "broke off at upload"). Then it forks: the worker calls `setsid()` (out of the SSH session's process group, so a pty hangup can't reach it), ignores SIGHUP and SIGPIPE, points stdin at `/dev/null` and stdout/stderr at `deploy/<app>/run.err` (so the SSH session's pipes are closed in it and the session can end without it), writes its pid to `current.json`, runs the rest and writes every protocol line to `deploy/<app>/run.log` (the previous run's is `run.log.1`). SIGTERM is an exception: the release is recorded `failed` at the step it reached ("broke off at gate: ..."), as `_Lock.__exit__` did. The parent closes its copy of the lock descriptor, follows `run.log` to the caller with the heartbeat, and stops at the final line; if its caller has gone (a broken pipe) it exits quietly, and if the worker exits without a final line it says so ("the deploy process on the VM ended at the gate step without a result (killed?); r5 of demo is pending: the next deploy or rollback, or `annex_vm.py deploy-reconcile demo` on the VM, settles it"). On the Mac, a call that ends without a final line after the run started, goes silent for 180 s (a dead connection: the heartbeat is every 30 s), or is interrupted (Ctrl-C) raises: "The connection to the VM dropped at the gate step (...); the deploy continues on the VM. `annex status demo` shows its step and `annex releases demo` its outcome." Before the upload finished the message says the deploy stopped before it was under way.
- **Other details.** The compose file is written as JSON (valid YAML; Compose and `migrate-networks`' `yaml.safe_load` read it), so the deploy path needs no PyYAML. The build's full output goes to `deploy/<app>/build.log` (the last 40 lines into the error, as before); free disk is `shutil.disk_usage`. `ANNEX_HEALTH_TIMEOUT`, `ANNEX_IMAGE_MAX_MB` and `ANNEX_BUILD_MIN_FREE_GB` from the CLI's environment travel in the meta's `overrides` (only those three keys; the tests set them), before the platform `.env` and the defaults. The drain's warning names `docker logs annex-ops-1` on the VM. A `record_release_db` warning becomes a note line.
- **Revises D17** (how the CLI deploys: it now validates, tars and makes one call; the steps run on the VM), **D30** (the gate's wording: the gate is polled from the VM-side process, and `ANNEX_HEALTH_TIMEOUT` is the CLI's environment passed in the meta, not read by the code that polls), **D64** (the drain before Compose replaces a container is run by the same deploy process; `secret set`, `remove` and `migrate-networks` still drain from the CLI until V2) and **D92** (the lock directory, token, 30-minute rule, takeover, `deploy-step`/`deploy-end` and `--break` are replaced by the flock and `current.json`; the pending line, the reconcile rules, the step names and "a build failure is a numbered failed release" stay).

**Deviations from the reviewed design** (`.build/plans/v1-spike.md`).
- **The route probe's port comes from `ANNEX_BIND_HTTPS` / `ANNEX_BIND_HTTP`** (their port part, L2's settings), falling back to 443 / 80, **not from `ANNEX_PUBLIC_PORT`**: on the VM `ANNEX_PUBLIC_PORT` is 8443, the port of the Mac's browser tunnel (D6), while Traefik binds 443; probing 8443 on the VM would have waited 30 s for nothing on every deploy. In L2's local mode both name the same loopback port, so local mode works unchanged. The URL carries the port (`https://<host>:<port>/` with `--resolve <host>:<port>:127.0.0.1`).
- `deploy-step` and `deploy-end` answer with the same update-your-checkout error as `deploy-begin` (harmless; an old CLI only reaches them if a deploy-begin had succeeded).
- The Mac-side message for a call that never started (no line at all, e.g. a platform from before D101 that has no `deploy` command) is the VM's own error, with "run scripts/push.sh first" when it is argparse's "invalid choice"; the detach message is only for a run that started.
- `_provision_args`, `_network_args`, `rewire_compose` and `_drain` stay in `ops.py` until V2 (`secret set`, `remove`, `migrate-networks` use them), as the design said; `Remote.step` and `timeout_message`'s 30-minute text are dead and go in V4 (L2 edits `remote.py` in parallel, so V1 only added `_argv` and `call`).

**Why.** The deploy was driven from the wrong side of the wire (control-plane plan): everything D92 added existed to survive a dozen separate SSH sessions, a laptop that slept during the gate killed the deploy, and the compose file an app ran with depended on the CLI version of whoever last deployed. One VM-side process makes the lock die exactly with the deploy, makes the compose file the platform's, and gives a deploy API (production item 1) one thing to wrap.

**Alternatives.**
- **Ctrl-C cancels** (a `deploy-cancel` that sends SIGTERM, turned into a failed release at the next step): Nejc chose detach; SIGTERM by hand (`kill <pid>` on the VM) does the same today, and `deploy-cancel` is the production item if builders ask for it.
- **Only ignoring SIGHUP and SIGPIPE, no fork:** a pty session's hangup reaches the whole process group, and the SSH session can't close while the process holds its pipes. **`systemd-run`** to detach: a system change (CLAUDE.md). **A double fork:** the parent could no longer `waitpid` the worker to tell "it died" from "it is slow".
- **Keeping D92's lock directory with the process's pid in it:** the flock is the same fact without a stale rule, and the kernel releases it.
- **Writing the compose file with PyYAML on the VM:** Ubuntu's `python3-yaml` is there, but JSON needs nothing and is valid YAML.
- **Resolving the rollback target on the Mac** (the plan's wording): racy against a deploy that finishes in between; under the lock it can't change.

**Limits.** logind's `KillUserProcesses=yes` would kill the worker with the session's cgroup (checked on the VM: not set). A `scripts/push.sh` during a deploy replaces the bundle under it (the worker has its Python loaded, but `annex_vm.py` subprocesses and the platform containers can change): documented as "no push during a deploy". `secret set` and `remove` still don't take the lock (V2); `remove`'s `rmtree(deploy/<app>)` would unlink `.lock.guard` under a running deploy, so V2 must take the flock in both. The meta's `overrides` let any caller lift the build limits for one deploy, as the CLI's environment did. `annex_vm.py`'s other commands are still called one SSH session each.

## D102. Secret set, remove, migrate-networks and run on the VM (22 Oct, control-plane V2)
**What.**
- **One call each** (`vm/annex_apps.py`, called by `annex_vm.py`; stdlib, PyYAML only to read an old compose file). `annex secret set` is `annex_vm.py secret-set <app> --actor <who> --recreate` with the `KEY=VALUE` lines on stdin (never argv, as before); `annex remove` is `annex_vm.py remove <app> --actor <who> [--keep-data]`; `annex migrate-networks` is `annex_vm.py migrate-networks <app> --actor <who> [--egress]`. The CLI functions in `ops.py` (`secret_set`, `remove`, `migrate_networks`) are validation plus one `Remote.call`; result dicts, `main.py`'s output and the MCP are unchanged (`secret_set`/`remove` gained an optional `progress` argument nothing passes yet). `secret-set` without `--recreate` keeps its old one-line answer (the CLI no longer uses it). What moved: the secret merge and audit (`annex_vm.store_secrets`, `parse_secret_lines`), `deprovision()` (the command wraps it), `rewire_compose` (into `annex_deploy`, raising `vm.Fail`, tests in `vm/tests/test_apps.py`), the drain (`annex_deploy.drain`, the same function a deploy uses: D64's "the same process" now covers all four container-replacing operations). `ops._provision_args`, `_network_args`, `_drain`, `rewire_compose`, `_compose_networks`, `OFELIA` and the `yaml` import are gone: the VM calls `provision` and `sync_app` as functions, from `deploy.json`.
- **The lock.** `Op` (annex_apps) takes `hold_app_lock` (D101's flock on `deploy/<app>/.lock.guard`) before it changes anything and holds it to the end of the process; it writes `current.json` like a deploy (`kind` = the command, actor, step, result at the end). A held lock is the same refusal as for deploys, naming the holder; the wording follows the holder's `kind` ("is having a secret set by", "is being removed by", "is being moved onto its own network by", default "is being deployed or rolled back by"), and for a refused `secret set` the value is not stored (the lock comes before the write). Steps in the protocol lines: `store`, `provision`, `switch` (secret set); `drain`, `down`, `deprovision`, `scheduler` (remove); `networks`, `switch` (migrate-networks). The process ignores SIGHUP and SIGPIPE and treats a failed stdout write as "the caller left": a dropped session never leaves an app half-removed. There is no detaching fork and no `run.log` (these take seconds). SIGTERM ends the run with an `ok: false` line at its step. A drop is reported by `Remote.call` as "the secret set / removal / network migration continues on the VM and finishes there" (no pointer to `annex releases`: there is no release).
- **`current.json` and a dead deploy.** A deploy that died leaves its step in `current.json`, which the next deploy reads to say where it stopped (D101). A secret set or removal in between would overwrite it, so a run that finds an unfinished deploy or rollback record keeps it under `"interrupted"` in its own `current.json`, and `dead_step` looks there too.
- **`remove` and `.lock.guard`** (the open point D101 left). Decided: **the lock file is never unlinked.** `remove` takes the lock first; `deprovision` (also when run by hand) now deletes everything under `deploy/<app>/` **except `.lock.guard`** (`clear_deploy_dir`), and the run writes its final `current.json` there. Unlinking the guard after releasing the lock is racy: a deploy that opened the old file and waits for the flock would take it on the unlinked inode while the next deploy creates a new file and locks that too, so two holders. Unlinking it while holding the lock has the same hole. A check "is this still the file at the path" after `flock` would close it but belongs in every taker; an empty file per removed app name is the cheaper fact, and a redeploy of the name reuses it. Alternative also considered: keep the lock files in a separate directory (`/srv/annex/locks/<app>`), which also survives, but moves D101's file and its documentation for the same result.
- **`run`** (`annex_vm.py run-job <app> <job>`). The command comes from the app's `deploy.json` on the VM, the job name is only a key (nothing is built into a shell line; the job name and the command go to `docker exec` as arguments). It takes **no lock**: it replaces nothing, and a long job must not block deploys (a deploy replacing the container ends the job, as before). Output protocol: the job's stdout and stderr, merged as the old `2>&1` did, go to the process's own stdout as they are written; the last line of the process's **stderr** is `{"ok": true, "exit_code": n, "seconds": s}` (or `{"ok": false, "error": ...}` for no such app or job, with the same texts as before); the exit code is the job's (1 for a refusal). The CLI collects it with `Remote.run` and builds the same `{app, job, exit_code, seconds, output}` (last 8000 characters). **Deviation from the plan's wording** ("stays a `Remote.stream`"): `run_job` was never a `stream` (that is `logs -f`, straight to the terminal); the MCP and `annex run` need the output in the result dict, so it stays captured. The VM side does stream (the output isn't buffered by the process), so `ssh annex annex_vm.py run-job ...` by hand shows it live. The trailer is on stderr so the job's own output can never be mistaken for it.

**Why.** The same reason as D101: the CLI replaced containers over several SSH sessions, so a `secret set` could interleave with a deploy (the secret written between a deploy's provision and its switch; a removal under a running deploy, D92's "Limits"), and what ran depended on the copy of the CLI that asked.

**Alternatives.** Running `remove` without a lock (as before; a deploy then recreates the app being removed). Detaching these three like a deploy (a fork and `run.log`): they take seconds and have nothing to reconcile, and a lock that dies with the process is the same either way. Taking the lock in `run-job` (a job and a `secret set` would then serialize, but so would a job and every deploy).

**Limits.** A `remove` that fails after `compose down` and before `deprovision` leaves a stopped app with its data (rerun it); the lock is free again. `deprovision` by hand while a deploy runs now keeps the guard and deletes the rest of the deploy's folder under it: don't. An old CLI calling `secret-set` without `--recreate` or `deprovision` directly still works but takes no lock.

**Tests.** `vm/tests/test_apps.py` (secret set: the order store, provision from `deploy.json`, drain, compose up; the value on no command line and not in the output; not-yet-deployed stores only; undeclared-key warning; a held lock refuses naming the holder and stores nothing; the wording by kind; a failed recreate says why and frees the lock; bad lines refused before the lock; the old one-line answer. Remove: the order drain, down, rmi, deprovision, scheduler restart; keep-data; no such app; a container with no record; a failed down stops before deprovision; a held lock removes nothing; the guard file keeps its inode and the lock is free after; `clear_deploy_dir` under a held lock keeps one holder on one file; the dead deploy's step survives a secret set. Migrate-networks: rewire, sync flags, backup kept once and egress recorded, drain before the recreate, no compose file, held lock, a failed recreate. `rewire_compose` (moved from `cli/tests/test_networks.py`). Run: the command from `deploy.json`, inherited stdout and merged stderr, the exit code and trailer, unknown job and app, no lock). `cli/tests/test_ops_vm_calls.py` (one call each and what is sent, the value on stdin only, `run`'s trailer and refusals, the detach wording). `scripts/test-rollback.sh` scenario 5 gained a refused `secret set` and `remove` during a deploy's gate. `test-notify.sh`, `test-apps.sh`, `test-jobs.sh` and `test-platform.sh` need no change (they call the same CLI commands); not run here.

## D103. Version coupling and one manifest module (22 Oct, control-plane V3)
**What.** The VM decides whether a CLI may deploy, and both sides validate `annex.yaml` with the same file.
- **One manifest module.** `cli/src/annex_cli/manifest.py` is the only copy of the rules. `scripts/render.py` copies it (and `logcheck.py`) into the bundle as `vm/annex_manifest.py` and `vm/annex_logcheck.py`; they are generated, never committed under `vm/` (`vm/tests/test_versions.py` fails if one appears or if `render.py` stops copying it). In the checkout, `vm/annex_deploy.py` falls back to the CLI's file, so the unit tests run the real rules. PyYAML on the VM is Ubuntu's `python3-yaml` (`load()` imports `yaml` inside the function); a missing module is reported as a platform problem, not as the builder's.
- **Re-validation.** After the upload is unpacked and before the build, `annex_deploy.revalidate_source` runs `annex_manifest.load` on `src/` and refuses with the module's own problem lines ("annex.yaml in the upload is not valid on the VM"), and it must equal the manifest in the meta: a difference refuses with "the manifest in the upload doesn't match what the CLI validated (differs in: ...)". The release is then recorded as failed at the upload step with that text; nothing is built. The CLI's local validation stays for fast failure; the VM's is the one that counts (a modified CLI can't skip a rule).
- **The comparison rule** (`annex_deploy.check_versions`, pure). The meta carries `cli` = `{commit, dirty, contract_version}` (`git rev-parse HEAD` of the checkout the CLI runs from, `unknown` outside a repository; dirty = uncommitted changes). `render.py` adds `contract=<ANNEX_CONTRACT_VERSION>` to the bundle's `VERSION`. A CLI whose **contract version is newer** than the platform's is refused before any release line: "push the platform first: scripts/push.sh". An **older** one deploys, with a note in the progress lines and the result's warnings ("your CLI is older than the platform (contract v2 < v3): update your checkout"). Equal passes. A missing number on either side (a platform pushed before the stamp, a CLI before this change) checks nothing; a CLI that sends no `cli` at all gets a note. Commits are only named in the messages: two checkouts differ in commits all the time, and the contract version is what the apps are written against.
- **Where it shows.** The release line carries `cli` = `{commit, dirty}`; `annex status` prints `cli` for the live release; `annex releases --json` has it; the console's Releases tab has a CLI column and the Config tab a "made with CLI commit" line. `annex_ops.releases` gets a nullable `cli jsonb` column (migration `005_releases_cli.sql`; the existing `manifest` and `git` columns carry other things); `release_row` and `releases_sql` copy it, older rows stay empty.
- **MCP.** A refusal is the usual `{"ok": false}`, which `Remote.call` turns into `AnnexError` and the MCP server's `_call` into a `ToolError` with the same text (unchanged code, checked).

**Alternatives.**
- **Refuse on any commit mismatch:** every unrelated commit would block deploys; the contract version is the thing that changes what an app may do.
- **Refuse an older CLI too:** a CLI one contract version behind still produces valid apps for the platform (the contract is additive so far); a note is enough, and the platform's push is not the builder's job.
- **A committed copy of `manifest.py` in `vm/` kept in sync by a script:** a second copy that can drift; generated at render time there is none to check.
- **Validating on the VM only:** an agent would wait for an upload and a lock to read a typo; the local check stays.
- **Putting `cli` in the `git` column:** that is the app folder's commit.

**Tests.** `vm/tests/test_versions.py` (19): the comparison (equal, newer, older, dirty, unknown numbers, no report), `platform/VERSION` parsing, a deploy refused before any release line, an older CLI's note, `cli` in the release line, an invalid, a missing and a mismatched `annex.yaml`, and the one-source checks. `cli/tests/test_cli_version.py` (4), `ops/tests/test_console_view.py` (2 added), `vm/tests/test_releases.py` (2 added). The existing deploy tests upload an `annex.yaml` now (`deploy_fakes.yaml_for`).

## D106. Goat Arcade after hardening: the FDW connection budget, the isolation probe, the client's secrets, refreshing a changed table (23 Oct)
**What.** Four adjustments found by checking the finished `docs/plans/democlient.md` against hardening (D79–D97) and control-plane (D98–D105), done before the Goat Arcade demo plan starts (its §5 lists them).

**Alternatives.** An array of nicknames in `tournaments` (changes a view apps already use, and a column of arrays is awkward to filter); the `player_id` as the key (the id is not exposed anywhere else, nickname is the key builders use); including the player's name and e-mail for the desk (personal data, not needed for the check).

## D111. Kanboard, self-hosted as an Annex app (23 Oct, GA.5; Nejc: Kanboard's own API token, no members job)
**What.** `examples/goat-arcade/kanboard/` runs Kanboard v1.2.54, the technicians' repair board, as an ordinary Annex app owned by `sam`, behind the same login. Nothing in the platform changed for it.
- **The image** is the official `kanboard/kanboard:v1.2.54`, pinned by its multi-arch index digest. v1.2.55 and v1.2.56 were under two weeks old.
  - The Dockerfile copies the release into a fresh image (`FROM scratch`, `COPY --from=upstream / /`). That keeps Kanboard, PHP and nginx as released, and drops what Annex can't use: the upstream `VOLUME` lines (anonymous volumes outside `/data` and the backups), the root s6 entrypoint (it writes into `/etc`) and the port-80 health check.
  - The image is 127 MB, and the app runs at about 28 MiB of 256 MiB.
- **Contract fit:**
  - `USER 10001`. Our own entrypoint starts php-fpm and nginx and exits when either stops.
  - Every runtime write goes to `/tmp` (pids, sockets, temp dirs, the rendered nginx config, uploads in progress). Kanboard's data, files, cache and plugins go to `/data`.
  - nginx listens on `$PORT` only. php-fpm is capped at 5 workers and 96 MB per request.
  - The health check is Kanboard's own `/healthcheck.php`.
  - Migrations run once at start. The schema's built-in `admin/admin` is disabled on every start.
  - No plugin installer, no email (mail settings hidden, `egress: []`).
  - The database comes from Kanboard's own `DATABASE_URL` parsing; the plan's split into `DB_*` wasn't needed.
- **Sign-in:** Kanboard's reverse-proxy auth reads `HTTP_REMOTE_USER`, which is the `Remote-User` header, with name and email from `Remote-Name` and `Remote-Email`.
  - **Not** Kanboard's default `REMOTE_USER`: that is the HTTP basic-auth user, which any client can choose.
  - Kanboard 1.2.5x honours the header only from `TRUSTED_PROXY_NETWORKS`. The entrypoint writes the container's own networks there: the app's internal network, shared only with platform containers (D88). The trust itself rests on the front door replacing every `Remote-*` header.
  - Kanboard's login form, password reset, remember-me and logout are off, and nginx answers 404 for their routes. `kaldi-admin` is Kanboard's admin (`KANBOARD_DEFAULT_ADMIN`).
- **Cross-site check (D91):** written as nginx maps with the same rule as the runtime's `csrf_violation`, so `ANNEX_CSRF` stays on. Kanboard's own CSRF tokens remain too; a few of its GET links change state, each with a Kanboard token.
- **Logging:** nginx writes one JSON line per request (`request_id`, user, method, path without query, status, duration) and returns `X-Request-Id`. Kanboard's own messages and PHP errors stay plain text: an off-the-shelf tool can't follow the convention fully, and the README says so.
- **The boards:** `annex run kanboard seed`, by hand, uses Kanboard's JSON-RPC API on `127.0.0.1` only; through the front door it's 403. It creates:
  - a project per open venue, plus "Parts to order", with columns Reported, Diagnosing, Waiting for parts, Fixed;
  - a card per open service ticket from the gateway (`service_log`), and a parts card per ticket waiting for parts.

  It is idempotent through Kanboard's task `reference` (`ticket-<id>`, `parts-<id>`), never moves cards, and adds everyone who has signed in so far to the Goat projects. `cronjob` (06:00) is Kanboard's own housekeeping.
- **The API token (Nejc):** Kanboard's own `api_token` from its settings table, read through the app's `DATABASE_URL`; no Annex secret.
  - If it is missing, or equals the fixed value in Kanboard's published schema dump, it is replaced at start by a new random one, made the way Kanboard makes them.
  - It is never printed or logged.
- **People after the seed (Nejc):** there is no "members" job. Someone who signs in for the first time later is added to the boards by a Kanboard admin, or by rerunning the seed.

**Why.** It shows that Annex hosts off-the-shelf tools a client would otherwise buy as SaaS, under the same rules as AI-built ones: one login, its own database, backups, health, logs and the console, with no change to the platform. Kanboard was the best fit of §2.7's options, because its reverse-proxy sign-in needs no OIDC. Kanboard's own token keeps a demo reset free of human steps. Without the members job, there's one less thing running every 15 minutes.

**Alternatives.**
- A wrapper that keeps s6, or a build from the release tarball on a PHP base: both more work for the same result.
- The token as an Annex secret (`KANBOARD_API_TOKEN`): it shows the secrets feature, but adds a human step per stack and reset.
- A members job every 15 minutes: people see the boards right away, at the cost of a frequent job and a membership policy in code.
- Wiki.js, Homebox, Vikunja or n8n (plan §2.7): they need OIDC, a second login, or credentials of their own.

Smoke and test-platform now **fail** instead of skipping when arcade-db isn't running or linked, since push guarantees it. Ops unit tests that use `client-lookup` or `monthly-report` as sample app names keep them: they are arbitrary strings.

README and the agent-facing copies (templates' sample code and `annex.yaml`, runtime docstrings, `SKILL.md`, the manifest's error examples, the contract's examples and allowlist) use Goat Arcade views: `machine_floor` in the web templates, `revenue_weekly` in the job template. `reset-demo.sh`, `demo-bad-deploy.sh`, `seed-usage.sh` and `docs/demo.md` still name the removed apps; GA.7 rewrites them.
- **Versions (D94).** `ANNEX_CONTRACT_VERSION` is **2**: four views left the allowlist, which an existing app reading them notices (its next deploy is refused, its reads fail), and a CLI checkout from before this commit gets the note that it is older. The runtime's `__version__` is **2** too, although only the `gateway()` docstrings changed: otherwise every unedited older copy would be reported as "the current version, but the file differs", which tells the builder they edited it.

**Why.** The demo plan makes Goat Arcade the whole story (`docs/plans/goat-arcade-demo.md` §1), and two data sets told builders' agents two stories: templates read wealth views next to an arcade's dashboards. The platform suites read the wealth views, so the data could not go before the tests moved; with Goat Arcade brought up by push, the suites have one data set they can rely on, on both lanes and in CI.

**Alternatives.**
- Keep the wealth tables in product-db and drop only the views: no app or agent would see them, but the instance would still carry a second, unused data set that has nothing to do with its client.
- Drop the wealth objects from `annex_api.sql` itself on every push: the push would drop views under an app that still reads them, and the code would carry a cleanup forever; a one-off script run by a human after the removals is explicit and leaves no trace in the push.
- `DROP SCHEMA product CASCADE`: shorter, but would silently take along anything someone built on those tables.
- `bootstrap.sh` starting democlient: it runs before the first push, when `annex-clientlink` doesn't exist yet; it would need its own platform start.
- Leave the suites skipping when Goat Arcade is missing: a skip would hide a broken push; push now guarantees it, so its absence is a failure.
- Keep the contract at 1 because the allowlist is data validated live at deploy: true for the deploy, but the contract text is what agents read, and D94's rule is "an existing app would notice".

**Tests.** Unit tests (ops, vm, cli, runtime Python and Node), `sync-runtime.sh --check` and `sync-contract.sh --check` green; `bash -n` on every changed script. Not run here (human steps first): `push.sh` on a fresh local stack (seeds and links), on the VM (re-applies only), `retire-wealth.sql` on both lanes, then `test-smoke.sh`, `test-apps.sh`, `test-audit.sh`, `test-errors.sh`, `test-platform.sh`.
