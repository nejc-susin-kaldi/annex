# M1.4 implementation plan: usage stats and the weekly digest

For a build agent. Written 15 Oct 2026, when M1.2 was committed (`640c277`) and M1.3 was planned (`docs/plans/m1.3.md`) but not yet built. **Start only once M1.3 is committed.** The milestone comes from Nejc's M1 plan, section "3. Usage stats"; this file is the how, and is complete on its own.

**Read first:** `CLAUDE.md`, `docs/brief.md` (ground rules), `docs/decisions.md` (all of it, including M1.3's entries), `docs/plans/m1.3.md`, the M1.3 commit (`git show --stat` and the code in `ops/`), and this whole file. Do only M1.4. Stop when it's done and report to Nejc; don't start M1.5.

## Goal
- **Owners see who uses their tool:** "used by 9 people this week" with a trend on its discovery tile, and in `annex usage`.
- **Kaldi and the client see which tools matter:** graduation candidates, dormant tools, error rates and response times per tool, in a Metabase dashboard and a weekly email digest.
- **Zero effort for apps:** everything comes from Traefik's access log. Apps change nothing.

## Done when (acceptance, from the M1 plan)
1. After a scripted session with `sam` and `cm` across three apps, the Metabase dashboard, the discovery tiles and `annex usage` all show matching numbers, and those numbers match the script.
2. The digest flags a dormant app.
3. Raw request rows are deleted after 30 days, never contain query strings, and per-person detail is shown only by `annex usage <app> --by-user`.
4. `scripts/test-usage.sh` passes, and so do all earlier suites (`test-platform.sh`, `test-apps.sh`, `test-jobs.sh`, `restore-test.sh`, `test-rollback.sh`, `test-notify.sh`, `test-alerts.sh`).

## What's already true (checked on the VM, 15 Oct)
- **Traefik's access log already carries the signed-in user.** `config/traefik/traefik-*.yml.tmpl` keeps the `Remote-User` header, and real lines look like this (trimmed): `{"DownstreamStatus":200,"Duration":11914061,"RequestMethod":"GET","RequestPath":"/?q=novak","RouterName":"app-client-lookup@docker","StartUTC":"2026-10-14T12:41:52.358737293Z","request_Remote-User":"cm", ...}`. So the M1 plan's "first spike" is done: no fallback is needed.
- `Duration` is in nanoseconds. `RequestPath` includes the query string, which can contain client names (`?q=novak`): **strip it before storing.**
- Anonymous requests (login redirects) have an empty `request_Remote-User`. Gatus probes apps directly, not through Traefik, so health checks barely appear in the log; exclude the app's health path anyway.
- Traefik writes about 1 KB per request, so Docker's rotation (10 MB × 3) holds about 30k requests: plenty for a follower that resumes from a cursor.

## Decisions already made for you
Defaults chosen when this plan was written. Log each in `docs/decisions.md` (what, why, alternatives), continuing the numbering.
1. **Per-person usage is acceptable, admins only** (Nejc, 15 Oct; M2 plan). Totals appear on tiles, in Metabase, in the digest and in `annex usage`. Logins appear only in `annex usage <app> --by-user`. In the prototype, CLI access means SSH access, which means admin.
2. **What counts as a request:** a line on an `app-<name>@docker` router with a non-empty `request_Remote-User`. Not counted: the app's health path, static assets (path ends in `.js .mjs .css .map .png .jpg .jpeg .gif .svg .ico .webp .woff .woff2 .ttf`), and platform routers (Homepage, Metabase, ...).
3. **Storage:** raw rows in `annex_ops.requests` for 30 days; daily and weekly summaries without logins, kept indefinitely. Weeks are ISO weeks (Monday start), days in `Europe/Ljubljana` (`TZ`).
4. **Signals:**
   - *graduation candidate:* the last 4 complete weeks each had at least as many users as the week before, the latest had **≥ 5**, and the latest is higher than the first;
   - *dormant:* no signed-in requests for **30 days**, and Annex first saw the app at least 30 days ago.

   Both thresholds are settings. With three demo users, graduation can only show with seeded history (optional step 7).
5. **The digest** goes out Mondays at 08:00 local time. Admins get every app; each owner gets their own apps. It's sent once per week, even across restarts.
6. **Tiles call ops without a token** (`GET /tiles/<app>`, totals and status only, never logins). Homepage proxies widget calls on its server side, so the browser never calls ops. Apps on `edge` can read these totals too; accept and log it.
7. **Metabase reads summaries only**, through a new read-only role `metabase_usage` that has no access to `annex_ops.requests`.

## How the pieces fit
```
annex-traefik-1 stdout ─(M1.3 follower, socket-ro)─▶ Traefik handler ─┬─▶ engine error window (M1.3, unchanged)
                                                                      └─▶ usage.ingest() ─batch insert─▶ annex_ops.requests (30 days)
usage thread, every 10 min: rollup → usage_daily, usage_weekly, app_seen; delete raw rows > 30 days
digest thread: Monday 08:00 → send_email(app="_platform") to admins and owners
Homepage tile ─server-side─▶ GET http://ops:8000/tiles/<app>          Metabase ─metabase_usage─▶ summaries + usage_apps view
annex usage ─ssh─▶ docker exec annex-ops-1 python -m annex_ops.ctl usage ... --json
```

## Step 1. Schema and roles
Append to `db/appdata/annex_ops.sql` (idempotent, applied by `push.sh` as `postgres`):
```sql
CREATE TABLE IF NOT EXISTS annex_ops.requests (
  ts          timestamptz NOT NULL,
  app         text NOT NULL,
  login       text NOT NULL,
  method      text NOT NULL,
  path        text NOT NULL,          -- no query string, at most 200 characters
  status      int NOT NULL,
  duration_ms int NOT NULL
);
CREATE INDEX IF NOT EXISTS requests_app_ts ON annex_ops.requests (app, ts);
CREATE INDEX IF NOT EXISTS requests_ts ON annex_ops.requests (ts);
CREATE TABLE IF NOT EXISTS annex_ops.usage_daily (
  day date NOT NULL, app text NOT NULL, users int NOT NULL, requests int NOT NULL,
  errors int NOT NULL, p95_ms int, synthetic boolean NOT NULL DEFAULT false, PRIMARY KEY (day, app));
CREATE TABLE IF NOT EXISTS annex_ops.usage_weekly (
  week date NOT NULL, app text NOT NULL, users int NOT NULL, requests int NOT NULL,
  synthetic boolean NOT NULL DEFAULT false, PRIMARY KEY (week, app));
CREATE TABLE IF NOT EXISTS annex_ops.app_seen (
  app text PRIMARY KEY, first_seen timestamptz NOT NULL, last_used timestamptz);
CREATE TABLE IF NOT EXISTS annex_ops.digests (week date PRIMARY KEY, sent_at timestamptz NOT NULL);
```
Plus a view `annex_ops.usage_apps`: one row per app in `app_seen`, with `users_7d`, `users_30d`, `requests_7d`, `error_rate_7d`, `p95_7d`, `last_used`, `first_seen`, the last four complete weeks' users, and `signal` (`graduation`, `dormant` or null). Compute rolling 7- and 30-day distinct users from `requests`; everything else from the summaries. Put the signal rules in the view, or in Python with the view taking `signal` from a small table the rollup writes; pick one and keep it in one place.

**Role `metabase_usage`:**
- `vm/bootstrap-secrets.sh`: `ensure_key APPDATA_DB_METABASE_USAGE_PASSWORD`.
- `push.sh` passes it to psql as `-v usage_pw=...`, read from `master.env` on the VM as for `ops_pw`.
- The SQL creates the role (LOGIN, password always re-set), grants `CONNECT` on `annex_ops`, `USAGE` on the schema, and `SELECT` on `usage_daily`, `usage_weekly` and `usage_apps` **only**. No grant on `requests`, `sends`, `incidents` or `app_grants`.
- The view is owned by `annex_ops`, but `users_7d` reads `requests`. Check that `metabase_usage` can select the view without a grant on `requests` (a view runs with its owner's rights by default; don't set `security_invoker`).

Run `scripts/bootstrap.sh`, then `scripts/push.sh --extras`.

## Step 2. Ingest
`ops/annex_ops/usage.py`, all decisions in pure functions:
- `parse_access_line(line) -> Request | None` applies decision 2. It needs each app's health path: read it from the container label `com.kaldi.annex.healthcheck` (new, step 4), cached and refreshed on `start` events. Strip the query string, cap the path at 200 characters, and convert `Duration` from ns to ms.
- Hook into M1.3's Traefik handler: the same parsed line feeds the engine's error window and `usage.ingest()`. Don't start a second follower on the same container.
- `ingest()` buffers rows and inserts them in batches (every 5 s or 200 rows, `executemany` or `COPY`), and keeps `app_seen.first_seen` (insert on first sight) up to date. Apps that exist but have no traffic also need a `first_seen`: on startup and on each `start` event, insert any running app container that's missing.
- The follower's cursor already avoids duplicates on restart. Check it with a restart test (step 6).

## Step 3. Rollup, signals, digest
- **Rollup thread**, every 10 min, plus `ctl rollup` to run it now. It upserts `usage_daily` for today and yesterday and `usage_weekly` for this week and last week, from `requests` (users = distinct logins; errors = status ≥ 500; p95 = `percentile_cont(0.95)` of `duration_ms`). It never overwrites rows with `synthetic = true`, updates `app_seen.last_used`, and deletes `requests` older than 30 days.
- **Settings** (`config.py`, overridable by env and by M1.3's `tuning.json`): `usage_retention_days` (30), `graduation_min_users` (5), `graduation_weeks` (4), `dormant_days` (30), `rollup_s` (600), `digest_weekday` (0 = Monday) and `digest_hour` (8).
- **Digest** (`digest.py`, rendered with the `notice` template, or the `details` field if M1.3 added one):
  - per app: users this week and the change from last week, requests, error rate, p95, and the 4-week trend as numbers (e.g. `3 → 4 → 4 → 6`);
  - sections "Graduation candidates" and "Dormant (no users in 30 days)";
  - a link to the Metabase dashboard and a line saying what's counted and that logins aren't shown.
  - Admins (group `admins` in the directory) get every app; each owner (from the container label) gets their own apps. Send with `email.send_email(app="_platform", ...)`.
  - A digest thread checks once a minute and records the week in `annex_ops.digests`, so it's sent once per week even across restarts.
  - `ctl digest [--send] [--to <login>] [--dormant-days N] [--min-age-days N]` previews it without `--send`; the overrides are for tests and the demo.
- **Tile endpoint** `GET /tiles/<app>` (no token, decision 6): `{"users_7d": 3, "trend": "↑2", "requests_7d": 41, "status": "ok", "last_run": "ok 09:30"}`.
  - `status` comes from M1.3's open incidents: `ok`, or a short word like `down`.
  - `last_run` (job apps) comes from `job_runs`.
  - Unknown app: 404 with `{"error": ...}`.
  - Never logins.
- **ctl** `usage [--app X] [--by-user] --json`:
  - without `--app`: one row per app from `usage_apps`;
  - with `--app`: the last 30 days by day, plus the app's row;
  - `--by-user` adds per-login request counts for the last 30 days (with `--app` only).

**Unit tests:** line parsing (exclusions, query stripping, ns → ms, the missing-user case); the graduation and dormant rules at their edges; the trend string; the digest content (admin vs owner, no logins in it); and the tile JSON (no logins, unknown app).

**`scripts/test-usage.sh`**, in the style of the other suites (tunnel, `curl --connect-to`, logins as `sam` and `cm`):
1. **Setup:**
   - `annex init static usage-probe` and `annex init static usage-idle` into `.build/test-usage/`, then deploy both;
   - make sure `client-lookup` is deployed;
   - record `annex usage --json` for the three visited apps.
2. **Scripted session,** with fixed counts per user and app, for example:
   - `sam` × 5 on `client-lookup /`;
   - `cm` × 2 on `client-lookup /?q=novak`;
   - `cm` × 3 on `usage-probe /`;
   - `sam` × 4 on `usage-probe /`.

   Plus requests that must **not** count:
   - each app's health path, as `sam`;
   - a static asset (e.g. `/favicon.ico` or a `.css`);
   - anonymous requests (they get 302).
3. Wait until ingest has caught up (poll `ctl usage` up to 60 s), then run `ctl rollup`.
4. **Assert:**
   - the increase in `requests_7d` per app equals the script;
   - `users_7d` includes the right logins (check with `--by-user`: `client-lookup` has sam and cm, `usage-probe` has sam and cm);
   - the tile JSON (`docker exec annex-ops-1 python -c` with urllib on `http://127.0.0.1:8000/tiles/<app>`) equals `ctl usage` for each app;
   - Homepage's `/api/services` (as `cm`) lists the widget for `client-lookup`;
   - if extras are on: each Metabase card's numbers for those apps (`POST /api/card/:id/query` as `kaldi-admin`) equal `ctl usage`.
5. **Privacy and storage:**
   - no row in `requests` has `?` in `path`;
   - `metabase_usage` gets "permission denied" on `annex_ops.requests` but can read `usage_apps`;
   - the tile JSON and the digest contain no login.
6. **Retention:** insert a row in `requests` dated 31 days ago, run `ctl rollup`, and check it's gone.
7. **Restart:** note the row count, `docker restart annex-ops-1`, make two more requests, wait, and check the count went up by exactly 2 (no duplicates, no gap).
8. **Digest:** clear Mailpit, then run `ctl digest --send --dormant-days 1 --min-age-days 0`:
   - `admin@annex.example` gets one digest that lists `usage-idle` under "Dormant" and not `client-lookup`;
   - `sam@annex.example`, who owns all the test apps, gets one too.
9. **Teardown:** `annex remove usage-probe --yes` and `annex remove usage-idle --yes`. Their usage history stays (it's platform data); say so in the docs.

Then run every suite. **Known flake:** right after a deploy that restarts Ofelia, `test-platform.sh` reports Ofelia as "health: starting" for up to 30 s; wait until it's healthy.

## Pitfalls
- **Rollback loads older manifests.** Any new manifest field needs a default; this plan adds none.
- **Only one follower per container.** Hook into M1.3's Traefik handler; don't open a second stream on `annex-traefik-1`.
- **Timestamps and time zones.** `StartUTC` is UTC. Bucket days and weeks with `AT TIME ZONE 'Europe/Ljubljana'` (the `TZ` setting), not the server's default.
- **Logins never leave `--by-user`:** not in tiles, Metabase, the digest, `ctl usage` without `--by-user`, or error messages.
- **Single-file bind mounts go stale (D7):** if you add a mounted file, mount its directory.
- **`docker restart` doesn't re-read env files.** Use `docker compose up -d --force-recreate <svc>` after changing them.
- **The view runs with its owner's rights,** so `metabase_usage` reading `usage_apps` doesn't need a grant on `requests`. Don't make it `security_invoker`.
