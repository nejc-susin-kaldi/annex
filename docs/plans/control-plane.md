# Control-plane plan: the deploy runs on the VM, the platform runs on the Mac

For an **orchestrator agent** (Opus) that delegates one step per subagent (Sonnet unless a step says Opus) and integrates the results, the way `docs/plans/hardening.md` was run. Written 22 Oct 2026 against the merge of hardening D79–D96 (`c2e8139`). It makes the two changes the review of 22 Oct named as the ones with the highest return: move deploy orchestration from the builder's laptop onto the VM as one call, and give the platform a local Compose mode so the suites run on the Mac (and in CI) instead of only against the shared VM.

**Read first:** `CLAUDE.md` (ground rules; it overrides everything), `docs/architecture.md` (the deploy sequence and the files on the VM, as they are now), `docs/decisions.md` D1, D17, D30, D31, D64, D85, D88, D92, D95 (the index at the top says what each is), `docs/plans/hardening.md` ("How the orchestrator works" and the production list), `docs/operations.md`, and this whole file. Every subagent gets the same reading list plus its one step.

## Why these two

**The deploy is driven from the wrong side of the wire.** `annex deploy` is a Python program on the builder's machine that runs about a dozen separate `ssh annex bash -c` steps (`cli/src/annex_cli/ops.py` `_deploy` at 693–752, `_activate` at 574–610, `_Lock` at 376–418, `_rollback_locked` at 975–1020). Everything that was added in hardening C1 (D92) exists to survive that split: the lock directory with a token because the holder is on another machine, the 30-minute stale rule, `deploy-step` so a dead deploy can say where it stopped, the pending line, reconcile on the next deploy, the CLI's own timeout message. A laptop that sleeps during the gate still kills the deploy. The compose file an app runs with is generated by whichever CLI version last touched it, and a second builder with an older checkout generates a different one on rollback. The production replacement, a deploy API bound to the builder's identity (hardening production list, item 1), has nothing to wrap until the sequence lives on the VM.

**Every integration test needs the VM.** Fifteen bash suites, about thirty minutes for the set, one shared environment, so one step at a time could touch it during hardening, and no CI can run them. Every image in `compose.yaml` is published for arm64 as well as amd64 (to confirm in L1), every path on the VM is `${ANNEX_DATA_DIR}`, and the CLI's only transport is `Remote` in `cli/src/annex_cli/remote.py` (`ssh … bash -c`), so the same scripts can drive a stack on the Mac's Docker Desktop, and on a Linux CI runner, if `vm()` and `Remote` can exec locally.

## What is kept
- The contract, `annex.yaml`, the templates, the runtime helpers, the MCP tools and the CLI's commands and output: builders and agents see the same interface. `deploy`'s result dict and the `progress` callback keep their shape, so `mcp/src/annex_mcp/server.py` does not change.
- SSH as the transport to the VM (D1). The VM-side program is what a deploy API will call later; the API is still a production item.
- `annex_vm.py` stays stdlib (plus PyYAML). What moves onto the VM is stdlib already.
- Releases, the health gate, snapshots, per-app networks (D88), build limits (D95), the pending release line and the reconcile rules (D92): the same decisions, taken by one process instead of a conversation between two.

## How the orchestrator works
The rules of `docs/plans/hardening.md` "How the orchestrator works" apply unchanged (branch, worktrees write and the main checkout pushes, approval gates, one decision entry per step numbered from **D97**, the report format, don't-touch list). Two additions:
1. **Two lanes once L2 lands.** The *local lane* is the Mac's Docker (`ANNEX_ENV=local`); the *VM lane* is `ssh annex`. After L2 every step is proven on the local lane first (bootstrap, push, smoke, the step's suite) and on the VM second. The local stack is one per machine (fixed container names and ports), so it is still one step at a time locally, but a step no longer waits for the VM.
2. **Order.** The local mode comes first (L1–L3), because the deploy rewrite (V1–V3) is then developed and tested against a stack that can be wiped and rebuilt in minutes. The VM is touched by L-steps only at the end of each (`push.sh` + `test-smoke.sh`, to prove nothing regressed there).

## L2. `ANNEX_ENV=local` (**Opus**, local then VM, **ask Nejc**: confirm the data dir `~/.annex/local` and the ports 8443/8080 before building)
**Goal:** `ANNEX_ENV=local scripts/bootstrap.sh && ANNEX_ENV=local scripts/push.sh && ANNEX_ENV=local scripts/test-smoke.sh` is green on the Mac, with the VM untouched.
**Design.**
- **Selection.** `ANNEX_ENV` names the settings file: unset or `vm` reads `.env` (today's behaviour); `local` reads `.env.local` (already gitignored by `.env.*`; add `!.env.local.example` to `.gitignore` so the committed example is not). `scripts/render.py` renders into `.build/<env>/platform` (today `.build/platform`; keep a symlink or update every reader: `lib.sh` `setting_local`, `testlib.sh` `use_tunnel`, `scripts/pushcheck.py`, `remote.py`'s `ControlPath`).
- **Transport.** `.env.local` sets `ANNEX_TARGET=local` (new key, default `ssh`), `ANNEX_DATA_DIR=$HOME/.annex/local` (expanded by `render.py` and `lib.sh`; it must be outside the repo so rsync and `git status` never see it, and under `~` so Docker Desktop shares it), `ANNEX_PUBLIC_PORT=8443`, `ANNEX_BIND_HTTPS=127.0.0.1:8443`, `ANNEX_BIND_HTTP=127.0.0.1:8080`. `lib.sh`: `vm()` becomes `bash -c "$*"` when the target is local (the scripts already pass one string with `$DATA` expanded, so the same string runs locally), `put()` replaces the two `scp` uses in `bootstrap.sh` (`cp`), `rsync` in `push.sh` targets the local directory, `setting()` reads the local `platform/.env`. `scripts/tunnel.sh` prints "local mode: no tunnel, Traefik is on 127.0.0.1:8443" and exits 0 for `up`/`status`. `remote.py`: `Remote` reads `ANNEX_ENV`, `ANNEX_TARGET`, `ANNEX_DATA_DIR` and `ANNEX_SSH_HOST` from the selected env file (today the CLI reads only the process environment, remote.py:22–23, so `./annex` and the scripts can disagree); with a local target `run`, `out`, `stream` and `vm` exec `bash -c` directly and `vm` runs `annex_vm.py` with the Mac's `python3` (uv's 3.13 has no PyYAML: `uv run --with pyyaml`, or install `pyyaml` into the CLI's venv, which already lists it; pick one and record it).
- **Compose.** `compose.yaml`: `ports: ["${ANNEX_BIND_HTTP}:80"]`; `compose.tls-local.yaml`: `["${ANNEX_BIND_HTTPS}:443"]`; `render.py` derives both (`80`/`443` on the VM, the loopback ports locally). Any image L1 found without arm64 gets `platform: linux/amd64` **only in a local override file** `compose.local.yaml` that `render.py` adds to `COMPOSE_FILE` for the local target; the VM's files don't change. The ops image and app images are built natively (arm64) locally; the brief's "images must support amd64" is about the VM and stays.
- **The VM script locally.** `annex_vm.py` runs unchanged if L1 found ownership works; otherwise the `/data` check (922–923) treats a bind mount whose owner can't be read as "chown each time". Container names, `docker exec` into the Postgres containers, `docker compose` in `deploy/<app>`: all the same.
- **mkcert.** `bootstrap.sh` issues the certificate into the local `certs/` directly; the CA is already trusted on the Mac. Browser access locally needs `/etc/hosts` lines for the hostnames (system change: `docs/setup.md` §3 gets a local variant, for Nejc to apply); the suites don't need it (`--connect-to`).
- **Two stacks on one Mac.** `.env` for the VM and `.env.local` for the Mac coexist; `.build/<env>` keeps renders apart; nothing else is shared. Document that `ANNEX_ENV=local` is per command, never a default.
**Tests.** Unit tests for `render.py`'s derivation (local vs vm) in `cli/tests` or a new `scripts/tests`; `test-smoke.sh` green locally; then `scripts/push.sh` and `test-smoke.sh` on the VM to prove the VM path is unchanged (`VERSION` stamp still refuses an older checkout, D85).
**Done when** both are green and `docs/setup.md` has a "Local stack" section (prerequisites: Docker Desktop with the memory from L1, mkcert, uv; how to wipe it: `rm -rf ~/.annex/local` after `docker compose down -v` of the two projects). Decision entry (D98) revising D1's "the VM's Compose" wording for the local case.

## V1. The deploy as one VM-side process (**Opus**, local then VM, **ask Nejc** on two points before building: Ctrl-C detaches rather than cancels; D92's lock directory and token are replaced by a process lock)
**Goal:** `annex deploy` makes one call: `annex_vm.py deploy <app> --actor … --via … --meta <json>` with the source tar on stdin. The VM process does everything `_deploy` does today, streams progress, and finishes even if the SSH session goes away. `annex rollback` the same with `annex_vm.py rollback`.
**Spike text (write this first, in the step's report, before code):** the list of functions that move and where each lands; what the CLI still does; the exact stdout protocol; the lock design; what happens on each failure (session drop, Ctrl-C, VM reboot, build failure, gate failure, two deploys).
**Design to start from.**
- **New module `vm/annex_deploy.py`** (stdlib; imported by `annex_vm.py`; synced like the rest of `vm/`). Into it, from `cli/src/annex_cli/ops.py`: `compose_for` and `_tile_labels`, `_compose_networks`, `rewire_compose`, `_network_args`, `_provision_args`, `_webhook_urls`, `_drain`, `_build` with `platform_label_offenders`, `build_space_verdict`, `image_size_verdict`, `_limit`, `_gate`, `_activate`, `_reload_scheduler`, `_write_record`, `_record_for`, `_cleanup`, `_prune`, `_gate_error`'s text, `_deploy`, `_rollback_locked`, `_rollback_target`, `_running_image`, and the `logcheck` warning for web apps. They call `subprocess` and the existing `annex_vm` functions directly instead of `r.run`/`r.vm`. The manifest class they need comes from the bundle (V3; until then `vm/annex_deploy.py` reads the stored manifest dict the way `Manifest.from_dict` does: V1 may copy `manifest.py` into the bundle by hand in `render.py` and V3 makes that the rule).
- **The lock.** One process holds `flock` on `deploy/<app>/.lock.guard` for its whole run (D92 rejected this because the deploy was many sessions; now it is one process, so the lock dies exactly when the deploy does). `deploy/<app>/current.json` holds actor, started_at, release and the current step, rewritten at each step. A second deploy that can't take the flock reads `current.json` and refuses, naming the holder and step. A pending line whose lock is **not held** is reconciled at once by the next deploy (D92's rules unchanged: healthy and running the pending image → live; otherwise failed and nothing switched), so the 30-minute rule, the takeover, the token, `ANNEX_DEPLOY_LOCK_STALE`, `deploy-begin`, `deploy-step` and `deploy-end` go. `deploy-reconcile` stays for a human.
- **Surviving the session.** The process ignores `SIGHUP` and `SIGPIPE`, writes every progress line to `deploy/<app>/run.log` as well as stdout, and treats a failed stdout write as "the caller left" (keep going, stop writing to stdout). The CLI, when the SSH call ends without a final result line, says: "the connection dropped at <last step>; the deploy continues on the VM; `annex status <app>` shows its step and `annex releases <app>` its outcome". Ctrl-C in the CLI closes the session the same way and prints the same message: it detaches, it does not cancel (that is the question for Nejc; the alternative is a `deploy-cancel` that sends SIGTERM to the holder, which the process would turn into a failed release at its next step).
- **Stdout protocol.** One JSON object per line: `{"progress": "Building r5 on the VM"}`, `{"note": "…"}` (the warnings `_Lock.notes` carried), and last `{"ok": true, …the result dict…}` or `{"ok": false, "error": "…"}`. Build output and gate log tails go into the error text as today, never as progress lines. `Remote.call(args, input, on_line)` reads stdout line by line (`subprocess.Popen`, no `capture_output`), feeds `progress`, returns the final object; the timeout is per silent interval (no line for 15 minutes), not per call, so a long build isn't cut.
- **The CLI after V1.** `deploy()`: load and validate the manifest locally (fast failure, agent-readable messages, unchanged), check the views against `annex_vm.py views` (unchanged), build `meta` (who, via, source, git, contract and runtime versions: today's `line`), tar the folder, one `Remote.call("deploy", …)`, print the result. `rollback()`: resolve the target by reading releases (unchanged), one call. `_Lock` is deleted. The MCP's `annex_deploy` and `annex_rollback` don't change.
- **Build failures** are still a failed release with a number (D92). **VM reboot** mid-deploy: the process is gone, the flock is free, the next deploy reconciles; `restart: unless-stopped` brings up whatever Compose last started, as today.
**Tests.** Pure functions keep their tests: move `cli/tests` cases for the moved functions into `vm/tests` (unittest), with the `run` seam of D96 for the ones that call Docker. `vm/tests/test_deploy_lock.py`: rewrite for the flock and `current.json` (refusal naming the holder, a free lock with a pending line reconciles, step rewrite, no temp files). `cli/tests/test_deploy_lock.py` goes; a new `cli/tests/test_remote_call.py` tests the line protocol with a fake process (progress order, a missing final line becomes the detach message, the silent-interval timeout). `scripts/test-rollback.sh` scenarios 4–6: two concurrent deploys (one refused, naming the holder); a deploy whose **CLI** is killed in the gate (the VM finishes it: the release ends `live`, no reconcile needed); a deploy whose **VM process** is killed in the gate (`SIGKILL` on the VM: pending line, free lock, the next deploy reconciles). Run locally, then on the VM.
**Done when** `test-rollback.sh`, `test-apps.sh`, `test-smoke.sh` and `test-logs.sh` (the drain) are green on both lanes, `ops.py` no longer contains the moved functions, and the decision entry (D100) revises D17, D30 (the gate's wording), D64 (the drain is now the same process) and D92.
**Prod:** the deploy API is an HTTP front over `annex_vm.py deploy`: it authenticates the builder, sets `--actor` from the identity, and streams the same lines. Nothing in the sequence changes again.

## V2. The other container-replacing operations (Sonnet, local then VM)
**Goal:** `secret set`, `remove`, `migrate-networks` and `run` are one call each, through the same `Remote.call`.

**Tests.** `scripts/test-notify.sh` (secret set), `test-apps.sh` (remove), `test-jobs.sh` (run), the `migrate-networks` check in `test-platform.sh`; unit tests for the new VM commands with the `run` seam. Both lanes.

## V3. Version coupling and one manifest module (Sonnet, local then VM)
**Goal:** the VM decides whether a CLI may deploy, and both sides validate the manifest with the same code.
**Do.**
- `scripts/render.py` copies `cli/src/annex_cli/manifest.py` (and `logcheck.py`) into the bundle's `vm/` as `annex_manifest.py` (generated, not in the repo's `vm/`; `sync-contract.sh --check` or `render` is the one source). `vm/annex_deploy.py` validates `src/annex.yaml` with it before building, so a modified CLI can't skip a rule; the CLI's local validation stays for fast failure.
- `--meta` carries the CLI's commit (`git rev-parse HEAD` of the repo it runs from, or `unknown`) and contract version; `annex_vm.py deploy` compares with `platform/VERSION` and the platform's contract version: a CLI whose contract version is **newer** than the platform's is refused ("push the platform first"); an older one gets a note in the result. `annex status` and the console's Config tab show the CLI commit a release was made with (it is in the release line already as `git`; add `cli`).
- The MCP server's error path: a refusal arrives as `{"ok": false}` and becomes a `ToolError` as today.
**Tests.** `vm/tests` for the comparison (pure); `test-smoke.sh` on both lanes; a deliberate mismatch by editing the local `VERSION` copy in a scratch render.
**Done when** the decision entry (D101) says where the manifest module lives and the comparison rule.

## What stays, and what production changes

The hardening plan's production list stands; this plan changes three of its items and adds two.

1. **Builder = root** (hardening item 1). After V1–V3 the deploy sequence is one VM-side program with a line protocol, so the production step is small: an HTTP front (`annexd`, in a container with the Docker socket, or the same script behind SSH `ForceCommand` per builder key) that authenticates the builder, sets `--actor` from the identity and streams the same lines. Human-only commands become authorisation in that front. Until then the shared key stays, and the audit actor is still what the CLI sends.
2. **Builds on the client's server** (hardening item 5). Unchanged in substance; the build step is now inside `annex_deploy.py`, so switching it to "pull `<registry>/<app>:r<n>`" is one function.
3. **Front door** (hardening item 3). The local mode binds Traefik to loopback ports and uses the mkcert CA; production is still ALB or CloudFront. The `ANNEX_BIND_*` keys from L2 are what a production compose override sets.
4. **New: the local stack is a development tool, not a second environment.** It has no backups worth keeping, no Slack, arm64 images for the ops and app images, and possibly one emulated image (L1). Nothing proven only locally counts as proven for the VM; the suites run on the VM before a demo and after platform changes, as today.
5. **New: Ctrl-C semantics.** If Nejc chooses "detach" in V1, a builder cancels a running deploy with `annex rollback` after it finishes or with `deploy-reconcile --break` on the VM; a `deploy-cancel` command is the production item if builders ask for it.
