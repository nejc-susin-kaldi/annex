## What a deployed app gets after M1
| Service | For the builder | For the client and Kaldi |
|---|---|---|
| Rollback | A bad deploy is undone automatically or with one command | No "the tool broke and nobody can fix it" |
| Downtime and error alerts | The owner hears about problems before users do | Kaldi sees the whole fleet's health |
| Usage stats | See who actually uses the tool | Shows which tools to graduate and which are dead |
| Sending email | Send reports and notifications with one API call | No SMTP passwords in tools; every email logged; internal recipients only |
| Slack | Post to approved channels with one API call | No bot tokens in tools |
| Incoming webhooks | Trello, Stripe or GitHub can call the tool | Tools stay behind login; signatures verified; events stored and replayable |

Everything stays the same for the builder: they declare what they need in `annex.yaml`, and Annex supplies the URLs and tokens as environment variables. No credentials ever go into app code.

## Shared foundation: `annex-ops`
One small internal service (Python, FastAPI) with its own `annex_ops` schema in appdata-db. It's reached by apps on the internal network, and by the CLI over SSH. It does five jobs:
1. **Notifications hub:** email and Slack, for apps and for platform alerts.
2. **Event watcher:** follows Docker events (container crashes, health changes, job exit codes) and Traefik's access log, both through the read-only socket proxy.
3. **Alert router:** decides who gets told what, removes duplicates, and sends "resolved" messages.
4. **Usage ingest:** turns access-log lines into usage rows and daily summaries.
5. **Webhook relay:** verifies, stores and forwards incoming webhooks.

**Why one service rather than five:** the VM has 3.8 GiB of RAM on a swapping host. One process at about 80 MB beats five, and the five jobs share the same data.

**Apps call it with a per-app token**, injected the way the M0 gateway token is: `ANNEX_OPS_URL` and `ANNEX_OPS_TOKEN`. The token is scoped to what the manifest declared, so an app that didn't ask for Slack can't post to Slack.

**Traefik change:** JSON access logs go to stdout. Docker's existing rotation (10 MB × 3) bounds the disk use, and annex-ops follows the logs, so no log files and no logrotate.

## 1. Rollback
**Builder gets:**
- Health-checked deploys that undo themselves if the new version doesn't come up.
- `annex rollback <app>` for everything else.

**How it works:**
- **Releases:** each deploy creates a release: image `annex/<app>:r<N>`, a snapshot of the manifest and non-secret env, the git SHA if any, who deployed it, when, and the result. The history is kept in `/srv/annex/apps/<name>/releases.jsonl` on the VM.
- **Pre-deploy snapshot:** before switching, the app's database is dumped. `/data` is archived too if it's under 200 MB; larger ones rely on the nightly backup.
- **Health gate:** start the new release and wait for its health check, 60 s by default. If it's healthy, mark it live. If not, switch back to the previous release automatically. The deploy then fails with the new release's last log lines, which an agent can act on.
- **Rollback re-applies the old manifest**, including the old gateway role, views and token, because those may differ between releases.
- **Retention:** the last 3 images and 3 snapshots per app, to fit the 25 GB disk.
- **Downtime:** a few seconds during the switch is acceptable for internal tools. Zero-downtime switching comes later.

**CLI / MCP:**
- New commands: `annex releases <app>`, `annex rollback <app> [--to rN] [--with-data]`.
- `--with-data` also restores the pre-deploy database snapshot, losing any writes since. It's human-only.
- The MCP gets `annex_releases` and `annex_rollback`, the latter without data.

**Done when:**
- Deploying a version of `client-lookup` with a broken health check rolls back automatically and returns its logs.
- `annex rollback` restores the previous version.
- `--with-data` undoes a destructive migration.

**Cost:** no new containers. Extra disk: roughly 3 × image size per app.

## 2. Downtime and error monitoring
**Owner gets:** an email or Slack message when their tool is down, crash-looping, throwing errors or failing a scheduled job, and another message when it recovers.

**Kaldi gets:** one channel showing the health of every app and the platform itself.

**Signals:**

| Signal | Source |
|---|---|
| Down / unreachable | Gatus checks each app's health URL on the internal network every 60 s, plus one end-to-end check through Traefik and Authelia. Gatus config is generated by the CLI from the manifests. |
| Crash loop / unhealthy | Docker events (`die`, `health_status`) watched by annex-ops |
| Job failed | Docker `exec_die` and `die` events with a non-zero exit code, covering Ofelia job-exec and job-run jobs alike |
| Error spike | 5xx share per app over 5 minutes from the access log, above a threshold (e.g. 5 % and ≥ 10 errors) |

**Alert routing (annex-ops):**
- Gatus sends its alerts to annex-ops through its webhook alert provider, so routing happens in one place.
- **Recipients:** the app owner, looked up from Authelia's user list, plus the platform channel: `kaldi-admin` email, and Slack `#annex-alerts` if configured.
- **No spam:** duplicates are dropped per app and problem; a reminder goes out after 1 h if it's still failing; a "resolved" message follows.

**Visibility:**
- A Gatus status page behind login.
- A Gatus widget on the discovery page, which Homepage supports natively.
- `annex status` shows the current health.

**Who watches the watcher:** if the VM dies, nothing on it can raise an alarm. Production gets an external heartbeat to Kaldi's fleet monitoring; for the prototype it's optional, e.g. a free dead-man's-switch service.

**Later:** application error tracking with stack traces, via a light Sentry-compatible server such as Bugsink, with templates wired to it.

**Done when:**
- Stopping an app, making it crash-loop, failing a job, and forcing a burst of 500s each produce exactly one alert to the owner and one "resolved".
- The discovery page shows live status.

**Cost:** Gatus at about 30 MB.

## 3. Usage stats
**Owner gets:** "used by 9 people this week" on their tool's discovery tile, and a trend line.

**Kaldi and the client get:**
- which tools matter, as graduation candidates;
- which are dead, as archive candidates;
- error rates and response times per tool.

**How it works:**
- **Source:** Traefik's access log for each request: host (which app), signed-in user, status, duration and time.
- **First spike:** verify that the `Remote-User` header set by forward auth appears in Traefik's access log. If it doesn't, fall back to a minimal usage-recording step after Authelia, and log that decision.
- **Storage:** raw rows kept for 30 days in `annex_ops.requests`, then daily summaries per app: unique users, requests, errors, p95 latency. Health checks and static assets are excluded.
- **Outputs:**
  - a Metabase "Annex usage" dashboard, provisioned through Metabase's API;
  - a per-app number on the discovery tile;
  - `annex usage [app]`;
  - a weekly digest to Kaldi and the owners listing graduation candidates and dormant tools.
- **Signals:**
  - *graduation candidate:* weekly users ≥ 5 and growing over 4 weeks;
  - *dormant:* no users in 30 days.

  Both thresholds are configurable.

**Privacy:** this is tracking of named employees. Show totals by default; per-person detail only to admins; delete raw rows after 30 days; and tell users, e.g. with a line on the discovery page. **Check this with Kaldi and each client before production:** employee-monitoring rules apply in the EU and UK, and Slovenian workplaces may need to consult employee representatives.

**Done when:**
- After a scripted demo session with `sam` and `cm` across three apps, the dashboard, the discovery tiles and `annex usage` all show matching numbers.
- The digest flags a dormant app.

**Cost:** no new containers; a little database storage.

## 4. Sending email
**Builder gets:** `POST $ANNEX_OPS_URL/email` with `to`, `subject`, and `html` or a template name.

**How it works:**
- **Recipients:** company domains only by default, because Annex is for internal tools. Anything else needs an explicit allowlist entry approved by the client.
- **Attachments:** discouraged. Send a link to the file inside the app instead, which is behind login and logged. This replaces "CSV in an email".
- **Limits and logging:** rate limits per app. Every email is logged (app, recipient, subject, time); bodies aren't kept.
- **Prototype:** mail goes to **Mailpit**, a local mail catcher with a web UI behind login, so nothing actually leaves the VM. That's also safe to demo.
- **Production:** the client's own Amazon SES (it's their AWS account), or **Goat Mailer** for templated email. Goat Mailer is the natural upsell: templates are managed there, and apps just name one.

**Manifest:** `notify: { email: true }`.

**Done when:** `monthly-report` emails "your report is ready, here's the link" to `cm`; it shows up in Mailpit; and an external recipient is rejected with a clear error.

**Cost:** Mailpit at about 30 MB.

## 5. Slack
**Builder gets:** `POST $ANNEX_OPS_URL/slack` with `channel` and `text` or blocks.

**How it works:**
- One Slack app per client workspace, installed by the client's Slack admin. Its bot token is held only by annex-ops.
- Each app may post only to channels listed in its manifest.
- Platform alerts use the same path.
- Microsoft Teams can come later behind the same API, since the app only names a channel.

**Prototype:** a free test Slack workspace. If there isn't one, Slack waits, and email covers alerts.

**Manifest:** `notify: { slack: ["#finance-reports"] }`.

**Done when:** `monthly-report` posts to an allowed channel; posting to another channel is refused; and platform alerts arrive in `#annex-alerts`.

**Cost:** none beyond annex-ops.

## 6. Incoming webhooks
**Builder gets:** external services can call the tool, while the tool itself stays behind login.

**How it works:**
- **A separate hostname**, `hooks.<domain>`, with no login in front of it. It only accepts paths declared in some app's manifest.
- **annex-ops checks the provider's signature** (Stripe, GitHub, Slack, Trello, or a generic shared secret). Then it stores the event, rate-limits it, and forwards it to the app's internal endpoint with an `X-Annex-Hook` header and a per-app token the app checks.
- **Durable delivery:** events are kept for 7 days and retried with backoff if the app is down. `annex hooks replay <app> [event]` redelivers them.
- **In production**, `hooks.<domain>` is the only internet-facing endpoint, so it needs its own rate limits and abuse protection.
- **In the prototype** (LAN only), external senders are simulated with signed curl requests from the Mac. No tunnels.

**Manifest:**
```yaml
webhooks:
  - name: trello
    path: /hooks/trello      # internal path in the app
    verify: trello           # trello | stripe | github | slack | shared-secret
```

**Done when:** a correctly signed simulated Trello event reaches the app; a badly signed one is rejected and logged; and an event sent while the app is stopped is delivered once it's back.

**Cost:** none beyond annex-ops.

## Later, not M1: AI model access
Kept here so the thinking isn't lost.
- **Gateway:** a proxy such as LiteLLM, with an OpenAI-compatible endpoint (`ANNEX_AI_BASE_URL`, `ANNEX_AI_KEY`).
- **Per-app virtual keys**, each with allowed models, a monthly budget and rate limits.
- **Key custody:** the client's provider keys are held only by the proxy.
- **Logging:** usage and cost per app; prompts not logged by default.
- **Data rules** are the client's call: which providers and models are allowed for which data.
- **Footprint:** about 250–400 MB RAM, so it sits in a compose profile that's off by default.
- **Manifest:** `ai: { models: [default], monthly_budget_eur: 20 }`.
