# M2 implementation plan: app observability, slim

For build agents, one step per session. Written 16 Oct 2026 against commit `ab37ad8` (M1 and the review follow-ups done). It replaces the M2 draft in Nejc's notes ("Kaldi Annex - build plan M2"): same goals, but **no new components**. Nejc approved the slim version on 16 Oct: no Loki, Grafana or Bugsink, and logs, errors, the console and the audit trail are built on annex-ops and its Postgres database.

**Read first:** `CLAUDE.md` (ground rules; it overrides everything), `docs/brief.md`, `docs/decisions.md` (all of it; D34–D58 describe annex-ops, its engine, followers and containers), `docs/plans/m1.md` and this whole file. Then do **only the step you were given**, and stop and report to Nejc when its "Done when" holds.

## What a deployed app gets after M2
| | For the builder | For the client and Kaldi |
|---|---|---|
| Logs that last | A failed or rolled-back version's logs are still there; searchable by release, level, text and request | 14 days of every app's logs, and its gateway reads |
| Logging convention | The template's logger already does it right | Every app logs the same way, so anyone can debug any app |
| Errors | New kinds of error in their app reach them by email, server and browser | A "new error" signal per app, not only error spikes |
| Console | One page per app: status, releases, usage, errors, logs, config. No CLI or SSH | The same pages for every app, plus a fleet overview |
| Audit | — | One timeline: who deployed, what data was read, what was sent, who changed a secret or an account, who signed in |

## Decisions already made
1. **No new components** (Nejc, 16 Oct). Logs go to a day-partitioned table in `annex_ops`. Errors are grouped from log lines. The console is server-rendered by the annex-ops image. In production, CloudWatch (in the client's AWS account) or Loki can replace the log table behind the same `annex logs` interface; Bugsink can come later if a pilot wants stack-trace UX.
2. **The logging convention warns, never refuses** (Nejc, 15 Oct).
3. **Per-person usage is fine, admins only** (Nejc, 15 Oct; D46).
4. **The console is its own container,** like the webhook receiver (D55): the ops image, with a read-only database role, on the `platform` network and a private network to the database. It's never on `edge` or `appdata`, where apps are. Apps can reach annex-ops on `annex-edge` and could send it a forged `Remote-User` header. They can't reach the console, so its `Remote-*` headers can only come from Traefik's forward-auth (the D2 problem with Dozzle, avoided by design).
5. **Defaults to confirm with Nejc at the start of the step that uses them** (change them if he says so):
   - logs kept **14 days**, audit events **1 year**;
   - the console shows an app to its **owner and admins**, and a plain "status" page (up/down only) to every signed-in user (that is what Gatus's page does today);
   - shipped logs: **all app containers**, plus annex-ops, the receiver, the gateway's request lines and Authelia's sign-in lines. **Not** shipped: the two socket proxies (41k lines a day of noise), Traefik (its access log already feeds usage) and Gatus.
6. **Owners aren't verified identities yet** (D58): `owner:` in `annex.yaml` is a claim. The console's "owner sees own apps" rests on it; that's accepted for the prototype and noted on the console's help line.

## Ground rules that bite here
- **Tests:** after every change, `scripts/push.sh` then **`scripts/test-smoke.sh`** (under a minute), plus the suite for the area you changed. **Ask Nejc before running `scripts/test-all.sh` or `scripts/test-alerts.sh`** (20–50 minutes); only do it when the change concerns what they prove. Extend `scripts/test-smoke.sh` with one cheap check per step.
- **No new images or components** without asking. Pin Python packages exactly; prefer the standard library, as annex-ops does.
- **Never log or store secrets, tokens, request bodies or cookies.** Strip them before storing; test that they're absent.
- **`annex_vm.py` stays stdlib** (plus PyYAML for users). annex-ops's engine stays pure. Schema changes go in `db/appdata/annex_ops.sql` (idempotent, applied by `push.sh`).
- **Error messages say what's wrong and how to fix it.**
- **VM hygiene:** temporary files under `/srv/annex`, never `/tmp`; one-off containers with `docker run --rm` and a command that exits.
- **Don't run** `scripts/wipe-vm.sh` or `scripts/reset-demo.sh`; don't touch the app `vibe-leads`.

## M2.1 Logging convention (contract v1)
**Goal:** every template logs the same way, out of the box, and agents are told to use it properly. This is also Nejc's note: "rules for app logging must be in the Claude skills: every vibe-coded app needs proper logging levels".

**The convention** (the contract's new "Logging" section):
- One JSON object per line on stdout. Required: `ts` (ISO 8601 with time zone), `level` (`debug|info|warn|error`), `msg`. Anything else is free-form.
- Added automatically during a request: `request_id` and `user` (the `Remote-User` login).
- `LOG_LEVEL` is injected (default `info`); override it under `env:`.
- **Never log** secrets, tokens, passwords, request bodies or full product records. IDs and counts are fine.
- Jobs log a start line and an end line with counts and duration, and exit non-zero on failure (already the alerting rule).

**Request IDs:** the app reuses an incoming `X-Request-Id` or makes one (16 hex characters), returns it as a response header, and puts it on every log line of that request.
- **Spike 1:** can Traefik's access log keep a *response* header? Add `X-Request-Id: keep` to `accessLog.fields.headers.names` in both Traefik templates and check whether a `downstream_X-Request-Id` field appears.
  - If it does, one ID links the access log, the app's lines and an error.
  - If not, link by time and user, and say so in the decisions.

**Where it goes:**
- `runtime/annex_runtime.py`:
  - a `log` object (stdlib `logging` with a JSON formatter, level from `LOG_LEVEL`);
  - `request_context(headers)`, a context manager that sets `request_id` and `user` for the lines inside it;
  - `new_request_id()`.
  - `print()` stays possible, but the AGENTS.md files steer away from it.
- `runtime/annex_runtime.js`: `log.info/warn/error/debug(msg, fields)` and a request middleware, `annexRequest(req, res, next)`, no new dependency.
- Then `scripts/sync-runtime.sh` copies both to every template, example and fixture.
- **Templates:**
  - `python-web`: a FastAPI middleware in `main.py` sets the context and the response header and logs one access line per request (method, path without the query string, status, duration).
  - `node-web`: the same with Express.
  - `python-job`: start and end lines.
  - `static`: `server.py` logs its requests in the format.
- **Examples:** `client-lookup` and `monthly-report` switch to the logger. The fixtures (`tests/*-probe`) can stay as they are, unless a check needs them.
- **Injected:** `LOG_LEVEL` (`compose_for`; add to `INJECTED_ENV`; allowed under `env:` as an override, unlike other `ANNEX_*` names).

**The check (warn only):** after the health gate passes, `deploy` reads the new container's first lines (`docker logs --tail 50`).
- If none parse as JSON with `level` and `msg`, the result gets a warning in the existing `warnings` list: "logs aren't structured: use `log` from annex_runtime.py instead of print() (see the Logging section of `annex contract`)".
- Job-only apps are checked on their first run instead (M2.2 can do this from stored lines; until then, skip them).
- Keep the parsing in a pure function with unit tests.

**Docs:**
- `contract.md`: the Logging section; `LOG_LEVEL` in the injected table.
- `skills/annex/SKILL.md`: a short "Logging" rule list.
- Every template's `AGENTS.md`: a "Logging" section: use the logger; pick the level (debug for detail, info for what happened, warn for odd but handled, error for failed); log job start and end with counts; log errors with context; never secrets or personal data beyond the login.

**Done when:**
- all four templates and both examples log in the convention (deploy them: no warning);
- a deploy of an app that uses `print()` succeeds with the warning;
- one request to `client-lookup` carries the same `request_id` in its response header and its log lines (and in Traefik's access log, if spike 1 worked);
- `test-smoke.sh` checks that `client-lookup`'s last log line parses.

## M2.2 Logs that outlive containers
**Goal:** `annex logs <app> --release r4 --level error` works after r4 was rolled back. Today Docker deletes a container's logs with the container, and every release replaces it.

**Storage** (append to `annex_ops.sql`):
```sql
CREATE TABLE IF NOT EXISTS annex_ops.logs (
  ts         timestamptz NOT NULL,
  app        text,              -- null for platform containers
  container  text NOT NULL,     -- e.g. annex-app-client-lookup, annex-ops-1
  release    int,               -- from the container's com.kaldi.annex.release label
  stream     text NOT NULL,     -- stdout | stderr
  level      text,              -- from JSON lines; else guessed: error for Traceback/ERROR/Exception lines, else null
  request_id text,
  msg        text NOT NULL,     -- the line (or its msg field), at most 8 KB
  fields     jsonb              -- the other JSON fields, minus anything that looks secret
) PARTITION BY RANGE (ts);
CREATE INDEX IF NOT EXISTS ... ON annex_ops.logs (app, ts DESC);   -- plus (request_id), (app, release), and a trigram index on msg if
                                                                      -- pg_trgm is available in the image (spike), else ILIKE on a bounded window
```
- **Partitions:** one per day, made 2 days ahead by ops, and dropped when older than `log_retention_days` (14), daily. A partition is dropped, not deleted from, so it's cheap.
- **Size guard:** if the table passes `log_max_mb` (2048), drop the oldest partition early and raise a platform signal (`platform:logs`), so admins hear about it.

**Shipping** (`ops/annex_ops/logship.py`), reusing `follow_logs.Follower` and its cursors (D42):
- One follower per shipped container (decision 5). Start it on the watcher's `Seen`/`Start` and stop it on `Destroy`.
- Each line: parse JSON (`ts`, `level`, `msg`, `request_id`, `user`, the rest into `fields`); drop keys that look secret (`password`, `token`, `secret`, `authorization`, `cookie`, case-insensitive); fill `app` and `release` from labels; batch insert (every 2 s or 500 rows), like usage's ingest. `ON CONFLICT DO NOTHING` on a content hash, as M1.4 does, so a replayed cursor can't duplicate.
- **Per-container rate cap:** 200 lines/s. Beyond it, count the dropped lines and write one line saying how many were dropped.
- **Gateway reads:** product-db's log has a `RAISE LOG` per gateway request with the app's role (D10). Follow `annex-product-db-1` and store those lines under the app (`app` from `app_<name>`, `container` = `gateway`). M2.5 aggregates them.
- **No gap on redeploy:** in `cli/ops.py` `_activate`, before `docker compose up` replaces the container, call `ctl logs-drain <container> --timeout 5`, which reads everything since the cursor and stores it. Do the same for a container that failed the health gate, before the rollback replaces it. A broken or slow annex-ops must never block a deploy: on error or timeout, the deploy carries on (log a warning). Lines written during the container's own shutdown can still be missed; say so in the docs.

**Release records in the database** (needed by the console and the audit trail):
- Table `annex_ops.releases` (app, release, image, result, deployed_at, deployed_by, via, git, note, rollback_of, manifest jsonb).
- `annex_vm.py` gets `release-record` (inserts one row as postgres, from JSON on stdin; stdlib, so through `docker exec ... psql` like the rest). `cli/ops.py` calls it wherever it appends to `releases.jsonl`, and the jsonl stays the file of record.
- `release-backfill` loads the existing `releases.jsonl` files once (idempotent).
- **Don't mount `/srv/annex/apps` into anything:** it holds app data.

**CLI and MCP:**
- `annex logs <app> [-n 100] [--since 2h] [--release rN] [--level warn] [--grep text] [--request id] [-f]`.
  - Without the new options it reads the stored logs (the same output as today, plus older lines).
  - `-f` keeps following the live container through Docker.
  - Through `ctl logs --json`.
- `annex_logs` in the MCP gets the same options except `-f`.
- **Job-only apps:** the M2.1 check now runs on the first run's stored lines (a warning in `annex status`).

**Done when:**
- a deploy that fails its health gate and rolls back still has all its lines via `annex logs <app> --release rN`;
- `annex logs client-lookup --grep novak --since 1h` finds a search;
- the gateway lines for an app are stored;
- `docker restart annex-ops-1` causes no duplicates and no gap (test as M1.4 did);
- no line in the table contains a test secret written by a fixture;
- partitions roll (test with a shortened retention in `tuning.json`).

Suite: `scripts/test-logs.sh`; one cheap check in `test-smoke.sh`. Record the database size in the resource record.

## M2.3 Errors
**Goal:** "a new kind of error appeared in client-lookup" reaches its owner, server or browser, without a new component.

- **Grouping** (pure, `ops/annex_ops/errors_group.py`), from stored lines with `level = error` (and guessed errors from unstructured lines):
  - the fingerprint is `(app, normalised message)`: numbers, UUIDs, hex ids, quoted values and file paths replaced by placeholders;
  - for a Python traceback, the exception type plus the last frame's file and function.
  - Table `annex_ops.error_groups` (fingerprint, app, first_seen, last_seen, count, first_release, last_release, sample_msg, sample_request_id).
- **Alerts:** a group seen for the first time, or again after "quiet" (not seen for `error_quiet_s`, default 24 h, or since a newer release went live), sends **one email** to the app's recipients (owner, `alerts.to`, admins), routed by `messages.recipients`.
  - At most `error_alerts_per_hour` (5) per app; the rest are summarised in the next one.
  - This is a notification, not an incident, because there's no "resolved" state to wait for. Reuse `incidents.send_alert`.
  - Log the send like every other.
- **Browser errors:**
  - `runtime/annex_runtime.js` (browser part, also served by the templates as `/annex-errors.js`) catches `window.onerror` and `unhandledrejection`, and POSTs `{msg, stack, url}` to the app's own `/api/_errors`.
  - The python and node web templates and the `static` server add that endpoint. It's rate-limited per client and logs one `level=error` line with `source=browser`, the login and the request ID.
  - So the browser only talks to its own host, behind login.
- **Resolution:** a group is "quiet since rN" when no line matched it in the current release for `error_quiet_s`. The console shows that; no email.

**Done when:**
- a forced exception in `client-lookup` (a test-only variant, like `test-rollback.sh`'s) and a forced JS error in a static app each appear as one group with release and user;
- the owner gets exactly one email per new group;
- a redeploy that fixes it shows the group as quiet in that release;
- 50 identical errors send one email, not 50.

Suite: `scripts/test-errors.sh`.

## M2.4 The console
**Goal:** builders never need the CLI or SSH just to look; Kaldi has one screen for the fleet.

**Container** (decision 4), `console`:
- the ops image with `uvicorn annex_ops.console_app:app`;
- network **`platform`** (Traefik, Gatus), plus a new internal network **`annex-console`** shared only with appdata-db, for its database. **Never `edge` or `appdata`:** apps with Postgres are on `appdata`, so they could reach it there;
- database role `annex_console` with `SELECT` on what it shows, and no access to `hook_events.body`, `app_grants` or tokens;
- `OPS_WATCHERS=0`, 96 MiB, a healthcheck, Traefik labels for `console.<domain>` with the normal forward-auth;
- `console` is already a reserved name.
- It reads Gatus's API (`gatus:8080`, on `platform`) until M2.6.

**Who sees what** (from `Remote-User` and `Remote-Groups`, which only Traefik can set here):

| | Owner (`owner` = login) | Admins | Other signed-in users |
|---|---|---|---|
| `/status` (every app and the platform, up or down) | yes | yes | yes |
| `/apps/<app>` | own apps | all | 403 |
| `/` fleet overview | their apps | all, with flags | 403, or a link to `/status` |
| Usage by person | — | yes | — |

**Pages** (server-rendered HTML, one stylesheet, no build step; a little vanilla JS only for "load more" in logs):
- **App page:**
  - status (health, open incident and its signals, last job runs);
  - releases (from `annex_ops.releases`: who, when, CLI or MCP, git, result, which is live; a failed release links to its logs);
  - usage (totals and the 4-week trend; per person for admins);
  - errors (groups, newest first, with release and request);
  - logs (search by level, release, text and request ID; paged);
  - config (the manifest from the live release, injected variable *names* only, views, Slack channels, webhooks, memory);
  - warnings (unstructured logging, no health check, a job that hasn't succeeded in 7 days).
- **Fleet overview:**
  - one row per app: owner, health, weekly users, open error groups, last deploy and warnings;
  - the graduation and dormant flags;
  - platform incidents and host numbers (`ctl host`).
- **Read-only:** no rollback, run or restart buttons in M2. Every page says so and shows the CLI command instead.

**Homepage:**
- a "Console" tile in Platform;
- the "Status" tile points at `console.<domain>/status`;
- app tiles keep the app's own URL.

**Done when:**
- `sam` sees the console for the apps he owns and nothing else; `kaldi-admin` sees the fleet; `cm` gets `/status` and a 403 on app pages;
- a request to the console container straight from an app's networks fails (it isn't on `edge` or `appdata`; test from an app with Postgres);
- a forged `Remote-User` from the browser changes nothing (`strip-identity`, tested);
- every number on an app page matches `annex status`, `annex usage` and `annex logs`.

Suite: `scripts/test-console.sh`.

## M2.5 Audit trail
**Goal:** one timeline answering "who did what, to which app, and which data did it read".

**Table** `annex_ops.audit_events` (ts, actor, app, action, details jsonb), kept `audit_retention_days` (365). Sources:

| Event | Written by |
|---|---|
| deploy, failed deploy, rollback, `--with-data` restore | `annex_vm.py release-record` (M2.2) also writes an audit row |
| secret set (names only), app removed, users add/set/remove/reset | `annex_vm.py` writes a row as it does the change (`audit-record`, stdlib, via psql) |
| gateway reads | hourly aggregates from M2.2's gateway lines: app, view, requests |
| email and Slack sends, webhook events received | views over `sends` and `hook_events` (not copied) |
| sign-ins and failed sign-ins | Authelia's log (spike 2) |

- **Spike 2:** Authelia logs failed first-factor attempts at `info`, but successful ones apparently not (checked 16 Oct: only "Unsuccessful 1FA" lines).
  - Find the cheapest reliable source: a log setting, or Authelia's `authentication_logs` in its sqlite (only if it can be read without mounting Authelia's state into ops), or a fallback.
  - The fallback: failed sign-ins from the log, plus "first signed-in request of the day per user" from Traefik's access log, which usage already ingests.
  - Write down which one, and why.
- **The actor:** for CLI actions it's `deployed_by` (user@host, not verified, D58); for MCP actions it's that plus `via: mcp`; for users it's the login.

**Outputs:**
- an "Audit" page in the console (admins);
- `annex audit [--app x] [--since 7d] [--action deploy]` (CLI, admins by convention);
- no Metabase dashboard in M2 (add one later if Kaldi wants it).

**Done when:** a scripted session (deploy, secret set, gateway reads, an email, a rollback, a user added, a failed sign-in) shows every step once, in order, with the right actor. Suite: `scripts/test-audit.sh`.

## M2.6 Retire Gatus
**Goal:** one less component, and the M1.3 workarounds go with it (the derived image, the generated config, restarting Gatus when a file is deleted).

- annex-ops checks each web app's health URL every `check_interval_s` (60). It can reach apps on `edge`.
  - It feeds the engine the same `GatusState`-shaped input after 2 failures or 2 successes (rename it `HealthState`, and keep the engine's rules).
  - It also checks the front door, as Gatus does today (`ANNEX_FRONTDOOR_URL` with `Accept: text/html`, D41).
- The app list comes from container labels (the health path label exists since M1.4), so `annex deploy` no longer writes or deletes check files.
- **Remove:** the `gatus` service, `images/gatus`, `config/gatus`, `state/gatus`, the restart in the CLI, `/internal/gatus` and `OPS_INTERNAL_TOKEN`. Keep the token's `ensure_key` line harmless or remove it with a note.
- **History** for the console comes from a small table `annex_ops.health_checks` (app, ts, ok, ms, error), kept 7 days.
- The Homepage "Status" tile becomes a `customapi` widget on `ops:/tiles/_status` (up and down counts).
- `test-alerts.sh` keeps passing with **shorter intervals** (now possible, since annex-ops reads `tuning.json`). This is the step that brings the alert suite down from 20 minutes. **Ask Nejc before running it.**

**Done when:**
- Gatus is gone;
- the console's `/status` shows the same up/down;
- the down/up scenario in `test-alerts.sh` gives one alert and one "resolved" (run with Nejc's go-ahead);
- smoke passes.
