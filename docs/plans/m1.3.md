# M1.3 implementation plan: monitoring and alerts

For a build agent. Written 15 Oct 2026 against commit `640c277` (M1.2 done). The milestone comes from Nejc's M1 plan, section "2. Downtime and error monitoring"; this file is the how, and is complete on its own.

**Read first:** `CLAUDE.md`, `docs/brief.md` (ground rules), `docs/decisions.md` (D1–D38), `docs/plans/m1.2.md` (how annex-ops was built), and this whole file. Do only M1.3. Stop when it's done and report to Nejc; don't start M1.4.

## Goal
- **The owner hears about problems before users do:** an email (and Slack, once connected) when their app is down, crash-looping, throwing errors or failing a scheduled job, a reminder if it stays broken, and a "resolved" message when it recovers.
- **Kaldi sees the whole fleet:** a status page behind login, a status widget on the discovery page, platform problems alerted to admins, and health in `annex status`.
- **No spam:** one alert per problem, however many signals notice it.

## Done when (acceptance, from the M1 plan)
1. Stopping an app, making it crash-loop, failing a job, and forcing a burst of 500s **each produce exactly one alert to the owner and one "resolved"** (and the same pair to admins).
2. A stopped platform service alerts admins only, then resolves.
3. The discovery page shows live status (Gatus widget), and `status.<domain>` serves the Gatus page behind login.
4. `annex status <app>` shows the current health, any open incident, and the last run of each job.
5. `scripts/test-alerts.sh` passes, and so do all earlier suites: `test-platform.sh`, `test-apps.sh`, `test-jobs.sh`, `restore-test.sh`, `test-rollback.sh`, `test-notify.sh`.

## Decisions already made for you
Defaults chosen when this plan was written. Log each in `docs/decisions.md` (what, why, alternatives); continue from D39.
1. **Recipients.** App problems go to the owner (the `com.kaldi.annex.owner` label → email from the user directory) and to every user in group `admins`. Platform problems go to admins only. If Slack is connected, every alert is also posted to `#annex-alerts` (setting `ANNEX_ALERT_SLACK_CHANNEL`). If the owner isn't in the directory, admins get it with a note saying so.
2. **The status page is visible to every signed-in user** (the existing catch-all Authelia rule). It shows app names and up/down, which the discovery page already shows.
3. **Incidents, not alerts.** One open incident per *subject*: `app:<name>`, `job:<app>/<job>` or `platform:<service>`. Signals (below) attach to their subject's incident. The first signal opens it and sends the alert; later signals are added to it without a new message; "resolved" goes out once every signal has cleared. That's what makes "stop an app", which both Gatus and Docker notice, produce exactly one alert.
4. **Job failures come from Ofelia's log, not Docker `exec_die` events.** Exec events only carry the command, and `monthly-report`'s two jobs run the same command; they also can't tell a scheduled run from `annex run`, whose caller already sees the exit code. Ofelia's log names the job and says `failed: true/false`. (This deviates from the M1 plan's wording; log it.)
5. **A 60 s grace period before "stopped".** Deploys, rollbacks, `secret set` and the Ofelia restart (D18) stop a container for a few seconds; none of them may alert. Only `restore.sh` and `rollback --with-data` (which can take longer) open a maintenance window.
6. **Thresholds** (all overridable, see "Tuning"): down = 2 failed Gatus checks 60 s apart, cleared by 2 good ones; crash loop = 3 non-zero exits within 10 min, cleared after 10 min without one; error spike = ≥ 5 % 5xx **and** ≥ 10 errors in 5 min, cleared after 5 min below; reminder after 1 h, then every 24 h.
7. **Containers are the registry.** annex-ops reads owner, alert recipients and job names from the app container's labels through the read-only socket proxy. No registration API.
8. **Gatus needs a derived image** for its healthcheck: the official image has no shell and no `wget` (checked on the VM: `user=` root, entrypoint `/gatus`, no healthcheck). `images/gatus/Dockerfile` copies a static busybox `wget` in. Every platform container keeps a healthcheck, as CLAUDE.md requires.
9. **Gatus is on `annex-edge`** so it can probe apps on their internal port. Any app could therefore read Gatus's API (up/down of every app) without login. That's not data; accept it and log it.
10. **Extras** (Metabase, Dozzle) being stopped is never alerted (`scripts/extras.sh off` does that on purpose); them being unhealthy while running is.
11. **`alerts.to` in `annex.yaml`** (contract v1, optional): extra logins or Slack channels to alert, besides the owner.
12. **No external heartbeat.** If the VM dies, nothing on it can say so; that needs something off the LAN, which the brief rules out. Note it in the decisions as a production item.

## How the pieces fit
```
Gatus (edge + platform) ── every 60 s ──▶ http://annex-app-<app>:<port><healthcheck>  (one file per app, written by annex deploy)
      │                └── every 60 s ──▶ https://home.<domain>/ via Traefik's edge alias, expects 302 (front door)
      └─ webhook on TRIGGERED/RESOLVED ─▶ ops /internal/gatus (Bearer OPS_INTERNAL_TOKEN)
ops: docker events  ◀── socket-ro ──  die / start / stop / destroy / health_status / oom
ops: log follower   ◀── socket-ro ──  annex-traefik-1 (JSON access log → 5xx per app), annex-ofelia-1 (job results)
ops: engine thread  ── one queue, one writer ──▶ incidents ──▶ send_email(app="_platform") / post_slack(...)
annex status ─ssh─▶ docker exec annex-ops-1 python -m annex_ops.ctl app-status <app> --json
```

## Step 3. annex-ops: watching
New modules in `ops/annex_ops/`. Use only the standard library for the Docker API (`http.client` to `socket-ro:2375`), as for Slack and SMTP: no new dependencies.

- **`docker_api.py`**: `get_json(path)`, `stream_events(since, filters)` (newline-delimited JSON; yields dicts), `stream_logs(container, since, follow=True)` (demultiplexes Docker's 8-byte frame headers; yields `(timestamp, stream, line)`; request `timestamps=1`), `tail_logs(container, n)` (for alert messages), `containers()` (`/containers/json?all=1` with the label filter).
- **`watch_docker.py`**: at startup, a reconcile pass over `containers()` (which are running, which unhealthy); then follow events from that moment, reconnecting with `since=<last event time>` if the stream ends. Only containers with a `com.docker.compose.project` of `annex` or `annex-app-*` count; others with the Annex label (test probes, `docker run --rm` helpers) are ignored. Turn events into engine inputs: `die` (with `exitCode`), `start`, `stop`, `destroy`, `health_status: healthy|unhealthy`, `oom`.
- **`follow_logs.py`**: a generic follower, one thread per container name, that keeps a cursor in `annex_ops.log_cursors` (container name → last timestamp) and survives the container being restarted or recreated (when the stream ends, wait 2 s, re-resolve the name, resume from the cursor; drop lines at or before the cursor). **M2.2 will reuse it to ship every container's logs, so keep it generic:** it takes a container name and a line handler. On first start (no cursor), begin at now minus 10 minutes.
  - **Traefik handler:** lines starting with `{` are access log entries (the rest is Traefik's own log). Use `RouterName` `app-<name>@docker` → app, `DownstreamStatus`, `StartUTC`. Feed `(app, ts, status)` to the engine's error-rate window.
  - **Ofelia handler:** strip ANSI codes; match `[Job "<key>" (<id>)] Finished in "<dur>", failed: <bool>, skipped: <bool>, error: <text>`. Map `<key>` to `(app, job)` via the app containers' labels (`ofelia.job-exec.<key>.schedule` on `annex-app-<app>`; cache, refresh on `start`/`destroy` events): app and job names both contain `-`, so never split the key on `-`. Record a row in `job_runs` and feed the result to the engine. Skipped runs count as neither.
- **`app.py`**: `POST /internal/gatus` (Bearer `OPS_INTERNAL_TOKEN`, compared with `hmac.compare_digest`; 401 otherwise) → engine input `down` set or cleared for `app:<endpoint>` (group `apps`) or `platform:front-door` (group `platform`). Start the watcher, follower and engine threads in a FastAPI `lifespan` (daemon threads), unless `OPS_WATCHERS=0` (for unit tests). `ctl.py` must not start them.

**`compose.yaml`** for ops: add network `socket-ro`; mount `${ANNEX_DATA_DIR}/state/ops:/annex/state:ro` (the tuning file); environment `ANNEX_ALERT_SLACK_CHANNEL`, `ANNEX_URL_STATUS`, `ANNEX_HOST_PATTERN`, `ANNEX_PORT_SUFFIX` (to build app links in messages).

## Step 4. annex-ops: the engine
**`engine.py`: pure logic, no DB, network or clock of its own,** so every rule is unit-tested. It holds open incidents and per-container counters, takes inputs `(now, input)` and returns actions (`open`, `add_signal`, `resolve`, `remind`, `forget`). `tick(now)` evaluates time-based rules (grace periods, windows, reminders).

| Signal | Subject | Raised when | Cleared when |
|---|---|---|---|
| `down` | `app:<a>` or `platform:front-door` | Gatus TRIGGERED | Gatus RESOLVED |
| `stopped` | `app:<a>` or `platform:<service>` | a container is not running 60 s after `die`/`stop` | `start` |
| `crash-loop` | same | 3 `die` with non-zero `exitCode` within 10 min | no `die` for 10 min and running |
| `unhealthy` | same | `health_status: unhealthy` | `health_status: healthy` |
| `oom` | same | `oom` | with `crash-loop` / `stopped` |
| `errors` | `app:<a>` | ≥ 5 % 5xx and ≥ 10 5xx in the last 5 min | 5 min below the threshold |
| `job-failed` | `job:<a>/<job>` | an Ofelia run with `failed: true` | the next run of that job with `failed: false` |

- `platform:<service>` uses `com.docker.compose.service`; ignore `stopped` for `metabase` and `dozzle` (decision 10).
- `destroy` → forget the container's counters and resolve its open incident **silently** (`annex remove`, `extras.sh off`). A Gatus webhook for an app with no container is ignored.
- **Maintenance:** a subject in maintenance (until a time) collects signals but sends nothing; when maintenance ends, signals still active open the incident then.
- **Reminders:** first after 1 h open, then every 24 h, each listing the current signals.
- On restart, the engine loads open incidents from the DB and the watcher's reconcile pass re-establishes current state. A signal that cleared while ops was down is cleared by the reconcile pass (e.g. running → no `stopped`).

**`incidents.py`**: persistence and side effects. One engine thread consumes a `queue.Queue` that the watchers and the webhook put inputs on, and runs `tick` every 15 s. It's the only writer, so there are no races. It applies actions to the tables and sends:
- **Recipients** (decision 1): the subject's owner from the container label plus extra logins and channels from `com.kaldi.annex.alerts-to`; admins from the directory (`groups` contains `admins`). Send with M1.2's internal `email.send_email(app="_platform", ...)`, and `slack.post_slack("_platform", ANNEX_ALERT_SLACK_CHANNEL, ...)` plus any app channel from `alerts-to` only when Slack is connected. Never let a failed send crash the engine; it's logged in `sends` already.
- **Message** (use the `notice` template; if it collapses newlines, add an optional escaped, monospace `details` field to it, with a unit test):
  - subject `[Annex] client-lookup is down`, `[Annex] monthly-report: job "monthly" failed`, `[Annex] platform: gateway stopped`, `[Annex] reminder: ...`, `[Annex] resolved: client-lookup is back (down 7 min)`;
  - body: what, since when, the active signals with their details, the last 20 log lines (`tail_logs`), and links: the app's URL, `{{ANNEX_URL_STATUS}}`, and the command `annex logs <app>`.

**Schema** (append to `db/appdata/annex_ops.sql`, idempotent, as the M1.2 tables):
```sql
CREATE TABLE IF NOT EXISTS annex_ops.incidents (
  id               bigserial PRIMARY KEY,
  subject          text NOT NULL,              -- app:<a> | job:<a>/<job> | platform:<service>
  app              text,                       -- null for platform
  opened_at        timestamptz NOT NULL DEFAULT now(),
  resolved_at      timestamptz,
  resolved_quietly boolean NOT NULL DEFAULT false,  -- removed apps: no "resolved" message
  last_notified_at timestamptz,
  reminders        int NOT NULL DEFAULT 0,
  signals          jsonb NOT NULL DEFAULT '{}', -- active: {"down": {"since": ..., "detail": ...}, ...}
  history          jsonb NOT NULL DEFAULT '[]'  -- every signal raised/cleared, for the console (M2)
);
CREATE UNIQUE INDEX IF NOT EXISTS incidents_one_open ON annex_ops.incidents (subject) WHERE resolved_at IS NULL;
CREATE TABLE IF NOT EXISTS annex_ops.job_runs (
  id bigserial PRIMARY KEY, app text NOT NULL, job text NOT NULL, finished_at timestamptz NOT NULL,
  ok boolean NOT NULL, duration_ms int, error text);
CREATE INDEX IF NOT EXISTS job_runs_app_job ON annex_ops.job_runs (app, job, finished_at DESC);
CREATE TABLE IF NOT EXISTS annex_ops.log_cursors (container text PRIMARY KEY, ts timestamptz NOT NULL);
CREATE TABLE IF NOT EXISTS annex_ops.maintenance (subject text PRIMARY KEY, until timestamptz NOT NULL);
```
Keep `job_runs` for 90 days (delete older rows in `tick`, once a day).

**Tuning:** every threshold has a default in `config.py`, overridable by env and, at runtime, by `/annex/state/tuning.json` (re-read when its mtime changes): `stopped_grace_s`, `crash_count`, `crash_window_s`, `crash_stable_s`, `error_window_s`, `error_min`, `error_ratio`, `reminder_first_s`, `reminder_repeat_s`, `tick_s`. The test shortens them; production never has the file.

**`ctl.py`** additions (all `--json`):
- `app-status <app>`: Gatus's current result for `apps_<app>` (from Gatus's API; `"unknown"` if Gatus can't be reached), the open incident (subject, since, signals) or none, and the last run per job.
- `incidents [--open] [--app X]`.
- `maintenance <subject> --minutes N` and `maintenance <subject> --end`.

**Unit tests** (`ops/tests/test_engine.py` and friends, run as in M1.2): stop + Gatus down → one open, one resolve; crash loop counting and clearing; a deploy-length stop (under the grace period) → nothing; error-rate thresholds (ratio and minimum both needed); job fail → resolve on the next good run of the *same* job only; reminders at 1 h and 25 h; maintenance holds then releases; `destroy` resolves quietly; extras' stops ignored; the Ofelia line parser (success, failure, skipped, ANSI codes); the job-key mapping with names that contain `-`; Docker frame demultiplexing; the Traefik line parser.

## Step 6. Tests
**Fixture `tests/alert-probe/`**: a standard-library Python app (no pip), `type: web+job`, owner `sam`, port 8080, `healthcheck: /healthz`, `storage: {files: true}`, one job `check` every minute (`* * * * *`, `["python", "probe.py", "check"]`). Its Dockerfile follows the python templates (uid 10001, `HEALTHCHECK`).
- `/healthz` → 200; `/boom` → 500.
- A background thread checks `/data/crashes` every second: if it holds a number above 0, it writes the number minus one and exits with code 1. On start it checks immediately, so the app crash-loops until the counter reaches 0, then recovers by itself. (`kill 1` won't work: PID 1 ignores signals it has no handler for.)
- `probe.py check` exits 1 while `/data/failjob` exists, else 0.

**`scripts/test-alerts.sh`**, in the style of the other suites:
- Setup: write short timings to `/srv/annex/state/ops/tuning.json` (e.g. grace 10 s, crash window 120 s, stable 30 s, error window 60 s, reminder 90 s; restore defaults on exit with a `trap`). Deploy `tests/alert-probe` and log in as `sam` through the tunnel. Clear Mailpit (`DELETE /api/v1/messages` as `kaldi-admin`).
- A helper counts Mailpit messages by recipient and subject (`GET /api/v1/search?query=...`) and polls until a count is reached or a timeout passes.
- Scenarios, one after another, each waiting for its resolve before the next:
  1. `docker stop annex-app-alert-probe` → exactly one alert `alert-probe is down` (or `stopped`, whichever signal came first) to `sam@annex.example` and one to `admin@annex.example`; keep it stopped past the reminder time → one reminder; `docker start` → exactly one `resolved` each. Expect about 3–5 minutes (Gatus's 60 s interval is the floor).
  2. `docker exec annex-app-alert-probe sh -c 'echo 4 > /data/crashes'` → one `crash-loop` alert, then one `resolved` after it recovers by itself.
  3. 20 × `GET /boom` as `sam` through the tunnel → one `errors` alert, then one `resolved`.
  4. `docker exec annex-app-alert-probe touch /data/failjob` → one `job "check" failed` alert; remove the file → one `resolved` after the next good run.
  5. `docker stop annex-gateway-1` → one platform alert to `admin@annex.example` and **none** to sam; `docker start` → one `resolved`.
- Also: `annex status alert-probe` shows `health_check` up, no incident and the `check` job's last run; Gatus's API lists `apps_alert-probe` and `platform_front-door`, both up; Homepage lists "Status".
- Teardown: `annex remove alert-probe --yes` → no "resolved" or other message for it (quiet forget), and its Gatus file is gone.
- Expect the whole suite to take 12–20 minutes; print timings per scenario.

Then redeploy `examples/client-lookup` and `examples/monthly-report` (so they get Gatus checks and the new label) and run every suite. **Known flake:** right after a deploy that restarts Ofelia, `test-platform.sh` reports Ofelia as "health: starting" for up to 30 s; wait until it's healthy. Leave `vibe-leads` alone: it gets its Gatus check on its next deploy (note this in the decisions, like D32).

## Pitfalls
- New manifest fields need defaults: rollback loads manifests stored by older releases.
- `master.env` is append-only via `ensure_key`; init SQL runs only on a fresh DB, so the schema goes in `annex_ops.sql` (applied by `push.sh`).
- `docker restart` does **not** re-read env files; recreate with `docker compose up -d --force-recreate <svc>` when env changes (see setup.md).
- Single-file bind mounts go stale (D7): mount directories (`state/gatus/apps`, `state/ops`).
- Gatus expands `$VAR` in its config: escape literal `$` as `$$`.
- Docker log streams for non-TTY containers are multiplexed (8-byte headers); the access log of Traefik shares stdout with Traefik's own log lines.
- App and job names contain `-`: map Ofelia keys through labels, never by splitting.
- ops runs read-only as uid 10001; it writes only to its database.
- Never put tokens in messages, logs or `ctl` output.
